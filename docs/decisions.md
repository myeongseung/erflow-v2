# 결정 로그 — erflow-v2

바꾸는 것마다 «왜» 를 남긴다. **"왜 이렇게 했는가"가 없으면 나중에 원복된다.**

번호는 전작([legacy-decisions.md](legacy-decisions.md), D-001~D-115)에 이어
**D-116 부터** 매긴다 — 코드 주석의 D-번호가 두 로그에 걸쳐 유일해야 한다.

전작과 규율이 하나 다르다. 그쪽은 «레거시가 정답» 이라 정답을 벗어나는 결정만
적었지만, 여기서는 정답을 우리가 만든다 — **화면·동작·스키마를 바꾸는 모든
결정**을 적는다.

---

## D-116 · 앱이 자기 스키마를 갖는다 — `erflow_v2`

전작은 스키마가 둘이었다. `erflow` 가 정답이고 `erflow_mig` 가 이관 대상이었다.
이 저장소는 레거시가 정답이 아니므로 **스키마를 우리가 바꾼다** — 그런데 계속
`erflow_mig` 를 쓰면 전작의 1단계 산출물이 우리 변경으로 덮인다. 「레거시와 행
수·뷰가 일치한다」는 증거가 사라지고, 나중에 «이게 원래 그랬나» 를 물을 자리가
없어진다.

**결정: 스키마 셋으로 간다.**

| 스키마 | 몫 | 권한 |
|---|---|---|
| `erflow` | 레거시 정답 | SELECT 만 — 관례가 아니라 권한으로 막는다 (D-011) |
| `erflow_mig` | 전작 1단계 산출물 | **동결.** 손대지 않는다 |
| `erflow_v2` | 이 저장소의 앱 스키마 | 읽고 쓴다 |

**만드는 방법.** 같은 서버 안이라 덤프 도구도 설치도 필요 없었다. 복제는 전부
SQL 이다 — `SHOW CREATE TABLE` 의 DDL 을 그대로 재실행했다. `CREATE TABLE LIKE`
는 외래키를 빠뜨리는데, DDL 재실행은 FK·AUTO_INCREMENT·컬럼 COMMENT·charset 까지
옮긴다. 데이터는 `INSERT ... SELECT`, 뷰 15개는 `DEFINER` 를 떼고 스키마 참조를
치환해 재생성했다(뷰-위-뷰 의존이 있어 회차를 돌렸다). 트리거·루틴은 0 이었다.

**collation 을 명시했다.** `CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci` —
`erflow` 와 `erflow_mig` 가 둘 다 이 값이다(O-005 에서 실측). 이걸 안 박고 서버
기본값에 맡기면 **한글 정렬이 조용히 어긋난다.** 화면에서 줄 순서가 달라지는데
아무 오류도 안 난다.

**앱 코드는 한 줄도 바뀌지 않았다.** 매퍼의 테이블명이 전부 비수식이라 어느
스키마를 쓰는지는 접속 URL 하나가 정한다. 다만 `application.yml` 의 기본값은
바꿨다 — `erflow` 를 가리키고 있었다. 프로파일 없이 뜨면 앱이 정답 스키마를
향한다는 뜻이고, 지금은 SELECT 만 있어 실패하지만 기본값이 그걸 노리고 있을
이유가 없다.

**`LegacyCloneTest` 는 그대로 뒀다.** 질의가 전부 스키마 수식이라 접속이
`erflow_v2` 를 향해도 계속 `erflow` ↔ `erflow_mig` 를 본다. 오히려 나아졌다 —
시험이 데이터를 건드려도 `erflow_v2` 에만 쌓이므로 baseline 대조가 시험 실행에
오염되지 않는다.

**한계 하나를 적어 둔다.** 스키마 신설은 앱 계정으로 못 한다. 그 계정은 `*.*` 에
`USAGE` 뿐이어서 `CREATE DATABASE` 가 오류 1044 로 거부된다. 권한 있는 계정으로
두 줄이 선행돼야 한다 — 사람 손이 필요한 지점이다.

```sql
CREATE DATABASE erflow_v2 CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
GRANT ALL PRIVILEGES ON erflow_v2.* TO '<앱 계정>'@'%';
```

**검증.** `erflow_mig` 와 대조해 다름 0 — 테이블 35 · 뷰 15 개수, 테이블·뷰별 행
수 전부, 컬럼 정의(이름·순서·타입·널·기본값·collation·주석·extra), 인덱스 항목,
외래키 3개, `AUTO_INCREMENT` 다음 값. 그 위에서 `./gradlew build` 가 348건 초록.

## D-117 · 주민등록번호는 뒷자리 한 자리만 남긴다 (O-012 해소)

레거시 사원 리스트는 주민등록번호를 **13자리 그대로** 표에 찍었다. 관리자만 들어오는
화면이라 1단계에서는 그대로 옮기고 안건으로 남겼다(O-012) — 화면에 보이는 글자를
바꾸는 일은 이관이 아니었다.

**수정:** 뒷자리 일곱 중 첫 한 자리만 남긴다(2026-08-21, 사용자 판단).

```
999999-9999999  ->  999999-9******
```

**왜 한 자리는 남기는가.** 그 자리는 성별·세기 코드다. 표에는 «성별» 과
«내·외국인» 칸이 따로 있고 나이도 거기서 나온다. 앞 여섯 자리와 이 한 자리가
있으면 그 셋을 그대로 읽을 수 있다 — **가리면서 잃는 정보가 없다.** 정말로 감춰야
하는 것은 그 뒤 여섯 자리다. 글자 수도 열넷 그대로라 칸 너비가 흔들리지 않는다.

**어디를 고쳤는가.** 둘이다.

- `admin/user/list.html` — 안건이 지목한 자리
- `admin/user/update.html` — 같은 값을 `readonly` 입력에 **전체로** 찍고 있었다.
  리스트만 가리고 이쪽을 두면 관리자가 한 화면에서는 가려진 값을, 옆 화면에서는
  전체를 본다. 가리는 의미가 없어진다

**수정 화면을 건드려도 안전한 근거.** `readonly` 입력도 폼과 함께 전송된다. 가린
값이 되돌아와 저장되면 데이터가 망가진다 — 그런데 `updateUser` 문장에
`social_number` 가 **없다**(레거시부터 없었고, 매퍼 주석에 적혀 있다). 저장되는
곳이 없어서 안전하다. 시험이 이 짝을 못 박는다.

**건드리지 않은 자리.** `admin/user/register.html` 은 새 번호를 **입력하는** 자리라
그대로 둔다(`insertUser` 는 이 값을 저장한다). `profile/update.html` 은 이미
`value=""` 로 비어 있고, 그것을 지키는 시험도 있다.

**가리는 규칙을 한곳에 뒀다.** `common/SocialNumbers` — 흩어 두면 또 어긋난다
(`LegacyDates` 와 같은 이유). 두 가지를 정해 두었다.

- **비어 있는 값은 비어 있는 그대로.** 빈칸을 별표로 채우면 없는 값이 있는 것처럼
  보인다. 실제로 55명 중 넷이 비어 있다
- **모양이 다른 값은 통째로 가린다.** 어디까지가 앞자리인지 모르는 채로 일부만
  남기면 그 «일부» 가 뒷자리일 수 있다. 모르면 더 가리는 쪽이 맞다. 지금 저장된
  51건은 전부 `999999-9999999` 이지만 규칙이 형식에 기대지 않게 해 둔다

**검증.** `./gradlew build` 357건 초록(348 + 9). 리스트 시험은 응답에 13자리 모양이
**아예 없는지**를 본다 — 그 화면에는 예시조차 없으므로 그 모양이 나오면 실제 값이
실린 것이다. 수정 화면 시험은 DB 에 저장된 값 자체가 응답에 없는지 본다.

## D-118 · 본문 HTML 은 지우지 않고 거른다 (O-010 해소)

레거시는 본문을 `out.print(content)` 로 내보냈다 — **저장된 HTML 이 그대로
실행된다**. 1단계는 `th:utext` 로 같은 동작을 옮기고 안건으로 남겼다(O-010). 자리는
셋이다: 게시글 본문, 결재 문서 내용, 문서 양식 미리보기.

**이스케이프는 답이 아니었다.** 저장된 내용을 세어 보고 알았다.

| 컬럼 | 태그 있는 행 | 무엇이 들어 있나 |
|---|---|---|
| `post_tbl.content` | 11 / 17 | `p` 30 · `a` 2 · `img` 1 |
| `document_tbl.content` | **16 / 16** | `td` 304 · `tr` 130 · `table` 16 · `input` 24 · `h1`·`div`·`span` |
| `template_tbl.content` | 2 / 3 | 같은 표 구조 + `input` 8 |

결재 문서와 양식은 **본문 전체가 표**다. `th:text` 로 바꾸면 결재 문서 16건이 태그
글자 무더기가 된다. 이 자리는 «HTML 이 곧 화면» 이므로 **지우는 대신 거른다.**

**수정:** 허용목록 정화기를 통과한 HTML 만 내보낸다. `common/SafeHtml` 한 곳에
정책을 두고, 세 화면이 `contentSafe()` 를 찍는다.

### style 을 허용해야 했다

정화기의 기본 설정은 `style` 을 지운다. 그런데 결재 문서의 표는 **테두리·배경색·
정렬·높이가 전부 인라인 `style`** 이다 — `td[style]` 186개를 셌다.

```
border-color:black; border-style:solid; border-width:1px
background-color:lightblue; text-align:center
border-collapse:collapse; border:1px solid black; margin:0 auto
```

지우면 문서가 테두리 없는 맨 표가 되어 알아볼 수 없다. 그래서 `style` 을 허용하되
**CSS 속성 이름과 값까지 검사**한다. 속성 목록은 코드에 못 박았고 값 검사는
라이브러리가 한다 — `url(...)`·`expression(...)` 이 든 값은 통과하지 못한다.

**`position` 과 `z-index` 는 목록에 없다.** 그 둘이 있으면 저장된 본문이 화면 위에
투명한 덮개를 씌워 남의 클릭을 가로챌 수 있다. 실제 데이터도 쓰지 않는다.

### input 에 name·value 를 주지 않는다

양식의 `input` 32개에 **`name` 도 `value` 도 없다** — `type`·`style`·`checked` 뿐이다.
즉 그 칸들은 «빈칸 모양» 이고 폼 기능이 아니다. 모양만 살리면 충분하고, `name` 을
허용하면 저장된 본문이 **화면의 진짜 폼에 칸을 끼워 넣을** 수 있다.

### 주소는 http·https·mailto 만

실제 데이터의 링크·그림은 `https:` 와 상대경로뿐이다. `javascript:` 와 `data:` 를
막아도 잃는 것이 없다.

### 저장할 때가 아니라 찍을 때 거른다

DB 는 그대로 둔다. 그래서 **이미 저장된 본문도 즉시 보호되고**, 정책이 지나쳤다는
것이 나중에 드러나도 되돌릴 수 있다. 저장할 때 걸렀다면 사람이 쓴 글이 영구히
깎이고, 기존 39건은 여전히 위험한 채로 남는다.

편집 화면(`form-register`)은 **원본을 그대로 받는다.** 거른 값을 편집기에 넣으면
저장할 때마다 서식이 조금씩 깎여 나간다.

### 부수 효과 하나

정화기가 표를 **정규화**한다 — `<table><tr>` 사이에 `<tbody>` 를 채워 넣는다.
브라우저가 파싱할 때 하는 일과 같아서 화면은 달라지지 않는다. 1단계에 «양식 내용은
HTML 그대로 나간다» 를 못 박아 둔 시험이 있었고, 기대 문자열을 정규화된 모양으로
고쳤다 — 그 시험의 뜻(«이스케이프되면 태그가 보인다»)은 그대로다.

### 지금 위험이 심어져 있었나

**없었다.** 저장된 본문 전체에 `<script` 도, `on...=` 이벤트 속성도 없다. 이 결정은
이미 벌어진 일을 되돌리는 것이 아니라 **앞으로를 막는 것**이다.

### 의존성

`com.googlecode.owasp-java-html-sanitizer:20240325.1`. CSS 속성 검사가 내장되어 있어
이 문제에 정확히 맞는다 — 직접 만들면 틀릴 방법이 너무 많다. 이 버전은 guava 를
끌고 오지 않는다(얇은 shim 둘뿐).

### 남는 한계

DB 에는 여전히 무엇이든 들어갈 수 있다. 막는 것은 «내보내는 자리» 이므로, **새로
`th:utext` 자리를 만들면 반드시 `contentSafe()` 를 찍어야 한다.** 원본을 그대로 찍는
자리가 하나 생기면 그 화면만 다시 열린다.

**검증.** `./gradlew build` 369건 초록. 정책 시험 11건이 «실행되는 것은 사라지고
서식은 남는다» 를 양쪽으로 못 박고, 결재 문서 시험은 **실제 저장된 문서**를 걸러도
표와 `style` 이 남는지 본다 — 정책을 나중에 조이다가 서식을 깎으면 거기서 깨진다.

## D-119 · 화면을 다시 그린다 — Tailwind 위의 자체 디자인 시스템

전작은 «레거시가 정답» 이라 화면을 손댈 수 없었다. 이 저장소는 화면을 다시 그린다.
그런데 열어 보니 **디자인이 낡은 것보다 배선이 망가진 것이 더 급했다.**

| 무엇 | 상태 |
|---|---|
| `code.jquery.com/jquery-latest.min.js` — **76곳** | jQuery 가 2014년에 동결한 URL. 영원히 1.11.x 를 준다 |
| `https://.../jquery-ui.js`, `https://.../all.min.css` | 말줄임표가 그대로 든 **깨진 URL** |
| FullCalendar | **CSS 5.10.1 + JS 6.1.9.** 6부터 CSS 가 JS 에 들어갔으니 그 링크는 죽은 참조. 게다가 메인 화면이 6.1.9 를 **두 번** 싣는다(모듈판·전역판) |
| `kit.fontawesome.com/a81368914c.js` | **남의 FontAwesome 키트 ID** |
| `raw.githubusercontent.com`, `bootdey.com` | 남의 사이트 이미지를 직접 링크 |
| CSS 2.2MB | `bootstrap.css` 와 `bootstrap2.css` 가 각 280KB(거의 같은 파일). rtl·min·grid·utilities 변종까지 전부 동봉 |

**결정: Tailwind v4 위에 자체 디자인 시스템을 올린다.** 스타일시트는 하나
(`app.css`)로 모으고 Bootstrap 은 걷어낸다. 2.2MB → **20KB**(압축).

### 왜 standalone 바이너리인가

Tailwind 는 실행 파일을 배포한다. `node`·`node_modules` 없이 Gradle 태스크로 돌므로
**빌드가 Gradle 하나로 닫힌다.** 바이너리는 `tools/`(gitignore)에 두고 — `build/` 에
두면 `clean` 마다 다시 받는다 — 만들어진 CSS 는 `build/generated` 에만 두고 리소스
소스셋에 얹는다. 생성물이 `src/` 에 섞이면 무엇이 손으로 쓴 것인지 알 수 없게 되고,
실수로 커밋된다.

### 왜 기존 클래스 이름을 다시 구현하는가

`btn` 199 · `table` 104 · `form-group` 91 · `input-group` 63 … 이름은 Bootstrap 것인데
**`form-group` 은 Bootstrap 5 에 없는 이름이다.** 즉 지금 보이는 모양의 상당 부분은
이미 Bootstrap 이 아니라 자체 CSS 였다.

그래서 컴포넌트 레이어가 **그 이름들을 그대로 재구현한다.** 마크업을 한 줄도 안
건드리고 화면이 새 디자인이 된다. 107화면의 class 속성을 동시에 고치는 일은 되돌릴
수도, 확인할 수도 없다.

### 방향 — «작업대»

하루 종일 보는 사내 도구다. 그래서 «눈에 띄는 화면» 이 아니라 **«눈에 안 띄는 도구»**
로 잡았다.

- **껍데기는 물러난다** — 사이드바는 짙은 흑연이라 배경이 되고 읽을 것이 없다
- **본문은 따뜻한 오프화이트** — 순백은 형광등처럼 눈을 찌른다
- **상자가 아니라 실선 한 겹** — 표에 세로줄을 넣지 않는다. 줄이 많아질수록 세로줄은
  격자 소음이 되고, 가로 실선이면 눈이 행을 따라간다
- **강조색은 차가운 강철 파랑 하나** — 상태색(초록·노랑·빨강)과 겹치지 않는 색이라야
  «출근/지각/결근» 을 색으로 읽을 수 있다
- **숫자는 `tabular-nums`** — ERP 의 표는 자릿수가 맞아야 읽힌다

글꼴은 Pretendard 를 **자체 호스팅**한다. `/fonts/**` 를 보안 설정의 허용 목록에
넣었다 — 막혀 있으면 로그인 화면조차 글꼴 없이 뜬다.

### 아이콘은 CDN 이 아니라 그려 넣는다

화면 전체가 쓰는 아이콘은 **여덟 개**뿐인데 그 여덟을 위해 FontAwesome 전체를 싣고
있었다. SVG 마스크로 그려 넣었고 기존 클래스 이름에 걸리므로 마크업은 그대로다.

세어 보니 실제로는 **열한 개**였다 — 셋이 **DB 에서 온다.** 헤더가
`class="${item.icon}"` 로 찍고 `menu` 테이블에 `fa-gear`·`fa-user-tie`·`fa-envelope`
가 들어 있다. **화면만 훑어서는 보이지 않는 자리다.**

### 함정 넷 (다음 사람을 위해)

**1. Tailwind 유틸리티가 컴포넌트 레이어를 이긴다.** 그래서 레거시 Bootstrap 클래스
이름이 Tailwind 유틸리티 이름과 겹치면 조용히 덮인다. 실제로 둘이 터졌다.

- `collapse` — Tailwind 에서 `visibility: collapse` 다. 헤더의
  `class="collapse navbar-collapse"` 때문에 **헤더 메뉴 전체가 보이지 않았다**
- 같은 이름이 게시글 답글 폼에도 있었다. 그쪽은 Bootstrap 의 `display: none` 에
  기대 숨어 있었고 jQuery `slideToggle()` 로 열렸다. Bootstrap 이 나가면 **기본으로
  펼쳐지고**, Tailwind 가 덮으면 «자리는 차지하는데 안 보이는» 상태가 된다.
  `slideToggle()` 은 display 를 만지므로 visibility 로 숨은 것을 열지 못한다

→ `.fold` 로 개명했다. **새 클래스 이름을 지을 때 Tailwind 유틸리티 이름을 피한다.**
남은 겹침 둘은 두고 본다 — `table`(`display: table`, 표에는 무해)과
`container`(Tailwind 가 max-width 를 덮는다).

**2. 옛 CSS 와 섞을 수 없다.** CSS 레이어 규칙상 **레이어 없는 CSS 가
`@layer components` 를 무조건 이긴다.** 화면별 CSS 를 남겨 두면 순서를 어떻게 해도
절반만 새 디자인이 된다. 그래서 한 번에 갈아탄다.

**3. 쪽 번호의 `disabled` 는 «현재 쪽» 이다.** 레거시가 «누를 수 없는 쪽» 이라는 뜻으로
붙였다. 흐리게 칠하면 **«지금 여기» 가 가장 안 보이는 칸이 된다** — 강조색으로 칠한다.

**4. `.menu-name` 은 제목이 아니라 길 표시다.** 39화면 전부
「사용자 > 생산관리 > 생산 설비 관리」 가 들어온다. 처음에 제목으로 보고 강조선을
붙였다가 되돌렸다. **이 앱에는 화면 제목 자리가 아예 없다** — 껍데기를 다시 그릴 때
마지막 조각을 제목으로 올린다.

### 눈으로 확인했다

시험은 마크업을 거의 붙잡지 않는다 — `contains` 단정 231개 중 마크업·클래스에 묶인
것은 **9개**뿐이다. 그래서 시험이 초록이어도 화면이 무너졌는지는 알 수 없다.

그래서 실제로 띄워 보고 찍었다. 방법을 적어 둔다 — 로그인 계정이 없어도 된다.
**시험 하네스의 인증을 재사용해** 화면을 그려 HTML 로 떨어뜨리고(절대경로를 띄워 둔
앱으로 돌려놓고), headless Chrome 으로 찍는다. 그렇게 위의 함정 넷을 다 잡았다.
쓰고 나서 그 임시 도구는 지웠다 — 시험이 아닌 것이 시험 자리에 남으면 빌드마다 파일을
쓴다.

### 100화면 전부를 공용 head 로 모았다

처음 센 «47/53» 은 틀린 기준이었다 — 그건 «조각을 아예 안 쓰는 파일» 수였다. 실제
기준은 «`<head>` 를 `th:replace` 하는가» 이고, 그 기준으로는 **100화면 중 34개만**
공용 head 를 썼다. 본문은 조각을 쓰면서 head 만 손으로 쓴 화면이 많았다.

66화면을 옮겼다. 66번 손으로 고치면 반드시 어딘가 틀리므로 변환기를 썼고, **자신
없는 화면은 건드리지 않고 이름을 남기게** 만들었다 — 조각이 표현할 수 없는 것
(`type=module`·`integrity`·인라인 스크립트·낯선 `meta`)이 하나라도 있으면 그 파일은
통째로 건너뛴다. 결과는 diff·빌드·실화면 그림으로 확인했다.

**함정 다섯: 조각 선택자는 요소 이름으로도 매칭한다.** 옮기는 동안 인수를 셋에서
둘로 줄이려고 «구식 호출을 위한 다리» 를 같은 파일에 두었다. 34화면이 한꺼번에
터졌다 — `~{fragments/head :: head(...)}` 의 `head` 가 `th:fragment` 이름이 아니라
**`<head>` 요소**에 걸려 앞의 조각이 잡혔고, 「2개를 선언했는데 3개가 왔다」로 죽었다.
문서 순서에 기대는 해법은 두지 않았다. 구식 호출부 34곳을 모두 옮기고 다리를 없앴다 —
**이 파일에 `<head>` 는 하나뿐이라야 한다.**

### popper 를 걷어냈다 — 12화면을 묶고 있던 매듭

popper CDN 태그에는 `integrity`·`crossorigin`·`referrerpolicy` 가 붙어 있어 공용
조각이 표현할 수 없었다. 그것 하나 때문에 12화면이 자체 `<head>` 에 발이 묶였다.

그런데 popper 를 싣는 54화면이 **하나도 빠짐없이 `bootstrap.js` 도 함께** 싣고
있었고, 저장소에 이미 `bootstrap.bundle.js`(같은 5.3.1, Popper 포함)가 있었다. 둘을
번들 하나로 줄이자 **외부 CDN 하나가 통째로 사라지고** 매듭도 풀렸다.

메인 화면은 **FullCalendar 를 두 번** 싣고 있었다 — cdnjs 의 ESM 판(`type="module"`)과
jsdelivr 의 전역 판. 앞의 것은 module 로 실어도 전역에 아무것도 붙이지 않아 죽은
참조였다. 지웠다.

### 옛 CSS 를 지웠다

이제 템플릿이 참조하는 스타일시트는 `/css/app.css` **하나뿐**이다. `bootcss`
2.0MB(업스트림 Bootstrap 17개 파일)를 지웠다 — 언제든 다시 받을 수 있고, 잣 파일이
남아 있으면 «혹시 쓰나» 를 계속 물어야 한다.

화면별 CSS 60개(267KB)는 **남겨 둔다.** 아무도 읽지 않지만, 화면을 하나씩 다시 그릴
때 «이 화면이 원래 어떤 레이아웃이었나» 를 볼 자리다. 그 작업이 끝나면 지운다.

### 화면별 레이아웃을 다시 짰다

화면별 CSS 를 내리자 «레이아웃이 그 파일에 있던» 화면들이 뼈대만 남았다. 갈래를 세어
보니 표 중심 29 · 폼 중심 47 · 그 밖 24 였고, **그 밖 24 중 14는 `result.html`**
— 몸통이 `alert()` 와 `location.href` 뿐이라 보이는 것이 없다. 손댈 자리가 아니었다.

**여백을 화면 컨테이너로 올렸다.** 레거시는 화면마다 다른 이름의 래퍼에 여백을
붙였다 — `user-insert-wrap`·`proposal-insert-wrap`·`table-wrap`·`wrap`·`box-wrapper`…
이름을 하나씩 쫓으면 반드시 빠뜨리고, 빠뜨린 화면만 글자가 벽에 붙는다. 그래서
«사이드바 옆에 오는 것» 과 «관리자 헤더 아래 오는 것» 에 한 번에 준다. **이름을
몰라도 걸린다.**

**폼은 판 위에 올리고 폭을 묶었다.** `form:has(.form-group)` 으로 «입력 묶음을 담은
폼» 만 고른다 — 목록 화면의 검색 폼은 `form-group` 을 쓰지 않아 걸리지 않는다. 묶지
않으면 입력칸이 1300px 까지 늘어나 라벨에서 입력으로 가는 눈의 거리가 멀어진다.
**규칙 한 벌이 폼 화면 47장을 동시에 덮는다.**

**단추는 요소에 기본 모습을 줬다.** 레거시는 화면마다 자기 이름의 단추를 갖는다 —
`userRegister-btn`·`btn_execDaumPostcode`·`goto-index`… 이름을 다 쫓는 대신 `button`
과 `input[type=submit]` 자체를 칠했다. 이름이 없어도 단추로 보인다.

**메인 화면**은 위젯 폭이 픽셀로 박혀 있었다(위젯 500px·달력 610px). 격자로 바꿔
`[위젯·위젯][달력]` 이 폭을 나눠 갖게 하고, 좁아지면 달력이 아래로 내려간다. 위젯
높이는 못 박았다 — 내용에 맡기면 두 열의 아래가 어긋나 판이 흔들린다. 이름 없는
`<div>` 세 자리에는 이름을 붙였다(`main-column`·`widget-column`·`calendar-column`);
이름 없는 div 에 걸린 규칙은 마크업이 한 겹만 바뀌어도 조용히 어긋난다.

**로그인·오류·팝업**은 껍데기를 거치지 않아 여백 규칙이 닿지 않았다. 따로 줬다.

### 남의 자산을 걷어냈다

로그인 3화면이 **남의 FontAwesome 키트 ID**(`kit.fontawesome.com/a81368914c`)를 부르고
**남의 GitHub 저장소**의 아바타 SVG 를 직접 링크하고 있었다. 프로필 화면은
`bootdey.com` 의 견본 아바타를 링크했다. 셋 다 걷어냈다 — 아이콘은 이미 우리가 그려
둔 것으로 대체되고, 아바타는 자리표시로 바꿨다. 남의 사이트가 내리면 깨지는 것을
화면에 두지 않는다.

프로필 화면에 남아 있는 «Website / Github / Twitter — bootdey» 다섯 줄은 **견본의
글자 그대로**다. 이번에는 손대지 않았다 — 지우는 것은 레이아웃이 아니라 내용
판단이고, 화면 다듬기 때 함께 본다.

### 함정 여섯·일곱

**6. Tailwind 의 `container` 유틸리티가 22화면의 폭을 빼앗고 있었다.** `collapse` 와
같은 충돌이다 — `width:100%` 에 중단점마다 `max-width` 까지 붙고, 유틸리티는 컴포넌트
레이어를 이긴다. 로그인 카드를 24rem 로 묶으려 해도 먹지 않았다. `page-box` 로 이름을
바꿨다(22곳). **레거시 클래스 이름이 유틸리티 이름과 겹치는지 먼저 본다.**

**7. `:read-only` 는 텍스트 입력만 뜻하지 않는다.** «읽기 전용 입력은 회색» 규칙을
`input:read-only` 로 썼더니 **로그인 단추가 회색이 됐다** — `input[type=submit]` 도
편집할 수 없으므로 `:read-only` 에 걸린다. 게다가 `:not()` 을 둘 붙여 특이도가
(0,3,1)이라 `.login-content .btn` 을 이겼다. 화면이 실제로 적어 둔 것만 잡도록
`input[readonly]` 로 바꿨다. **의사클래스가 뜻하는 범위를 확인하고 쓴다.**

### 달력이 안 그려지던 진짜 이유

메인의 «일정관리» 가 빈 상자였다. 이중 로딩 때문인 줄 알았는데 아니었다 —
`calendar.render()` 가 **ajax 성공 콜백 안에만** 있었다. `/calendar/view` 가 실패하면
오류를 로그에 찍고 끝이라 **달력 자체가 그려지지 않는다.** 일정이 없는 것과 서버가
대답하지 않는 것은 다르고, 어느 쪽이든 달력은 보여야 한다. 먼저 그리고 나서 일정을
얹도록 고쳤다.

### 껍데기를 하나로 합치고 제목 자리를 만들었다

**상단 바가 둘이었다.** 사용자 쪽은 Bootstrap navbar 마크업, 관리자 쪽은 자체
클래스(`admin-header`). 같은 앱인데 위쪽이 화면마다 다르게 생겼고, 고칠 때마다 두 번
고쳐야 했다. 합칠 수 있었던 이유는 `LayoutModelAdvice` 가 `headerMenu`·`currentUser`
를 **모든 화면에** 넣어 주기 때문이다 — 관리자 화면도 이미 갖고 있었다. 조각 하나로
모으고 `admin-header.html` 은 지웠다.

**자리도 맞췄다.** 관리자 화면은 사이드바가 세로로 다 차지하고 헤더가 오른쪽 칸
«안에» 들어가는 구조였다. 이제 둘 다 «상단 바 + [사이드바 | 본문]» 이다. 사이드바
맨 위의 상표 자리는 접었다 — 상표가 한 화면에 둘일 이유가 없다.

**화면 제목이 생겼다.** 이 앱에는 제목이 없었다. 39화면이 **오른쪽 구석의 작은 길
표시 한 줄**로 「사용자 > 생산관리 > 생산 설비 관리」 를 말하는 것이 전부였고, 화면을
열었을 때 눈이 먼저 닿는 곳이 없었다.

길 표시의 **마지막 조각이 곧 그 화면의 이름**이다. 그것을 떼어 제목으로 올리고 길
표시는 위에 작게 남겼다 — **글자를 새로 지어내지 않았다. 자리만 바꿨다.**

39곳이 세 가지 모양이었다(정적 28 · 인라인 식 2 · `th:text` 9). 전부 `|...|` 리터럴
치환 하나로 모아 조각 호출로 바꿨다. 변환기는 이번에도 **자신 없으면 물러나게**
만들었고, 실제로 company 세 화면에서 물러났다 — `th:text` 값 **안에 `>` 가 있어서**
속성 끝을 잘못 잡은 것이었다. 그 셋은 손으로 했다.

**함정 여덟: Thymeleaf 의 `#strings` 에는 `substringAfterLast` 가 없다.** 마지막
조각을 떼려고 그것을 썼다가 관리자 화면 전부가 터졌다. `arraySplit` 으로 자르고
마지막 칸을 쓴다 — 구분자가 없는 길 표시는 조각이 하나뿐이라 갈래도 필요 없다.

시험 하나를 고쳤다. `LayoutRenderTest` 가 «레거시 헤더의 고정 요소» 로 `section2`
(헤더 아래 파란 띠)를 붙잡고 있었는데, 상단 바를 합치면서 그 띠는 없앴다 — 둘 중
한쪽에만 있던 장식이다. 그 자리에 «합친 상단 바» 를 확인하는 단정을 넣었다.

**`jquery-latest` 는 버전이 없는 이름이 아니라 «1.11.1 에 고정» 이다.** jQuery 가
2014년에 그 주소를 동결했다 — 받아서 배너를 확인했다. 그래서 이 앱은 화면에 따라
1.11.1 과 1.12.4 **두 버전**을 쓰고 있었다.

**1.12.4 로 모았다.** 1.x 의 마지막이고, 이미 7화면이 쓰던 것이고, 1.11.1 을 겨냥해
쓴 코드가 그대로 돈다. **3.x 로 올리는 것은 별도 판단이다** — 자체 JS 51개가 걸려
있고 제거된 API(`.load()`·`.bind()`·`.size()`…)를 하나씩 봐야 한다.

**두 가지는 남겼다.** 성격이 다르다.

- **Daum 우편번호**(17곳) — 라이브 *서비스*다. 내려받아 두면 그쪽이 주소 체계를
  고칠 때 우리만 옛것을 쓴다. 남의 서버를 부르는 것이 맞는 자리다
- **CKEditor 4.22.1**(5곳) — 내려받을 수는 있지만 플러그인을 실행 중에 더 받는
  구조라 통째로 옮겨야 한다. 게다가 **CKEditor 4 는 지원이 끝났다** — 자체 호스팅이
  아니라 «무엇으로 바꿀까» 를 정할 자리다

**죽은 외부 참조 하나를 더 걷어냈다.** `datepicker.js` 의 `buttonImage` 가
`http://jqueryui.com/resources/demos/...` 를 가리켰다 — 남의 데모 서버이고 평문
HTTP 다. 그런데 `showOn` 이 주석 처리돼 **그 버튼은 그려지지도 않는다.** 관련 설정
셋을 함께 뺐다.

**날짜 고르기를 우리 디자인으로 다시 그렸다.** 저장소에 남의 테마(`jquery-ui.css`,
36KB)가 있었지만 화면별 CSS 를 내리면서 같이 내려갔다 — 달력이 꾸며지지 않은 표가
돼 있었다. 그 테마를 되살리는 대신 여기서 그린다. 쓰는 위젯이 **달력과 줄 끌기 둘
뿐**이라 그편이 짧다.

**`readonly` 가 두 뜻으로 쓰인다는 것도 드러났다.** 폼 안에서는 «못 고치는 칸»
(사번·주민번호)이고, `.input-group` 안에서는 «값을 보여 주는 자리» 다 — 레거시가
글자를 입력칸에 담아 찍었고 23화면이 그렇다. 뒤엣것까지 회색 상자로 두면 화면이
«고칠 수 없는 폼» 처럼 보인다. 자리를 갈랐다.

### 아직 남은 것

레이아웃의 큰 줄기는 섰다. 남은 것은 «내용에 손이 가는» 자리다.

- **프로필 화면** — 견본에서 온 다섯 줄(Website/Github/Twitter/Instagram/Facebook,
  값은 전부 `bootdey`)이 그대로 있다. Bootstrap 격자 클래스(`col-md-4`·`d-flex`·
  `list-group`)에도 기대고 있어 따로 봐야 한다
- **바깥 상자 이름이 아직 둘이다** — `admin-wrap` 과 `content-wrap`. 보이는 것은
  같아졌지만 이름을 하나로 합치려면 마크업 100장을 건드려야 해서 두고 본다
- **jQuery 3.x** — 지금은 1.12.4 다. 올리려면 자체 JS 51개를 봐야 한다
- **상태 색** — 결재·근태 상태색이 Java 에서 인라인 `style` 로 나온다. 우리 팔레트로
  바꾸려면 서버를 함께 고쳐야 하고, 라벨 통일(D-068)과 묶는 편이 낫다

  *(화면별 CSS 는 D-124 에서 지웠고, 관리자 홈은 D-123 에서 표로 폈다.)*

**검증.** `./gradlew build` 369건 초록 — 화면 100장의 head 를 갈아끼우고, CSS 를 전부
바꾸고, 레이아웃을 다시 짜는 동안 시험이 하나도 깨지지 않았다. 시험이 마크업을 거의
붙잡지 않기 때문이며, 그래서 **그림으로 확인하는 절차가 시험을 대신하지 못한다** —
둘 다 필요하다. 이번에 잡은 결함 넷(로고 터짐·쪽번호 반전·`:read-only`·달력 미렌더)은
전부 그림에서만 보였다.

## D-120 · 편집기를 Jodit 4 로 바꾼다 (CKEditor 4 종료)

게시글·결재 문서·문서 양식 다섯 화면이 **CKEditor 4.22.1** 을 남의 CDN
(`cdn.ckeditor.com`)에서 받아 쓰고 있었다. **CKEditor 4 는 지원이 끝났다** —
자체 호스팅으로 옮길 것이 아니라 무엇으로 바꿀지 정해야 하는 자리였다(D-119).

### 무엇을 편집해야 하는지부터 셌다

| 자리 | 내용 |
|---|---|
| 게시글 등록·답변·수정 | `p` 30 · `a` 2 · `img` 1 — 단순 서식 |
| 결재 문서 작성 | 양식을 불러와 채운다 — **표 HTML** (`td` 304 · `input` 24) |
| 문서 양식 작성 | 양식 자체 + HTML 파일을 읽어 부어 넣는 길 |

**결재 문서는 고치는 화면이 없다** — 만들기만 한다. 16건은 기록이고 화면 표시는
편집기가 아니라 정화기(D-118)를 지난다. 그러니 편집기를 바꿔도 옛 문서는 그대로
보인다. **실제로 편집되는 것은 문서 양식 3건뿐이다.**

### 제일 큰 걸림돌은 «빈칸» 이었다 — 그런데 아니었다

양식에 `<input>` 이 24개 박혀 있다. 요즘 편집기 대부분은 스키마를 갖고 있어
스키마 밖의 것을 **조용히 버린다** — 양식을 불러와 저장할 때마다 빈칸이 사라진다는
뜻이다. 이것이 CKEditor 5·Quill·Toast UI 계열을 떨어뜨린 이유다.

속성을 세어 보니 그 `input` 들에 **`name` 도 `value` 도 없었다**(`type`·`style`·
`checked` 뿐). 제출되지도 값을 담지도 않는, 「여기에 쓰세요」 표시일 뿐이다.

### 고른 기준 넷

**MIT**(사내 비공개 배포라 GPL 계열은 상용 계약이 필요하다) · **빌드 없이
`<script>` 하나**(이 저장소는 node 없이 Gradle 하나로 닫혀 있다, D-119) ·
**살아 있는 유지보수** · **기존 양식 보존**.

npm 레지스트리로 실제 배포일과 라이선스를 확인하고, **LICENSE 파일까지 받아**
읽었다 — 메타데이터만 믿지 않는다.

| | 라이선스 | 최근 배포 | 비고 |
|---|---|---|---|
| SunEditor 3.3.0 | MIT | 2026-08-06 | **3.0 은 최근의 대규모 재작성** |
| Jodit 4.13.23 | MIT | 2026-08-18 | 4.x 의 13번째 마이너 |
| Quill 2 · Toast UI | MIT/BSD | — | 표·인라인 style 을 버린다 |
| CKEditor 5 · TinyMCE 7 | GPL/상용 | — | 라이선스로 탈락 |

### 실물로 쟀다

「비슷해 보인다」로는 판단할 수 없어서, **실제 양식(근태계)을 넣고 되읽어 태그와
속성 개수를 원본과 대조**했다.

Jodit 4 — **손실 0.** `input` 8→8, `input[type]`·`input[style]` 8→8,
`td` 19→19, `th` 4→4, `td[style]` 18→18, `colspan`·`rowspan`·`table[border]`
전부 그대로, 보이는 글자도 같았다. 늘어난 것은 빈 셀의 `<br>` 여덟 개뿐이다 —
빈 셀을 누를 수 있게 하는 표준 동작이고 정화 목록에 `br` 이 있다.

**SunEditor 3 은 판정하지 못했다.** 초기화는 됐지만(실패 원인은 내가 넘긴
`lang: 'ko'` 옵션이었다) 내용을 넣고 되읽는 API 를 찾지 못했다 — README 의
호출법과 번들 안에 실제로 있는 문자열(`html.set`·`getValue`)로 네 번 시도했고,
인스턴스가 열거로 내놓는 키는 `$` 하나였다. **「안 된다」가 아니라 「내가 못
했다」** 이며, 그렇게 적어 둔다. 다만 제약이 «무빌드 드롭인» 인 상황에서 문서대로
해서 안 돌아갔다는 것은 약한 신호이긴 하다.

**결정: Jodit 4.13.23.** 제약을 다 만족하는 하나면 충분하다 — SunEditor 를 더
파서 얻을 수 있는 최선은 「둘 다 된다」이고 그러면 결정은 그대로다.

**양식 3건을 다시 만들 필요가 없어졌다.** 그대로 살아남는다.

### 도구모음을 정화 목록에 맞춰 깎았다

화면에 나가는 HTML 은 `SafeHtml` 의 허용목록을 지난다(D-118). 편집기가 그 목록
밖의 것을 만들 수 있으면 **「저장했는데 화면에서 사라지는」** 일이 생긴다. 그래서
단추를 목록에 맞춰 골랐다 — 영상·파일 넣기가 없는 것이 그 때문이다.

**그림은 주소로만 넣는다**(`insertImageAsBase64URI: false`). 파일을 끌어다 놓으면
base64 (`data:` 주소)가 되는데 허용 프로토콜은 http·https·mailto 뿐이라 저장 뒤에
사라지고, 게다가 본문 칸에 수 MB 가 들어앉는다.

### 설정을 한 곳으로 모았다

레거시는 게시글 셋이 `js/common/editor.js` 를 공유하고 결재 화면 둘은 각자 화면
안에 `CKEDITOR.replace` 를 적어 두었다. 다섯 화면이 같은 편집기를 쓰는데 설정이
흩어져 있을 이유가 없다 — `js/common/editor.js` 하나로 모았다. 되돌릴 때도 그
파일 하나만 보면 된다.

**편집기 CSS 는 편집기가 스스로 불러온다.** 화면이 싣는 스타일시트는 `app.css`
하나라는 것이 규칙인데(D-119), 다섯 화면에만 필요한 161KB 를 100화면이 나눠 지게
할 수는 없다. 그래서 `editor.js` 가 실행 중에 `<link>` 를 붙인다.

### 남은 외부 참조는 하나뿐이다

화면이 부르는 남의 주소는 이제 **Daum 우편번호**(17곳)뿐이다. 그건 라이브
*서비스*라 내려받아 두면 그쪽이 주소 체계를 고칠 때 우리만 옛것을 쓰게 된다 —
남의 서버를 부르는 것이 맞는 자리다.

### 미리보기 상자가 좁아 표가 흘러나왔다

실제로 눌러 보고서야 보였다. 양식 목록의 «보기» 모달을 열면 **표가 상자 밖으로
흘러 옆 화면을 덮었다.**

저장된 양식이 **A4 폭으로 못 박혀 있기 때문**이다 — 바깥 div 가
`width: calc(21cm + 14px)`(약 808px)인데 모달은 44rem(704px)이었다. 상자를 넓히고
(58rem), 그래도 넘치면 **상자 안에서 가로로 굴리게** 했다. 화면 밖으로 흐르게 두지
않는다.

같이 걸린 것 하나. **저장된 본문에도 `class` 가 들어 있다** — 양식의 바깥 div 가
`class="wrap"`, 그 안이 `class="container"` 다. 우리 화면 클래스와 **이름이
겹친다.** 지금은 둘 다 해가 없지만 화면 쪽에서 같은 이름에 레이아웃을 주면 저장된
문서가 그 규칙에 끌려간다 — 본문 안에서는 끊어 뒀다. 정화 목록이 `class` 를
통과시키는 한(서식이 거기 걸려 있으니 통과시켜야 한다) 늘 있는 위험이다.

**검증.** `./gradlew build` 369건 초록. 그리고 실제 화면을 띄워 근태계 양식이
편집기 안에 표·하늘색 셀·체크상자까지 그대로 뜨는 것, 미리보기 모달 안에 온전히
들어가는 것을 눈으로 확인했다.

## D-121 · 줄마다 자기 양식이 열린다 (D-066 해소)

문서 양식 리스트의 «보기» 는 모달을 연다. 그 모달이 `th:each` **안에** 있어 양식
수만큼 그려지는데, **셋 다 id 가 `calendar-plus` 로 같았다.** 버튼도 전부 그 id 를
가리켰다.

브라우저는 중복 id 에서 첫 번째를 집는다. 그래서 **2번·7번·9번 어느 줄의 «보기»를
눌러도 첫 줄(근태계)이 떴다.** 전작이 «레거시 그대로» 로 옮기며 기록해 둔 결함이다
(D-066).

이름 자체가 흔적이다 — `calendar-plus` 는 **메인 화면의 일정 등록 모달** id 이고,
이 화면은 그 자리를 통째로 복사해 왔다. 지금도 `index.html` 에 같은 이름이 있다.

**수정:** id 에 양식 번호를 붙인다.

```
th:id="'template-preview-' + ${template.id}"
th:data-bs-target="'#template-preview-' + ${template.id}"
```

닫기는 손대지 않았다. `documentFormList.js` 가 `$('.close-button')` 과
`$('.modal')` 로 — 클래스로 — 잡고 있어서 id 가 바뀌어도 그대로 돈다.

**딸린 것 하나.** `aria-labelledby="calendar-plus-label"` 이 **없는 요소를
가리키고 있었다**(이 모달에는 제목 요소가 없다). 매달린 참조를 지우고 양식 제목을
`aria-label` 로 준다 — 글자를 지어내지 않고 이미 그 줄에 있는 값을 쓴다.

**시험으로 못 박았다.** 이 결함은 **시험에 잡히지 않았다** — 화면이 그려지기만
하면 통과했기 때문이다. 이제 모달 id 가 겹치지 않는지, 버튼이 가리키는 곳이
모달과 짝이 맞는지, 옛 이름이 남아 있지 않은지를 본다. 양식이 없으면 건너뛰게
해 두었지만 실제로는 3건이 있어 돌았다(건너뜀 0을 확인).

**검증.** `./gradlew build` 370건 초록.

## D-122 · 프로필 화면에서 남의 견본을 걷어낸다

프로필 왼쪽에 **Website · Github · Twitter · Instagram · Facebook** 다섯 줄이
있었다. 값이 전부 `bootdey` 였다 — 부트스트랩 견본(bootdey.com)의 글자 그대로이며
사용자 정보와 아무 상관이 없다. 아바타도 그 사이트 그림을 직접 링크했다(D-119 에서
자리표시로 바꿨다).

1단계는 «화면에 보이는 것이므로 옮긴다» 로 두었다. 그 규율은 옳았다 — 그때는
레거시가 정답이었다. **이제 화면은 우리가 정한다.** 지웠다.

### 격자를 되살리지 않고 구조를 바꿨다

레거시는 이 화면을 부트스트랩 격자(`row` + `col-md-4/8` + `col-sm-3/9`)로 짰다.
그런데 **그 격자를 쓰는 화면이 이 하나뿐이다.** 12칸 격자를 되살리는 것은 한 화면을
위해 규칙 열둘을 들이는 일이라, 이 화면의 구조를 우리 것으로 바꿨다 —
`profile-layout`(옆칸 + 본문) · `info-list`(라벨과 값).

값이 비어 있으면 `—` 를 찍는다. **비었다는 것도 정보다** — 라벨만 덩그러니 남으면
«안 불러온 것» 인지 «없는 것» 인지 알 수 없다.

### 머리글이 없는 칸을 선언하고 있었다

근무 현황 표의 머리글이 `<th colspan="5">통계</th>` 였다. 그런데 통계 칸은
«정상·지각·조퇴·연차» **넷**이다.

칸을 세어 보면 모든 줄이 20칸이다 — 앞줄 16칸(1~16일) + 통계 4칸, 뒷줄 16칸
(17~32일, 달을 넘는 날은 빈 칸) + 통계 4칸. **머리글만 21칸을 선언했다.** 그
한 칸이 표를 제 몸보다 넓게 만들어 **맨 오른쪽 «연차» 가 잘렸다.** 넷으로 맞췄다.

1단계 기록(D-077)에 «두 줄의 칸 수가 하나 어긋난다 — 그대로 옮긴다» 로 적혀 있던
그것이다. 화면을 다시 그리는 지금이 고칠 자리다.

### 범례 색은 서버가 칠하는 값 그대로

색상자 다섯(`box1`~`box5`)에 색이 없어 흰 네모였다. 칠하되 **`WorkCalendar` 가 날짜
칸에 넣는 색과 똑같이** 맞췄다 — 정상 `greenyellow` · 지각 `yellow` · 조퇴
`skyblue` · 결근 `#E51A2E` · 연차 `#dbdbdb`. 범례가 그림과 다른 색을 말하면 없느니만
못하다.

이 색들은 레거시 팔레트라 디자인 시스템과 어긋난다. 다만 **칸 색이 Java 에서 인라인
`style` 로 나오므로** 팔레트를 바꾸려면 서버를 함께 고쳐야 한다 — 라벨 통일(D-068)과
같이 볼 자리로 남긴다.

### `id="box"` 가 다섯 번 있었다

색상자마다 `id="box"` 가 붙어 있었다. D-066 과 같은 종류의 결함이다(중복 id). 아무도
그 id 로 찾지 않아 겉으로 드러나지 않았을 뿐이다. 지웠다 — 구분은 `box1`~`box5`
클래스가 한다.

**시험 하나를 뒤집었다.** `ProfileScreenTest` 가 `contains("https://bootdey.com")`
으로 **견본 글자가 있는 것**을 못 박고 있었다. 이제 `doesNotContain("bootdey")` 로
없는 것을 못 박는다.

**검증.** `./gradlew build` 370건 초록. 화면을 띄워 견본 카드가 사라진 것, 라벨과
값이 갈린 것, 표의 «연차» 칸이 잘리지 않는 것을 눈으로 확인했다.

## D-123 · 관리자 홈의 표를 표로 편다

관리자 홈의 결재 판이 이상하게 보였다. 값들이 **회색 입력칸에 담겨** 늘어서 있고
머리글과 아귀가 맞지 않았다.

마크업을 보니 이유가 분명했다.

```
<th>사번</th> <th>문서제목</th> <th>결재요청시각</th> <th>진행상황</th>   ← 넷
<td>사번</td> <td colspan="3"> input-group( 제목 | 시각 | 상태 ) </td>   ← 둘
```

**머리글은 네 칸인데 몸통은 두 칸**이고, 그 한 칸 안에 `input-group` 으로 세 값을
욱여넣었다. 값이 `readonly` 입력으로 나오니 «고칠 수 없는 폼» 처럼 보였다(D-119 에서
`.input-group` 안의 readonly 를 글자로 읽히게 바꾼 것이 이 자리다 — 그것만으로는
정렬이 해결되지 않는다).

**수정:** 표로 편다. 머리글 넷에 셀 넷. 상태는 알약(`status-badge`)으로 만든다.
출/퇴근관리 표도 같은 모양이라 같이 폈다.

색은 그대로 서버가 준다(`ProposalStatus.color` — 승인 `#C2FF63` · 반려 `#EA7B86` ·
진행 중 `#FFFF40`). 레거시 팔레트라 우리 색과 어긋나지만 **색이 Java 에서 인라인
`style` 로 나오므로** 바꾸려면 서버를 함께 고쳐야 한다 — 프로필 범례와 같은
자리이고, 라벨 통일(D-068)과 함께 볼 일이다.

레이아웃도 격자로 다시 짰다. 왼쪽에 근무 현황·결재, 오른쪽에 수/발주·공지사항·
출퇴근. 좁아지면 한 줄이 된다.

### 내가 만든 규칙이 남의 화면을 밟았다

프로필의 근무 달력을 꾸미며 `.table-bordered` 에 **가운데 정렬과 작은 글자**를 줬다.
그런데 `table-bordered` 는 관리자 홈의 **공지사항 표도 쓰는 이름**이었다 — 제목이
한가운데로 몰렸다.

`.main-body .table-bordered` 로 그 화면 안에 가뒀다. **재구현하는 클래스 이름이
두 화면에서 다른 뜻으로 쓰이는지 먼저 세어야 한다** — 이번에는 두 곳뿐이라 금방
찾았지만, 그림으로 보지 않았으면 몰랐을 일이다.

### 고치지 않은 것

**출/퇴근관리 판이 머리글만 있고 비어 있다.** 확인해 보니 렌더링 결함이 아니라
**자료가 없다**(오늘 출근 기록 0건). 「기록이 없습니다」 같은 문구를 넣을 수도
있지만, 화면에 없던 글자를 지어내는 일이라 사람 판단으로 남긴다.

**근무 현황 그래프**도 자료를 못 받으면 빈 자리다. `adminGraph.js` 에 오류 처리는
있으나 화면에는 아무 말도 하지 않는다 — 달력에서 고친 것(D-119)과 같은 성격이지만,
원 그래프는 자료가 없으면 그릴 것이 없어 «먼저 그린다» 가 통하지 않는다. D-069(그래프
이름 밀림)와 함께 볼 자리다.

**검증.** `./gradlew build` 370건 초록. 화면을 띄워 결재 표가 머리글과 맞는 것,
상태가 알약으로 나오는 것, 공지사항 제목이 왼쪽으로 돌아온 것을 눈으로 확인했다.

## D-124 · 화면별 CSS 를 지운다 — 그리고 그것이 드러낸 것

화면별 CSS 60개(267KB)를 남겨 두었다. **아무도 읽지 않지만** 화면을 하나씩 다시 그릴
때 «원래 어떤 레이아웃이었나» 를 볼 자리로 쓰려 했다(D-119).

지웠다. 지우기 전에 확인한 것 — 템플릿이 참조하는 스타일시트는 `/css/app.css`
하나, JS 가 끌어들이는 것 없음(편집기 CSS 는 `/js/vendor/` 에서 온다), Java 에 언급
없음. `clean build` 로 처음부터 다시 지어도 370건 초록이고, 산출물의 CSS 는
`app.css` 하나다.

### 지우기가 드러낸 것

**삭제가 화면을 깨뜨린 것이 아니다.** 그 파일들은 D-119 이후로 실려 본 적이 없다.
다만 그 뒤로 **내가 한 번도 열어 보지 않은 화면**이 있었고, 이 정리를 하며 비로소
열었다.

- **결재 문서 보기** — 좌우 두 단이 뭉개지고, 결재선 도장 표가 겹쳐 「결재라인」이
  세로로 흘렀다. 이 앱의 중심 업무 화면이다
- **게시글 보기** — 머리말(작성자·작성일·댓글수·조회수)이 세로로 쌓이고 댓글 목록이
  줄줄이 늘어졌다

둘 다 짰다. 문서는 종이처럼 보이는 판에 담고 도장 표를 오른쪽 위에 붙였다. 게시글은
머리말을 한 줄로 묶고(작성자는 왼쪽, 나머지는 오른쪽) 댓글을 판으로 갈랐다.

게시글 머리말은 마크업이 잘못돼 있다 — `<table class="subject">` 안에 `div` 를
쌓아서 브라우저가 표 밖으로 밀어낸다. 구조를 건드리지 않고 **표 노릇을 그만두게**
해서(`display: block`) 블록으로 읽히게 했다. 마크업을 고치는 편이 옳지만 그것은
이 화면을 다시 짜는 일이고, 지금은 보이는 것을 바로잡는 데서 멈춘다.

### 교훈

«참고용으로 남겨 둔다» 는 대체로 자기기만이다. 267KB 를 여섯 달 두었어도 열어 보지
않았을 것이고, **정작 필요한 것은 파일이 아니라 화면을 열어 보는 일**이었다. 지우는
김에 열어 봤고, 그래서 두 화면을 찾았다.

git 이 갖고 있으니 언제든 `git show` 로 꺼낼 수 있다. 그것으로 충분하다.

**검증.** `./gradlew clean build` 370건 초록. `app.css` 47KB — 화면별 CSS 267KB 와
Bootstrap 2.0MB 를 합쳐 2.2MB 이던 것이 여기까지 왔다.

## D-125 · 근무 상태의 이름과 색을 한 벌로 — 그리고 거기서 나온 것들

D-068 은 «라벨이 두 자리에서 다르다» 로 남아 있던 안건이다. 열어 보니 그보다
넓었다 — 같은 코드를 **네 곳이 따로** 읽고 있었고, 둘이 틀리고 있었다.

### 뭐가 어긋나 있었나

**그래프의 3·4 가 뒤바뀌어 있었다.** `adminGraph.js` 만 `['결근','출근','퇴근',
'지각','조퇴',...]` 이었고 나머지 세 곳은 전부 «3 조퇴 · 4 지각» 이다 —
출퇴근 표, `WorkCalendar` 의 집계(3을 `leave`, 4를 `late` 로 센다), `AttendanceSheet`
가 칸에 직접 찍는 글자. **어느 쪽이 맞느냐는 취향이 아니라 사실이다.**
그래프가 틀렸고, 조퇴와 지각이 서로의 이름을 달고 나오고 있었다.

**조퇴 색도 화면마다 달랐다.** 달력은 `skyblue`, 근태표는 보라(`#8507F7`).
반대로 **반차와 연차는 둘 다 `#dbdbdb`** 라 구분이 안 됐고, 범례에는 반차가
아예 없었다(다섯 칸을 손으로 적어 둔 탓이다).

### 어떻게 했나

`com.erflow.common.WorkStatus` 하나가 유일한 출처다. 이름도 거기서 나오고, 색은
거기서 정한 **클래스 이름**을 타고 `app.css` 의 `--color-status-*` 로 간다.
Java 는 «무슨 상태인가» 만 말하고 색은 디자인 체계가 정한다.

같은 이름이 자리마다 다르게 쓰인다 — 달력 칸은 바탕을, 근태 표는 글자를,
범례는 작은 네모를 칠한다. 원 그래프는 SVG라 CSS 로 못 칠하므로 `adminGraph.js`
가 `--color-status-*` 를 직접 읽는다. 그래도 값은 한 곳이다.

코드 1 은 **«근무 중»** 이다(사용자 판단). 코드 2 가 «퇴근» 이므로 1 은 «아직
일하는 중» 이라는 뜻이고, 근무 시간을 계속 세는 동작과도 맞는다.

범례는 이제 상태 목록에서 그려 낸다. 손으로 적지 않으니 어긋날 자리가 없고,
일곱 칸이 되면서 반차가 돌아왔다. 반차·연차는 회색 두 단으로 갈랐다.

**결재 상태도 같이 넘겼다.** `ProposalStatus` 가 `#C2FF63` 같은 형광색을 인라인
style 로 뿜고 있어 화면을 다시 그려도 그 세 개만 떠다녔다. 같은 방식으로
클래스로 바꾸니 알약이 나머지 화면과 같은 팔레트로 들어왔다.

### 열어 보지 않았다면 몰랐을 것 — 그래프의 나머지 셋

라벨만 고치려고 `adminGraph.js` 를 열었는데 세 개가 더 있었다.

- **없는 조각을 그렸다.** `for (i = 0; i < keys.length; ++i)` 로 늘 일곱 칸을
  돌았다. 그날 세 상태만 있었으면 나머지 넷은 `{name: undefined, value:
  undefined}` 가 되고 `d3.pie()` 가 NaN 각도를 만든다
- **색이 자리로 정해졌다.** 색 다섯 개를 `d.index`(조각 순서)로 골랐다. 상태는
  일곱인데 색은 다섯이고, 게다가 순서라 **어제 초록이던 결근이 오늘 노랑**이 된다
- `arc = d3.arc()` 가 선언 없이 전역을 만들었다

라벨은 이제 서버가 붙여 보낸다(`WorkStatusCount`). 스크립트가 이름을 소유하지
않으니 어긋날 자리 자체가 없어졌다.

### 특정도 함정 — 인라인 style 을 걷어내면 따라오는 것

인라인 `style` 은 **무조건 이긴다**. 클래스로 바꾸는 순간 그 보호막이 사라지고,
그때까지 무시되던 규칙이 이긴다. 두 자리가 그렇게 조용히 죽었다.

- **달력 칸 높이** — `.main-body .table-bordered td`(0,2,1)의 `height: 1.625rem` 이
  `.work-cell`(0,1,0)을 이겼다
- **주말 날짜 색** — 같은 리그의 `th { color: ... }` 이 `.is-sunday` 를 이겼다

둘 다 같은 리그로 맞받아 고쳤다. 다만 높이는 레거시의 50px 로 되돌리지 않았다 —
머리글 두 줄이 26px 인데 몸통만 50px 이면 떠보이기만 한다. 36px 로 둔다.

**교훈.** 인라인 style 을 걷어낼 때는 걸려 있던 속성을 하나하나 세서, 같은 속성을
건드리는 규칙이 있는지 보아야 한다. 시험은 이걸 잡지 못한다 — 색과 높이는
눈으로만 보인다.

### 남은 것

그래프 조각 이름이 작은 조각에서 밖으로 삐져 잘린다(D-069). 색과 이름이
맞아지고 나니 오히려 더 잘 보인다. 그것은 따로 볼 자리다.

**검증.** `./gradlew build` 371건 초록(그래프가 라벨을 붙여 보낸다는 시험 하나 늘었다).
프로필 달력·근태 확인·관리자 홈 세 화면을 눈으로 확인했다 — 범례 일곱 칸이
달력 색과 맞는 것, 근태표의 «반차»·«지각» 글자가 제 색으로 나오는 것, 원
그래프의 일곱 조각 이름과 색이 범례와 같은 것, 결재 알약이 형광색을 벗은 것.

## D-126 · 그래프 조각 이름을 밖으로 — 겹칠 자리를 없앤다

D-069 는 «원 그래프의 조각 이름이 밀려 잘린다» 로 남아 있던 안건이다. D-125 에서
색과 이름을 맞추고 나니 오히려 더 잘 보였다 — 「결근 2명」이 조각을 벗어나 잘리고,
작은 조각이 이웃하면 이름끼리 겹쳤다.

### 왜 조각 안에 넣으면 안 되나

레거시는 `${라벨} ${인원}명` 을 조각의 `centroid` 에 찍었다. 글자 길이는 고정인데
**조각 크기는 그날 자료가 정한다.** 한 명짜리 상태가 셋만 있어도 셋이 같은 자리에서
겹치고, 조각보다 글자가 길면 밖으로 나가 판 밖에서 잘린다.

«적당한 자리» 를 계산해 피하는 방법도 있다(바깥으로 빼고 지시선을 긋는 식). 그러나
그건 겹침을 **줄이는** 것이지 없애는 것이 아니고, 자료가 나빠지면 다시 겹친다.

이름을 판 밖으로 뺐다. 오른쪽에 «네모 · 이름 · N명» 목록을 세우면 조각이 아무리
작아도 이름은 언제나 한 줄로 읽힌다. 겹칠 자리 자체가 없어진다.

조각 안에는 **비율만** 남긴다. `42%` 는 짧아서 웬만한 조각에 들어가고, 그마저
안 들어갈 만큼 작은 조각(7% 미만)에는 아무것도 적지 않는다 — 그 값은 옆의 목록이
이미 정확히 갖고 있다.

가운데를 비운 것(도넛)은 멋이 아니라 자리다. 그 자리에 그날 인원 합계를 적는다.
전에는 어디에도 없던 값이다.

### 같이 나온 것

**`<svg>` 안에 `<svg>` 를 또 넣고 있었다.** 심는 자리가 이미 `<svg id="graph">` 인데
`d3.select("#graph").append("svg")` 를 했다. 중첩 svg 는 그려지긴 하지만 바깥 것이
`width="100%" height="100%"` 라 크기 계산이 두 번 일어난다. 심는 자리를 `<div>` 로
바꿨다. 시험으로 못박아 뒀다.

**빈 칸에 말을 붙였다.** 오늘 근무 기록이 없으면 그릴 조각이 없어 판이 통째로
비었다 — 화면이 고장 난 것과 구별되지 않는다. «오늘 근무 기록이 없습니다» 를 적는다.
자료를 못 받았을 때(`error`)는 «근무 현황을 불러오지 못했습니다» 로 갈라 적는다.
둘은 다른 상황이고, 보는 사람이 할 일도 다르다.

### 검증

`./gradlew build` 372건 초록(심는 자리가 `<div>` 라는 시험 하나 늘었다).

그래프는 자료에 따라 모양이 달라지므로 **세 경우를 각각 눈으로 봤다.**

- **보통** — 일곱 상태가 고루 있는 날. 비율이 조각 안에, 이름이 오른쪽에
- **잔 조각이 많은 날** — 한 명짜리가 여섯. 전에 이름이 겹치던 경우다. 지금은
  7% 미만이라 조각 안이 비고 목록만 읽힌다
- **기록이 없는 날** — 빈 판 대신 말이 나온다

**남은 것.** 근태 확인 화면의 성명·부서·직책 칸이 눌려 글자가 세로로 흐른다
(「이 용 원」). 표도 가로로 넘쳐 통계 칸이 잘린다 — D-077 과 같은 자리다.

## D-127 · 한 달 합계를 만든다 — 그리고 23칸짜리 표를 읽히게 한다

D-077 은 «통계가 줄마다 따로 세어진다» 로 남아 있던 안건이다. 1단계는 그대로 옮겼다 —
합계를 더해 보이는 것은 **화면에 없던 숫자를 만드는 일**이었기 때문이다. 이제 만든다.

### 없던 숫자

프로필 달력도 근태 확인 표도 한 달을 두 줄로 그린다 — 1~16일, 17일~말일. 오른쪽 끝의
«정상·지각·조퇴·연차» 는 **그 줄만의** 합계다. 레거시가 두 줄을 그리는 사이에 카운터를
0으로 되돌린다.

두 줄에 같은 이름의 칸이 위아래로 붙어 있어 **합계처럼 보이지만 아니다.** 한 달이
며칠 정상 근무였는지 알려면 위 숫자와 아래 숫자를 눈으로 더해야 했다.

`WorkTally` 하나를 만들어 두 화면이 같이 쓴다. 두 줄을 가로질러(`rowspan="2"`) 한
번만 적고, 머리글에 «(한 달)» 을 달았다 — 숫자가 무엇을 세는지 화면이 말하게 한다.

**줄별 셈은 그대로 남겨 두었다.** 합계는 그 둘을 더해 만드는 것이라, 줄별 셈이
틀어지면 합계도 틀린다. 기존 시험도 그대로 두고 이름만 사실에 맞게 고쳤다.

### 23칸짜리 표는 왜 뭉개졌나

근태 확인 표는 칸이 23개다 — 이름셋에 날짜 16에 통계 넷. 판에 억지로 집어넣으면
브라우저가 **이름 칸부터** 줘어짜서, 「이 용 원」처럼 한 글자씩 세로로 흘러내렸다.
가로로도 넘쳐 통계 칸이 잘려 나갔다.

너비를 잡는 데 두 번 돌아갔다. 남는 기록이라 적어 둔다.

1. **`table-layout: fixed` + `min-width`** — 남은 폭을 20칸이 균등하게 나눈다. 칸마다
   안쪽 여백 `0.75rem × 2` 를 빼고 나면 글자 자리가 20px 밖에 안 남아 «09…» 로
   잘렸다. 또 다른 눈속임이다
2. **`auto` + `nowrap` + 칸마다 `width`** — **auto 배치는 `width` 를 «희망» 으로만
   읽는다.** 5rem 이라고 적은 칸이 63px 로 잡혔다. 고정한 칸의 `left` 는 내가 적은
   5rem 대로 붙으니, 실제 너비와 어긋나 칸 사이가 17px씩 벌어졌다
3. **`colgroup` + `table-layout: fixed`** — 적은 대로 준다. 재어 보니 80 · 104 · 80
   으로 정확히 맞고 틈이 없다

**교훈.** 「왼쪽에 고정한다」는 `left` 값을 손으로 더해야 하므로, 열 너비가 **선언한
값과 같다는 보장**이 있어야 한다. auto 배치에는 그 보장이 없다. 눈으로 보고 «맞는
것 같다» 하지 말고 브라우저에 실제 치수를 물어야 한다 — 두 번째 시도는 스크린샷으로는
멀쩡해 보였고, 재보고 나서야 어긋난 것을 알았다.

### 이름 세 칸을 왼쪽에 고정했다

23칸을 오른쪽으로 밀면 **지금 보는 줄이 누구인지** 잊는다. 성명·부서·직책은 왼쪽에
붙여 두고 날짜만 흐르게 했다. 고정한 칸에 경계선을 그어 굴러간 자리임을 보이게 한다.

### 줄무늬가 사람을 가르지 않았다

한 사람이 두 줄인데 줄무늬는 `tr:nth-child(even)` 이었다. 그래서 **한 사람의 윗줄은
희고 아랫줄은 회색**이었다 — 줄무늬가 가르는 것이 사람이 아니라 줄이었으니, 표를
훑을 때 경계가 거꾸로 읽혔다. 사람마다 `<tbody>` 를 두고 `tbody:nth-of-type(even)`
으로 칠한다. 마우스를 올리면 사람 전체가 밝아지는 것도 같은 이유다.

### 검증

`./gradlew build` 374건 초록. 새 시험 둘은 D-077 의 핵심을 못박는다 — 줄별 합계가
2와 1일 때 한 달 합계가 3이라는 것, 반차가 0.5로 더해져 «0.5» 로 찍힌다는 것.

화면은 **두 너비에서** 봤다. 넓은 판에서는 표가 통째로 들어와 통계까지 한눈에 보이고,
좁은 판에서는 이름 세 칸이 왼쪽에 남은 채 날짜가 그 뒤로 흐른다. 프로필 달력도
합계 한 블록으로 바뀌었고 주말 색은 그대로다.

**남은 것.** 이 화면은 jQuery 를 세 번 싣는다(레거시 그대로다 — 주석은 «두 번» 이라고
적혀 있지만 실제로는 셋이다). 아직 지우지 않은 `js/bootjs/` 도 여기서 실린다.
라이브러리 정리 때 함께 볼 자리다. *(D-130 에서 정리했다.)*

## D-128 · 비밀번호 저장을 bcrypt 로 승격한다 (O-006 해소)

레거시 해시는 약하다 — SHA-256 을 열 번 돌릴 뿐이고 salt 가 저장값 안에 그대로
들어 있다(D-014). 그런데도 1단계에서 못 바꾼 이유는 하나였다. **기존 사용자 55명의
비밀번호가 그 형식으로 저장돼 있고, 해시에서 평문을 꺼낼 수 없으니** 형식을 바꾸면
아무도 로그인하지 못한다.

**결정: 형식과 검증을 가른다.** Spring Security 의 `DelegatingPasswordEncoder` 를
쓴다 — 저장값 앞에 `{bcrypt}` 같은 접두사가 붙고, 검증은 접두사가 고른 방식으로
간다. 새로 저장하는 비밀번호(변경·신규 등록)는 전부 bcrypt 다.

### 평문을 모르는 계정은 «겹씌운다»

기존 55명을 두 갈래로 나눴다. 기동 때 도는 승격기(`PasswordStorageMigration`)가
접두사 없는 행만 골라 처리하므로 몇 번을 떠도 무해하다.

- **비밀번호가 사번과 같은 39명** — 평문(사번)을 아는 것이므로 바로
  `{bcrypt}` 로 간다. 최초 로그인 판정(비밀번호=사번)도 그대로 성립한다
- **그 밖의 16명** — 평문을 모른다. 저장된 레거시 해시 자체를 bcrypt 에 넣는다
  (`{erflow-bcrypt}` = salt 40글자 + bcrypt(레거시 최종 해시)). DB 가 유출되어도
  공격자는 bcrypt 부터 뚫어야 한다. 로그인 검증은 입력 평문을 salt 로 레거시
  방식대로 늘인 뒤 그 결과를 bcrypt 로 대조한다

**bcrypt 에 넣는 것은 저장값 전체가 아니라 안쪽 해시(hex 64글자)다.** bcrypt 는
입력을 72바이트까지만 받는데 레거시 저장값은 140글자다 — 통째로 넣으면 요즘
Spring Security 는 예외를 던진다.

### 겹씌움은 과도기다 — 로그인 성공 때 순수 bcrypt 로

로그인이 성공하는 순간은 평문을 아는 순간이다. `ErflowUserDetailsService` 가
`UserDetailsPasswordService` 를 겸해, 저장 형식이 기본(bcrypt)이 아닌 사용자가
로그인에 성공하면 Spring Security 가 그 자리에서 bcrypt 로 다시 저장한다 —
O-006 에 적어 두었던 «로그인 시 재해시로 점진 교체» 가 이것이다.

### 연기 시험이 잡아준 것 하나

`ErflowApplicationTests` 는 local 프로파일 없이(=DB 없이) 컨텍스트만 띄우는
시험인데, 승격기가 기동 때 DB 를 읽으면서 처음으로 깨졌다 — 지금까지 기동 시점에
DB 를 건드리는 것이 없었던 것이다. 승격기는 DB 에 닿지 못하면 경고만 남기고
물러난다. 위험하지 않다 — 접두사 없는 값도 여전히 레거시 방식으로 검증되므로
승격이 미뤄져도 로그인은 되고, 다음 기동이 다시 시도한다. 같은 이유로 트랜잭션도
안 묶는다 — 행마다 독립이고, 중간에 끊겨도 이미 승격된 행은 남는 편이 낫다.

### 그대로인 것

- `ErflowPasswordEncoder` (레거시 재현)는 남는다 — 겹씌움의 안쪽 계산과, 승격 전
  값의 안전망 검증이 그것을 쓴다. `LegacyPasswordCompatibilityTest` 도 그대로다 —
  스키마 수식으로 `erflow`(정답)를 읽으므로 `erflow_v2` 를 승격해도 유효하다
- **O-007(비밀번호=사번 39명)은 그대로 남는다.** 그 39명의 비밀번호가 사번이라는
  사실은 데이터 문제이고, 이 결정은 그 값을 «어떻게 저장하는가» 만 바꿨다

**검증.** `./gradlew build` 386건 초록(겹씌움 단위 5 + 승격 확인 4 + 이름 정합 3 이
늘었다). 그리고 실제로 띄워 놓고 다섯 가지를 눈으로 확인했다 — ① 초기 계정이
로그인되어 비밀번호 변경 화면으로 간다 ② 틀린 비밀번호는 거부된다 ③ 겹씌움 계정이
로그인된다(원본 해시를 보관한 뒤 admin 에 아는 평문으로 만든 합성 겹씌움 값을 심어
확인했고, 끝나고 원본으로 되돌렸다) ④ 그 로그인 직후 저장값이 `{bcrypt}` 로 바뀐다
⑤ 바뀐 값으로 다시 로그인된다. DB 는 55명 전원 승격 — `{bcrypt}` 39 ·
`{erflow-bcrypt}` 16, 접두사 없는 행 0.

## D-129 · 프로그램 이름을 메뉴 라벨에 맞춘다 (O-002·O-003·O-004 해소)

전작이 «이관 후 결정» 으로 미뤄 둔 이름 셋을 정리했다.

### 오타 (O-003)

권한 프로그램에 **«결재관리 관리»** 가 있었다. 메뉴는 «결재라인 관리» 다. 레거시는
이름의 해시가 곧 식별자라 고치면 권한이 통째로 깨졌지만(D-003), 이관하며
`program_id` 를 불투명한 식별자로 만들어 뒀다 — **이름을 고쳐도 아무것도 안 깨지는
지금이 고칠 자리다.**

### 용어 통일 (O-004)

메뉴 라벨과 프로그램 이름이 17개 중 10개가 달랐다(D-004). 관리자가 권한 화면에서
보는 이름과 사용자가 메뉴에서 보는 이름이 다르면, 권한을 고칠 때 어느 화면 것인지
헷갈린다. **방향은 메뉴 라벨이다** — 사용자 쉰다섯이 매일 보는 이름과 관리자 하나가
가끔 보는 이름 중에 전자가 기준이다.

여덟을 고쳤다: 문서 작성→기안 작성 · 문서 관리→문서 리스트 · 결재관리 관리→결재라인
관리 · 입고 관리→입고 제품 관리 · 출고 관리→출고 제품 관리 · 출고제품 관리→완제품
재고 관리 · 근태 관리→근태 확인 · 게시판 목록 조회→게시판.

**«구매/영업 협력업체 관리» 둘은 그대로 둔다.** 메뉴 라벨이 둘 다 «협력업체 관리» 라
그대로 맞추면 권한 화면에 같은 이름이 두 줄 생긴다 — 수식어가 구별의 전부다. 그래서
정합 규칙은 «같거나, 수식어 뒤에 라벨이 온다» 다.

**이름은 두 테이블에 있다.** `program.name`(권한 판정용)과
`permission_program_tbl.program_name`(관리자 화면용) — 같은 값을 두 곳이 갖고 있어
둘 다 고쳤고, 시험이 «두 테이블이 항상 같다» 를 못 박는다.

### 데드 레코드는 없었다 (O-002)

O-002 는 «영업 협력업체 관리 데드 레코드를 지울지» 였는데, 그 전제가 이미
철회됐다(D-008 철회 — seed 생성기의 잘못이었고 레거시는 제대로 구분하고 있었다).
남은 후보였던 «부서 일정 등록» 도 데드가 아니다 — 화면(`screen` 표)에는 없지만
`CalendarService` 가 프로그램 코드로 직접 쓴다(부서 일정 만들기 권한). **지울 것이
없다. 유지가 결론이다.**

**검증.** `ProgramNameAlignmentTest` 셋 — 메뉴에 걸린 프로그램 이름이 라벨을
따르는지, 두 테이블이 같은지, 오타가 사라졌는지. 빌드 386건 초록.

## D-130 · jQuery 를 3.7.1 로 올린다

D-119 에서 1.12.4 로 모아 두고 «3.x 는 별도 판단» 으로 남겼던 것이다. 1.x 는 2016년
이후 멈춘 줄기라 보안 수정도 안 나온다.

**자체 JS 51개를 먼저 쟀다.** 3.x 에서 제거된 API — `.size()` · `.andSelf()` ·
`.load()/.unload()/.error()` 이벤트 단축형 · `.bind()/.delegate()` · `$.browser` ·
jqXHR 의 `.success()/.error()/.complete()` — 를 전부 훑었는데 **사용이 0** 이었다.
템플릿 인라인 스크립트에도 없다. 3.5 에서 바뀐 자기닫힘 태그 파싱에 걸릴 문자열도
없다(`$('<tr></tr>')` 하나뿐이고 그 모양은 안전하다). 올리는 데 코드를 고칠 것이
없다는 뜻이다.

**jQuery UI 도 1.13.3 으로 같이 올렸다.** 1.12.1 은 jQuery 3 과의 짝이 보장되지
않는 판이다. 쓰는 위젯은 달력(datepicker)과 줄 끌기(sortable) 둘뿐이고(D-119) 그
API 는 그대로다.

**중복 로딩도 정리했다.** 근태 확인은 jQuery 를 **세 번**, 일곱 화면(입출고
등록·수정, 발주·수주 등록·수정, 부서 수정, 다중 제품 찾기)은 **두 번** 싣고 있었다 —
레거시 그대로다. 같은 파일을 거듭 싣는 것은 전송 낭비 말고 아무 뜻이 없어 한 번으로
줄였다.

옛 파일 둘(1.12.4 · UI 1.12.1)은 지웠다. 참조 86곳이 전부 새 파일을 가리키는 것을
확인한 뒤다.

**검증.** 빌드 386건 초록 — 다만 시험은 JS 를 실행하지 않으므로(D-119 의 교훈)
실제로 띄워 찍었다. 메인(달력)·근태 확인·관리자 홈·사원 리스트·결재라인
등록(sortable)·설비 등록(datepicker)·게시판·문서 리스트·협력업체 리스트가 모두
그려지고, 날짜 고르기는 옛 버전과 **같은 화면 HTML 로 A/B 대조**까지 했다 — 픽셀이
같다.

**남은 것 하나(전부터 있던 것).** 설비 등록 화면의 날짜 달력이 화면을 열 때부터
펼쳐져 있다. 옛 jQuery 로도 똑같이 펼쳐지므로 이번 일이 아니라 원래 그랬던 것이다 —
화면 다듬기 때 볼 자리.

## D-131 · 바깥 상자 이름을 content-wrap 하나로 (D-119 잔여)

껍데기를 합친 뒤에도(D-119) 바깥 상자 이름이 둘이었다 — 사용자 화면은
`content-wrap`(37장), 관리자 화면은 `admin-wrap`(9장). 보이는 것은 같은데 이름이
달라서, 상자에 규칙을 줄 때마다 두 이름에 나눠 적어야 했다.

**관리자 9장을 `content-wrap` 으로 바꿨다.** 다수결이기도 하고, 껍데기가 하나가 된
마당에 «admin» 이라는 수식이 남을 이유가 없다. CSS 의 `.admin-wrap` 규칙은
지웠다 — `.content-wrap` 과 글자까지 같았다.

**함정 하나를 기록한다.** 본문 여백 규칙이 `.content-wrap > *:not(.app):not(...)`
모양인데, **`:not()` 은 안의 선택자만큼 특이도를 더한다** — 이 사슬은 (0,4,0)이라
어지간한 클래스 규칙을 다 이긴다. 관리자 화면이 이 이름을 쓰게 되면서 관리자
사이드바(`aside-bar`)와 본문 상자(`admin-main-content`)가 이 규칙에 새로 걸렸고,
빼먹으면 사이드바가 본문처럼 늘어난다. 제외 목록에 둘을 넣었다 — 제외하는 것은
«본문이 아닌 껍데기 조각» 이므로 D-119 의 «이름을 몰라도 걸린다» 원칙은 그대로다.

**검증.** 빌드 386건 초록. 관리자 홈·사원 리스트·문서 양식 리스트를 띄워 찍어
사이드바 폭과 본문 여백이 그대로인 것을 확인했다.
