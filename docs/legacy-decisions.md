## D-001 · 스택 핀

|---|---|---|

## D-013 · Spring Security 와 CSRF

인증 기반으로 Spring Security 를 쓴다. 필터 체인·세션 고정 공격 방어·CSRF·로그아웃을
프레임워크가 맡고, **레거시 규칙이 담긴 부분은 직접 구현한다** — 비밀번호 해시(D-014),
권한 비트마스크(D-015), 화면별 권한(`ScreenAuthorizationManager`).

**CSRF 는 레거시에 없던 것을 더하는 유일한 항목이다.** form 마다 `_csrf` hidden 입력이
렌더링 시점에 붙는다. 정합성 게이트가 이것을 "레거시에 없던 요소"로 잡으며, 그게 맞다.
사유를 적어 `migration/allowlist.json` 에 등록해 통과시킨다.

실제 게이트 결과 — CSRF 말고는 추가된 것이 없다는 증명이다.

```
allowlist 없이 :  FAIL  ['control:hidden|_csrf|hidden']
allowlist 적용 :  PASS  차이 0 / 예외승인 ['control:hidden|_csrf|hidden']
```

**주의:** 템플릿 원본끼리 대조하면 CSRF 가 보이지 않는다. Thymeleaf 가 렌더링 시점에
넣기 때문이다. 런타임에 끼어드는 요소는 **렌더링 결과**로 대조해야 잡힌다. 반복 영역이
없는 화면(등록·수정)은 렌더링 결과 대조가 가능하고, 목록처럼 반복이 있는 화면은
템플릿 대조만 유효하다.

## D-014 · 비밀번호 해시 1:1 재현

레거시 `PasswordHashServiceImpl` 의 방식.

```
salt      20바이트 난수를 hex 로 편 40글자
stretch   SHA-256 을 10번 되풀이. 입력은 (비밀번호 + salt)
저장       base64(salt + 최종해시hex)  ->  디코드하면 40 + 64 = 104 글자
```

**바꿀 수 없다.** 기존 사용자 55명의 비밀번호가 이 형식으로 저장돼 있어, BCrypt 같은
것으로 교체하면 아무도 로그인하지 못한다.

알고리즘 재현은 운영 데이터로 확인했다. 55명 중 **42명이 비밀번호가 사번과 같은
상태**(최초 로그인 전)라 평문을 알 수 있고, 그 42명의 해시를 정확히 재생성한다.

이 방식은 요즘 기준으로 약하다 — 반복 10회는 너무 적고, salt 가 결과 안에 그대로 들어
있다. 다만 그것은 이관이 아니라 개선이다. **로그인 성공 시 새 방식으로 다시 해시해
점진 교체**하는 것이 맞고, 별도 안건으로 둔다([O-006](#미결-사람-판단-필요)).

시험은 두 겹이다. 운영 해시를 소스에 옮겨 적지 않는다 — 공개 저장소이고 약한 해시라
더욱 그렇다.

- `ErflowPasswordEncoderTest` — 합성 입력에 대한 기대값 고정
- `LegacyPasswordCompatibilityTest` — DB 를 직접 읽어 실제 사용자와 대조

## D-015 · 권한 판정은 Java 에서

레거시 판정식.

```java
관리자   (deptPermission & Long.MIN_VALUE) == Long.MIN_VALUE
      && (jobPermission  & Long.MIN_VALUE) == Long.MIN_VALUE
접근     (programDept & userDept) != 0 && (programJob & userJob) != 0
```

**이 계산을 SQL 로 옮기면 안 된다.** MariaDB 의 비트 연산 결과는 부호가 없다.

```
MySQL : -9223372036854775808 & -9223372036854775808 = 9223372036854775808
Java  : -9223372036854775808 & -9223372036854775808 = -9223372036854775808
```

실제로 SQL 로 관리자를 세면 **0명**이 나온다(맞는 값은 1명, `admin`). 매퍼는 값만 읽어
오고 계산은 `Permissions` 클래스에서 한다. 회귀 방지는 `PermissionsTest` 가 맡는다.

## D-011 · DB 분리와 권한

**레거시가 살아 있다.** 개발 서버의 `erflow` 스키마가 레거시 원본 그대로다
(47/47 테이블 일치, `permission_program_tbl` 20행 일치). 덤프 파일뿐 아니라 **동작하는 DB**
가 정답으로 존재한다는 뜻이고, 이관 결과를 실제 데이터로 대조할 수 있다.

| | |
|---|---|
| 서버 | MariaDB 10.6.27 |
| 레거시 | `erflow` — **건드리지 않는다** |
| 신규 | `erflow_mig` — utf8mb4 / utf8mb4_general_ci |

`erflow_mig` 라는 이름을 고른 이유: `erflow` 와 한눈에 구분되고, 같은 서버의
`dev_arcodex` / `sso_auth_shadow` 접미사 관례와 어긋나지 않는다.

**앱은 root 로 붙지 않는다.** 전용 계정 `erflow_mig` 를 만들고 권한을 이렇게 줬다.

```sql
GRANT ALL PRIVILEGES ON `erflow_mig`.* TO 'erflow_mig'@'%';
GRANT SELECT          ON `erflow`.*     TO 'erflow_mig'@'%';
```

이것으로 **"정답은 읽기 전용"이 관례가 아니라 권한이 된다.** 하네스가 실수로든
버그로든 레거시를 건드릴 수 없다. 실제로 확인했다 — `CREATE TABLE erflow.__probe` 는
에러 1142 로 거부된다.

접속 정보는 파일에 남기지 않는다. `app/src/main/resources/application-local.yml` 에
두고 `.gitignore` 로 제외한다.

## D-012 · 스키마 복제

**한 번에 전부 옮긴다.** 슬라이스마다 필요한 테이블만 가져가면 도메인이 바뀔 때마다
같은 작업을 반복하게 되고, FK 가 없어 의존 관계가 코드에만 있으므로 어디까지 필요한지
매번 다시 조사해야 한다. 스키마 이관은 기계적이므로 한 번에 끝내고, **화면 이관만
슬라이스 단위로 계속한다.**

**덤프 파일이 아니라 라이브 레거시에서 복제한다.** 덤프는 MySQL 8 에서 떠서
`utf8mb4_0900_ai_ci` 처럼 MariaDB 에 없는 collation 이 박혀 있다. 반면 라이브 DB 는
이미 MariaDB 에서 돌고 있어 `SHOW CREATE TABLE` 결과를 그대로 재생할 수 있고,
무엇보다 **정합성 판정의 정답이 라이브 DB** 이므로 정답과 같은 것을 복제하는 편이 옳다.

결과:

| | |
|---|---|
| 테이블 | 32개 / 2,077행 — 전량 행수 일치 확인 |
| 뷰 | 15개 |
| FK 제약 | 0개 (레거시에 애초에 없다) |

**이름을 바꾸지 않는다.** `*_tbl` 접미사도, 컬럼명도 그대로 둔다. 1:1 이관이 먼저이고,
이름을 손대면 레거시 SQL 과 대조할 수 없게 된다. 정리는 이관 완료 후 별도 안건이다.

뷰는 두 군데를 고쳤다. 이관에 필요한 최소 변경이다.

- `DEFINER=root@%` 제거 — 특정 계정에 묶이면 그 계정이 사라질 때 뷰가 깨진다
- `SQL SECURITY DEFINER` → `INVOKER` — 조회하는 계정의 권한으로 동작시킨다

뷰가 뷰를 참조하므로(`work_view` → `user_view` 등) 생성 순서 문제가 있다.
위상 정렬 대신 **만들어질 때까지 반복하고 한 바퀴에 하나도 못 만들면 중단**하는
방식을 썼다. 의존 그래프를 따로 관리하지 않아도 되고, 순환이면 즉시 드러난다.

구현: `migration/tools/clone_legacy_schema.py`.
이 스크립트는 레거시를 향한 문장이 `SHOW`/`SELECT` 인지 실행 전에 검사한다. 서버 권한이
이미 막아주지만, 관리 계정으로도 돌 수 있고 **정답 오염은 한 번이면 복구가 불가능하다.**

회귀 방지는 `LegacyCloneTest` 5건이 맡는다 — 객체 수, 전 테이블 행수, 뷰 결과수,
한글 정렬 결과, 레거시 쓰기 차단.

## D-006 · collation — 실측 결과

원본 덤프 파일에는 `utf8mb4_0900_ai_ci`(MySQL 8 전용)로 적혀 있어 MariaDB 이관 시
한글 정렬이 달라질 위험을 [O-005](#미결-사람-판단-필요)로 잡아뒀다. **측정해 보니
위험이 없다.**

| | collation |
|---|---|
| `erflow` (레거시 라이브) | `utf8mb4_general_ci` |
| `erflow_mig` (신규) | `utf8mb4_general_ci` |

레거시 라이브 DB 자체가 이미 `general_ci` 로 돌고 있다. 정답이 general_ci 이므로
같은 값을 쓰면 순서가 어긋날 수 없다.

교차 확인으로 `erflow.unit_tbl.name` 49행을 4개 collation 으로 정렬해 비교했고
(`general_ci` / `unicode_ci` / `unicode_520_ci` / `bin`) **전부 같은 순서**였다.
한글·영문·숫자·기호 혼재 표본도 `general_ci` 와 `unicode_ci` 가 동일했다.

```
' 공백', '!느낌표', '123', 'Apple', 'zebra', 'ㄱㄴㄷ', '가나다', '나무', '홍길동'
```

**단서:** 이 검증의 정답은 개발 서버의 라이브 DB다. 원 운영 환경이 MySQL 8 `0900_ai_ci`
였다면 그쪽과는 다를 수 있으나, MariaDB 에는 해당 collation 자체가 없고 대조할 대상도
없다. 회귀 방지는 `MenuSeedTest.collationMatchesLegacy` 가 맡는다.

## D-003 · program_id 보존

레거시는 `program_id = SHA256(한글 프로그램명)` 이다
(`driver/ProgramIDGenerateDriver.java`).

이 설계의 대가가 실제로 드러나 있다. 권한 테이블에 **"결재관리 관리"** 라는 항목이
있는데 메뉴는 **"결재라인 관리"** 다. 오타로 보이지만 **고치면 program_id 가 바뀌어
권한 매핑이 통째로 깨진다.** 이름이 식별자를 결정하기 때문이다.

**결정:** 기존 SHA256 값은 데이터 그대로 옮긴다. 다만 신규 코드에 해시 재생성 로직을
이식하지 않는다. `program_id` 는 그냥 불투명한 식별자가 되고, 이름을 고쳐도 권한이
깨지지 않는다. 값은 호환, 동작은 개선.

## D-004 · 라벨 불일치 유지

메뉴 라벨과 권한 프로그램명이 다르다.

| 메뉴 | 권한 프로그램 |
|---|---|
| 기안 작성 | 문서 작성 |
| 문서 리스트 | 문서 관리 |
| 입고 제품 관리 | 입고 관리 |
| 게시판 | 게시판 목록 조회 |
| 근태 확인 | 근태 관리 |
| 완제품 재고 관리 | 출고제품 관리 |

17개 중 이름이 일치하는 것은 7개뿐이다.

**결정:** 통일하지 않는다. 사용자에게 보이는 문구를 바꾸는 것은 이관이 아니라 개선이고,
1:1 정합 기준을 흔든다. 두 이름을 각각 `menu.label` 과 `program.name` 에 보존한다.
용어 통일은 이관 완료 후 별도 안건.

## D-005 · 라우트 변환 규칙

레거시는 URL 이 곧 JSP 파일 경로라 **대응 정답이 없다.** 화면마다 임의로 정하면
판단이 누적되어 나중에 근거를 못 댄다. 그래서 규칙을 고정한다.

```
/ERFlow/{domain}/{screen}.jsp  ->  /{domain}/{screen-kebab}
```

- 화면명이 도메인명으로 시작하면 중복이므로 제거 — 단 **camelCase 경계일 때만**.
  `unit/unitList` → `/unit/list`. 하지만 `product/productedProduct` 는 "product" +
  "edProduct" 가 아니므로 건드리지 않는다 → `/product/producted-product`
- `index` 는 제거 — `message/index.jsp` → `/message`
- 남는 게 없으면 도메인 루트 — `work/work.jsp` → `/work`
- 쿼리스트링 보존 — `?flag=1` 과 `?flag=0` 은 **서로 다른 메뉴**다(구매/영업)
- 값이 동적인 파라미터는 제거 — `profile.jsp?id=<%=headerUserId%>` → `/profile`
  (현재 사용자는 서버가 세션에서 채운다)
- 폴더가 두 겹이면 폴더를 **순서대로** 떼어낸다 — 관리자 화면이 그렇다.
  `admin/board/adminBoardList` 는 "admin" 과 "board" 를 차례로 떼어
  `/admin/board/list`. 규칙은 한 겹일 때와 같고 적용 횟수만 다르다.
  이 항목을 넣기 전에는 `to_route` 가 첫 폴더만 봐서 `/admin/board/admin-board-list`
  가 나왔다. 고친 뒤 seed 를 다시 뽑아 바이트가 같은 것을 확인했다 — 지금까지의
  메뉴에는 두 겹짜리가 없었다

구현: `migration/tools/build_menu_seed.py` 의 `to_route()`.
게이트는 이 규칙을 모른다. seed 가 `legacy_url` 로 출처를 기록하고 게이트는 그 출처만
검증하므로, 규칙이 바뀌어도 게이트를 고칠 필요가 없다.

## D-016 · 파라미터로 갈리는 화면 권한

레거시는 화면 안에서 요청 파라미터를 보고 `PROGRAM_CODE` 를 골랐다.

```java
// company/companyList.jsp
switch (paramFlag) {
    case "0": programId = OUT_PROGRAM_CODE; break;   // 영업 협력업체 관리
    case "1": programId = IN_PROGRAM_CODE;  break;   // 구매 협력업체 관리
}
```

**10개 화면이 이렇다** — `company` 3, `bound` 5, `task` 2. 판별 파라미터는 모두 `flag`
이지만 값 어휘가 다르다(`0`/`1`, `inbound`/`outbound`, `sell`/`purchase`).

`screen` 테이블에 `param_name` / `param_value` 를 두어 한 경로에 규칙이 여럿 붙을 수
있게 했다. 어느 규칙이 걸리는지는 **Java 에서 고른다** — 비트마스크와 같은 이유로
판정을 SQL 에 맡기지 않는다([D-015](#d-015--권한-판정은-java-에서)).

분기 조건은 자바 코드 안에 있어 기계로 뽑을 수 없다. 확인해서 생성기의
`CONDITIONAL_PROGRAMS` 에 고정했고, **규칙이 없는 다중 코드 화면을 만나면 생성기가
멈춘다.** 아무거나 고르면 절반이 엉뚱한 권한을 갖고 그 사실이 드러나지 않는다.

## D-021 · 원칙의 유일한 예외 — 자격증명과 개인정보

공개 전환 전 점검에서 나왔다.

| 위치 | 내용 |
|---|---|
| `util/MailSender.java` | Gmail 앱 비밀번호가 평문 |
| `ERFlow-DB.sql` | 사용자 55명의 이름·주민등록번호·주소·휴대전화·이메일 |
| `mail/SendMailServlet.java`, 덤프 헤더 | 살아있는 인프라 호스트명 |

**"레거시는 정답이니 수정하지 않는다"가 이 프로젝트의 원칙이다. 여기가 유일한
예외다.** 그 원칙은 이관 정합성을 위한 것이지, 살아있는 자격증명과 개인정보를
공개하는 근거가 될 수는 없다.

조치가 둘로 갈린다.

- **가린다** — 자격증명·호스트명은 문자열 치환으로 해결된다.
  `migration/tools/redact_legacy.py` 가 재현 가능하게 처리한다.
- **뺀다** — `ERFlow-DB.sql` 은 치환으로 안 된다. 저장소에서 제외하고
  (`.gitignore`), 이관에 필요한 권한 프로그램 20건만 `extract_programs.py` 가
  뽑아 `migration/seed/programs.json` 으로 커밋한다. 스키마와 데이터는 라이브 DB
  에서 복제한다.

**과거 커밋에서도 지웠다.** 파일만 고치면 이력에 남고, 공개하면 이력도 함께
공개된다. 커밋 10개를 다시 써서 흔적을 없앴다.

**게이트에 영향이 없다.** 가린 곳은 메일 발송 코드와 DB 덤프뿐이고, 게이트가 보는
것은 화면 마크업이다. 적용 후 `run_gates.py` PASS 로 확인했다.

### 메일 도메인을 이관할 때

레거시는 SMTP 계정과 앱 비밀번호를 소스에 박아 뒀다. **이관하면서 그대로 옮기지
않는다.** 접속 정보는 `application-local.yml` 과 환경변수로 받는다 — DB 접속에
이미 쓰고 있는 방식과 같다.

이것은 [D-014](#d-014--비밀번호-해시-11-재현)(비밀번호 해시)와 다르다. 해시는 기존
데이터와 호환돼야 해서 바꿀 수 없지만, SMTP 자격증명은 **어디에 두느냐**의 문제일
뿐이라 옮겨도 동작이 달라지지 않는다.

## D-020 · 실화면 대조

게이트가 6화면 전부 PASS 였는데, 레거시를 띄워 나란히 놓자마자 어긋난 곳이 나왔다.

```
레거시   2023년 06월 20일      (WebHelper.getDate 는 "yyyy년 MM월 dd일")

PASS  협력업체 관리 (구매): 15행 일치
PASS  협력업체 관리 (영업): 15행 일치
```

**CI 에서는 돌지 않는다.** 두 앱과 DB 가 모두 있어야 하고 접속 정보는 커밋하지 않는다.
도메인을 옮길 때마다 로컬에서 한 번씩 돌리는 것으로 한다.

곁들여 드러난 것 — 레거시 소스를 복사하며 접속 정보를 주입하는 Gradle 태스크가 주입
값을 입력으로 선언하지 않아, 대상을 바꿨는데도 **예전 스키마를 보는 WAR** 가 나왔다.
그런 WAR 로 비교하면 무엇을 비교했는지 알 수 없다. 입력으로 선언해 고쳤다.

## D-017 · 업종 검색이 아무것도 못 찾을 때

레거시 `CompanyServiceImpl.getCompanies`.

```java
vlist = repository.getFieldCodes(keyword);        // 걸리는 업종이 없으면 빈 목록
for (int i = 0; i < vlist.size(); i++) sb.append(",?");
String query = sb.toString().substring(1);        // "".substring(1) -> 예외
```

여기 남긴다. 회귀 방지는 `CompanyScreenTest.searchByFieldWithNoMatch` 가 맡는다.

## D-018 · 처리에도 화면 권한이 걸린다

[D-009](#) 로 `*Proc.jsp` 를 화면과 같은 URL 의 `POST` 로 합쳤다. 그런데 레거시는

요청은 이미 화면을 통과했으므로 달라지는 것이 없고, 막히는 것은 URL 을 직접 두드린
경우뿐이다.

## D-008 · 철회 — 협력업체 관리는 결함이 아니었다

**앞서 이렇게 기록했다가 철회한다.**

발견했다 — 정답 추출이 원본의 **일부만** 보고 있으면 게이트는 조용히 통과한다.

## D-022 · 추출기가 보지 않던 요소 — `title` 툴팁과 `alt` 이미지

게시판(post) 도메인을 시작하며 원본을 훑다가 발견했다.

레거시 89개 화면 중 **22개에 `<i class="fa-solid ..." title="검색하기">` 가 있다.**
돋보기 아이콘이고, 마우스를 올리면 "검색하기"가 뜬다. 추출기는 이것을 한 번도
signature 로 만든 적이 없다. `_signature_for` 가 `a·button·input·select·textarea·th`
와 위젯만 처리했기 때문이다.

**이미 이관한 `unit/list.html` 과 `company/list.html` 에도 해당된다.** 확인해보니
두 템플릿 모두 `title="검색하기"` 를 갖고 있었지만, 그것은 마크업을 그대로 옮겼기
때문이지 게이트가 요구해서가 아니다. 지웠어도 PASS 였다.

`<img alt="첨부파일">` 도 같다. 게시글에 첨부가 있는지를 알려주는 유일한 표시인데
추출 대상이 아니었다.

**결정:** 둘 다 추출한다.

| 대상 | signature | 근거 |
|---|---|---|
| signature 를 못 내는 요소의 `title` | `text:tooltip\|검색하기\|` | 툴팁으로 화면에 뜬다 |
| `alt` 가 있는 `<img>` | `media:image\|첨부파일\|<src>` | 정보를 전달하는 이미지다 |

`alt=""` 인 이미지는 세지 않는다. 접근성 관례상 장식이라는 뜻이고, 그 관례가 맞다 —
로고·여백 이미지까지 세면 대조가 소음에 덮인다. `alt` 가 아예 없는 이미지도 세지
않는다. 라벨을 만들 수 없고 `src` 로만 견주면 이관하며 경로가 바뀔 때마다 걸린다.

이미지의 `detail` 은 `src` 다. 경로가 바뀌면 "라벨은 같고 대상만 다름"으로 분류돼
라벨을 건드리지 않게 된다 — 메뉴 링크와 같은 처리다.

상호작용 요소의 `title` 은 툴팁으로 세지 않는다. 그쪽은 이미 라벨 후보로 쓰고
있어서, 또 세면 같은 글자를 두 번 센다.

`EXTRACTOR_VERSION` 을 2 -> 3 으로 올렸다. 정답 6건을 다시 뽑았고, 목록 화면 둘이
signature 1건씩 늘었다(검색하기 툴팁).

**이것이 세 번째다.** D-008 은 정답 생성기가 원본의 일부만 읽어서, 날짜 형식(D-020)은
값이 동적이라서, 이번은 추출기의 대상 목록에 구멍이 있어서. 셋 다 **게이트가
아니라 사람이 원본을 읽다가** 찾았다. 게이트는 "정답 대비 다른가"만 본다.

## D-023 · 스크립틀릿이 찍는 글자는 고치지 않는다

`postList.jsp` 는 계층 답글을 이렇게 표시한다.

```jsp
<% for (int j = 0; j < pos; ++j) { out.println("&nbsp;&nbsp"); }
   if (pos > 0) { out.println("답글 : "); } %>
```

"답글 : " 는 화면에 뜨는 글자인데 전처리가 `<% %>` 를 통째로 지우므로 추출기가
보지 못한다. D-022 와 같은 종류의 구멍이다.

**결정: 고치지 않는다.** 이유는 두 가지다.

첫째, **고쳐도 이 자리에서는 안 보인다.** "답글 : " 는 `<a>` 안에 있고 그 `<a>` 의
텍스트는 바로 뒤 `<%=subject%>` 때문에 이미 `«dyn»` 이다. 문자열 리터럴을 꺼내
붙여도 라벨은 여전히 `«dyn»` 다.

둘째, **끝이 없다.** 리터럴만 처리하면 `out.println(prefix + name)` 은 못 본다.
JSTL, 커스텀 태그, JS DOM 조작도 같은 문제다. 자바를 해석하는 추출기를 만들면
그것이 또 다른 정답이 되고, 그 정답이 맞는지는 누가 보는가.

**대신 e2e 실화면 대조(D-020)가 답이다.** 날짜 형식 결함도 게이트가 아니라 그쪽이
잡았다. 렌더링된 화면에는 "답글 : " 가 글자로 찍혀 있다.

한계를 아는 채로 두는 것과 모르고 두는 것은 다르다. `tests/test_jsp_extraction.py`
의 `TestKnownBlindSpot` 이 이 구멍을 못으로 박아 둔다 — 나중에 "고쳐졌겠지" 하고
방심하지 않도록.

## D-024 · 목록과 개수가 다른 조건으로 분기한다

`PostServiceImpl` 의 두 메서드가 같은 검색을 서로 다르게 판단한다.

```java
getPostViews : if (keyfield != null && !keyfield.trim().equals(""))  // keyfield 기준
getTotalCount: if (keyword  != null && !keyword.trim().equals(""))   // keyword  기준
```

검색 항목만 고르고 검색어를 비운 채 조회하면 이렇게 갈린다.

| | 조건 | 결과 |
|---|---|---|
| 목록 | `subject like '%%' and board_id = ?` | `subject` 가 `NULL` 인 글이 빠진다 |
| 개수 | `board_id = ?` | 전부 센다 |

`like` 는 `NULL` 에 대해 `NULL` 을 돌려주므로 목록에서만 빠진다. 페이지 수는 있는데
그 페이지가 비는 상황이 된다.

**실데이터에는 `subject` 가 `NULL` 인 글이 없다.** 확인했다(0행). 그래서 지금은
드러나지 않는다.

**결정:** 그대로 옮긴다. `PostSearch.activeForList()` 와 `activeForCount()` 를 따로
두고 각각 레거시 조건을 담는다. 하나로 합치면 검색 결과 건수가 레거시와 달라질 수
있고, 그러면 "레거시와 같은가"를 판정할 수 없다.

`PostSearchTest.listAndCountDisagree` 가 이 불일치를 못으로 박아 둔다. 나중에
"버그 같으니 고치자"는 사람이 나오면 시험이 먼저 말을 건다.

## D-025 · 게시판 목록의 페이징이 동작하지 않는다

`boardList.jsp` 는 `start` 를 계산해 두고 쓰지 않는다.

```jsp
int start = (nowPage - 1) * numPerPage;      // 계산은 한다
Vector<BoardBean> boardList = activityCon.getBoards(keyword);   // LIMIT 없음
for (int i = 0; i < numPerPage; ++i) {
    BoardBean board = boardList.get(i);       // 언제나 0번부터
```

`getBoards` 의 SQL 은 `select * from board_tbl [where subject like ?]` 로 `ORDER BY`
도 `LIMIT` 도 없다. 2페이지를 눌러도 1페이지와 같은 목록이 나온다.

**게시판이 4개뿐이라 페이지 번호가 하나만 그려져 드러나지 않는다.**

**결정:** 그대로 옮긴다. `BoardService.list` 가 `pagination.start()` 를 쓰지 않고
0번부터 자른다 — 의도적이며 주석으로 남겼다. 고치면 게시판이 15개를 넘는 순간
레거시와 다른 화면이 된다.

정렬도 넣지 않는다. `ORDER BY` 를 더하면 지금 당장 화면에 뜨는 순서가 달라진다.


> **2단계에서 해소했다(D-108).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-026 · 같은 앱 안에서 날짜 형식이 화면마다 다르다

`WebHelper.getDate` 가 `yyyy년 MM월 dd일` 로 바꿔 주지만 **게시판은 이 헬퍼를 쓰지
않는다.** `ResultSetExtractHelper.extractViewPostBean` 이 `rs.getString("created_at")`
으로 읽어 그대로 찍는다. 화면에는 `2023-11-10 17:29:23` 이 뜬다.

설비·협력업체 화면은 `yyyy년 MM월 dd일` 이다(D-020). 같은 앱인데 다르다.

**결정:** 화면마다 레거시 그대로 간다. 통일하지 않는다.

**게이트는 이 자리를 못 본다.** 날짜는 서버가 채우므로 signature 가 `«dyn»` 이고,
형식이 무엇이든 통과한다. 처음에 `yyyy년 MM월 dd일` 로 썼다가 원본을 읽고 고쳤다 —
게이트는 끝까지 아무 말도 하지 않았다. D-020 과 같은 사각지대이며, 잡는 방법도
같다(실화면 대조).

그대로 옮기는 것은 이관이 아니다.** 첨부를 정상적으로 받는 흐름은 달라지지 않는다.

## D-029 · 조회수 집계 조건이 뒤집혀 있다

`postView.jsp` 는 `postId` 쿠키에 본 글 번호를 쌓아 중복을 막으려 했다. 조건이
반대다.

```jsp
if (cookie == null) {
    result = activityCon.updateCount(postId);          // 쿠키가 없으면 올린다
} else {
    if (cookiePostList.indexOf(postId + "") != -1) {   // 목록에 **있으면**
        cookie.setValue(cookie.getValue() + ";" + postId);
        result = activityCon.updateCount(postId);      // 또 올린다
    }
}
```

| 상황 | 동작 |
|---|---|
| 쿠키가 아예 없다 (첫 조회) | 올린다 |
| 쿠키는 있는데 이 글은 처음 | **안 올린다** |
| 이미 본 글을 또 연다 | **볼 때마다 올린다** |

중복을 막으려던 장치가 정확히 중복만 세고 있다. 새 글은 세지 않고, 그 글은
쿠키에 담기지도 않으므로 영원히 세지 않는다.

**결정:** 그대로 옮긴다. 조회수는 화면에 뜨는 값이라 규칙을 고치면 레거시와 다른
숫자가 된다. 판단을 `PostViewCounter` 로 떼어내 `PostViewCounterTest` 가 못을
박는다 — 코드에 섞여 있으면 그대로 옮겼는지 확인할 수 없다.

글쓴이 본인이 열면 이 판단 자체를 하지 않는 것도 레거시 그대로다.

## D-030 · 답변글의 게시판 번호를 되살린다

`PostServiceImpl.replyPost` 에 이런 줄이 있다.

```java
int boardId = 2; // 외래키오류때문에 임시
```

`postReplyProc.jsp` 가 `bean.setBoardId(boardId)` 로 **올바른 번호를 담아 넘기는데
서비스가 이 줄로 덮어쓴다.** 어느 게시판에 답변을 달든 자유게시판(2번)에 쌓인다.

**결정:** 넘어온 값을 쓴다. 레거시 동작을 재현하지 않는다.

지금까지의 결함들(D-024 검색 분기, D-025 페이징, D-029 조회수)은 **보이는 것이

호출부가 이미 올바른 값을 갖고 있으며, 원저자가 "임시"라고 적어 두었다.

게이트도 실화면 대조도 이 선택을 검증하지 못한다. 둘 다 읽는 화면만 본다.
그래서 판단이라는 것을 분명히 적어 둔다. 되돌리려면 이 항목을 뒤집으면 된다.

## D-031 · 댓글 삭제를 POST 로 받는다

레거시는 링크였다.

```jsp
<a class="dropdown-item" href="commentDeleteProc.jsp?boardId=..&postId=..&id=..">삭제하기</a>
```

GET 으로 지워진다. 이관하며 CSRF 방어를 켰는데(D-013) 그 방어는 GET 을 보지
않으므로, 댓글 삭제만 방어를 비켜 간다. `<img src="...comment/delete?id=5">` 한 줄로
남의 댓글이 지워진다.

**결정:** POST 로 받는다. 화면의 "삭제하기"는 그대로 링크이고 JS 가 숨은 폼을
보낸다. 라벨도 위치도 달라지지 않는다.

**대가가 있다.** 숨은 입력 셋(`boardId`·`postId`·`id`)이 늘어 발명 게이트에 걸린다.
allowlist 에 사유와 함께 등록했다. 그 키들의 초과분이 이 화면에서 더는 검사되지
않는다는 뜻이므로, 공짜가 아니라는 것을 적어 둔다.

## D-032 · 글쓰기 화면의 게시판 이름이 하드코딩이다

`postRegister.jsp` 는 게시판 이름을 계산해 두고 쓰지 않는다.

```jsp
BoardBean board = activityCon.getBoard(boardId);
String boardName = board.getSubject();          // 계산은 한다
...
<input type="text" class="write-header-type" value="자유게시판" readonly>   <!-- 그런데 -->
```

공지사항에 글을 써도 "자유게시판"이 뜬다. `postReply.jsp` 와 `postUpdate.jsp` 는
같은 자리에 `<%=boardName%>` 을 쓴다. 같은 화면 셋 중 하나만 틀렸다.

**결정:** 그대로 옮긴다. 읽기 전용 표시라 저장되는 값에 영향이 없고, 고치면 화면
글자가 달라진다.

**게이트는 이것을 보지 못한다.** `value` 는 버튼류가 아닌 입력에서 라벨이 아니므로
(그 규칙 자체는 옳다), 정답에는 `control:input||text` 로만 남는다. 하드코딩이든
동적이든 같은 signature 다. `PostScreenTest.registerHardcodesBoardName` 이 실제
렌더링 결과에서 확인한다.

## D-033 · 이미 본 글을 다시 열면 레거시가 죽는다

실화면 대조로 찾았다. 조회수 규칙(D-029)을 실제로 돌려 보다가 500 이 났다.

```
java.lang.IllegalArgumentException: 쿠키 값에 유효하지 않은 문자 [59](;)가 있습니다.
        at org.apache.jsp.post.postView_jsp._jspService(postView_jsp.java:227)
```

`postView.jsp` 가 본 글 번호를 세미콜론으로 이어 붙인다.

```jsp
cookie.setValue(cookie.getValue() + ";" + postId);
response.addCookie(cookie);
```

세미콜론은 쿠키 값에 들어갈 수 없다. Tomcat 이 거부하므로 **이어 붙이는 순간
페이지가 500 으로 죽는다.**

D-029 의 뒤집힌 조건과 겹치면 실제 동작은 이렇게 된다.

| 순서 | 동작 |
|---|---|
| 아무 글이나 처음 열기 | 조회수 +1, 쿠키에 그 번호가 담긴다 |
| 다른 글 열기 | 쿠키에 없는 번호라 **조회수 안 오름**, 쿠키도 그대로 |
| 처음 열었던 글 다시 열기 | 이어 붙이다 **500** |

즉 브라우저 하나당 한 시간에 **글 하나만** 조회수가 오르고, 그 글은 다시 열 수
없다. 20년쯤 그렇게 돌았을 것이다.

**결정: 구분자만 바꾼다.** 세는 규칙(D-029)은 그대로 두고 `;` 를 `_` 로 바꾼다.
쿠키 값에 허용되는 글자다. 값의 뜻은 달라지지 않는다.

레거시가 남긴 `;` 짜리 값도 읽을 수 있게 둔다 — 이 Tomcat 에서는 만들어지지
못했지만 다른 설정에서는 남아 있을 수 있다.

**차이가 생긴다.** 신규는 이미 본 글을 다시 열면 조회수가 오르고 화면이 뜬다.
레거시는 죽는다. 500 을 재현하는 것은 이관이 아니다 — D-017(빈 검색어에 터지던
화면)과 같은 판단이다.

### 이 결함이 어디까지 안 보였는가

| 검사 | 결과 |
|---|---|
| 정합성 게이트 | 통과. 조회수는 `«dyn»` 이고 쿠키는 마크업에 없다 |
| 화면 한 번 받아 대조 | 통과. 첫 조회는 정상이다 |
| 규칙을 돌려 본 대조 | **여기서 잡혔다** |

**한 번 받아 보는 것으로는 부족하다.** 상태를 바꾸는 화면은 규칙을 여러 번
돌려야 드러난다. `compare_live.py` 에 조회수 집계 검사를 넣은 이유다.

### 대조가 대상을 바꾼다

같은 문제를 만드는 함정이 하나 더 있었다. 두 앱이 같은 스키마를 보므로 게시글
보기를 그냥 열면 **먼저 연 쪽이 조회수를 올려 놓아** 뒤에 연 쪽과 값이 달라진다.
처음에 그것을 결함으로 보고했다가 원인을 찾았다.

D-029 의 뒤집힌 조건을 역이용해 막았다 — 어떤 글 번호와도 겹치지 않는 쿠키를
심으면 양쪽 다 조회수를 올리지 않는다. 결함이 시험 도구가 된 셈이다.

## D-034 · 고칠 수 없는 입력의 `value` 는 화면 글자다

D-032 를 기록하면서 "게이트는 이것을 보지 못한다"고 적었다. 사각지대를 아는 채로
두는 것과 닫을 수 있는데 안 닫는 것은 다르다. 닫았다.

**규칙:** `readonly` 또는 `disabled` 가 걸린 입력의 `value` 를 라벨로 본다.

편집 가능한 입력의 `value` 는 데이터다 — 사용자가 지우고 다시 쓴다. 그것을 라벨로
세면 수정 폼의 모든 입력이 `«dyn»` 이 되어 정답이 아무것도 말해주지 않는다(D-002).
그 판단은 지금도 옳다.

**하지만 고칠 수 없는 입력은 다르다.** 사용자가 읽기만 하므로 그 자리에 박힌 글자와
다를 바 없다. 화면에 보이는 것을 세는 것이 이 하네스의 규칙이다.

### 닫혔다는 증거

레거시 글쓰기 화면의 게시판 이름(D-032)이 이제 정답에 남는다.

| 화면 | 이전 | 지금 |
|---|---|---|
| `postRegister` | `control:input\|\|text` | `control:input\|자유게시판\|text` |
| `postReply` | `control:input\|\|text` | `control:input\|«dyn»\|text` |
| `postUpdate` | `control:input\|\|text` | `control:input\|«dyn»\|text` |

셋이 구별된다. 이전에는 전부 같아서 **하드코딩이든 동적이든 게이트가 통과시켰다.**

말로만 닫혔다고 하지 않고 실제 화면으로 확인했다. `register.html` 의 하드코딩을
`th:value` 로 "고쳐" 보면 양쪽 게이트가 **HIGH** 로 막는다.

```
[1] check_no_invention   HIGH  control:input ««dyn»» [text]  레거시에 대응물 없음
[1] check_completeness   HIGH  control:input «자유게시판» [text]  신규에 대응물 없음
```

`TestFixedInputValue.test_hardcoded_and_dynamic_no_longer_look_alike` 가 이 성질을
못으로 박는다.

`EXTRACTOR_VERSION` 을 5 -> 6 으로 올렸다. 12화면 정답을 다시 뽑았고 전부 PASS 다 —
템플릿을 충실히 옮겨 두었기 때문에 고칠 것이 없었다.

### 닫지 못하는 것은 그대로 둔다

같이 검토했지만 닫지 않기로 한 것들이다. 할 수 있는데 안 하는 것과 원리상 못 하는
것을 구별해 둔다.

| 사각지대 | 왜 닫지 못하는가 |
|---|---|
| 날짜 형식 (D-020·D-026) | 형식이 자바 코드에 있다. 마크업만 보는 게이트가 닿지 않는다. e2e 몫 |
| 스크립틀릿 출력 (D-023) | 자바를 해석해야 한다. 리터럴만 처리하면 변수 연결은 여전히 못 본다 |
| 조회수 같은 상태 규칙 (D-033) | 마크업에 없다. 실화면을 여러 번 열어야 드러난다 — `compare_live` 가 본다 |

## D-035 · 팝업이 값을 돌려주는 방식을 하나로 맞춘다

찾기 팝업은 고른 값을 부모 창에 돌려주고 닫힌다. 레거시가 두 가지 방식을 쓴다.

```html
<!-- findBank.jsp — 마크업에서 함수를 직접 부른다 -->
<a onclick="selectBank('003', '기업은행')">003 기업은행</a>

<!-- findWork.jsp — data 속성에 담고 JS 가 읽어 간다 -->
<a class="a-work-info" data-key="010301" data-value="어로 어업">010301 어로 어업</a>
```

Thymeleaf 는 첫 번째를 거부한다.

```
Only variable expressions returning numbers or booleans are allowed in this context,
any other datatypes are not trusted
```

**막는 것이 옳다.** 이름에 작은따옴표가 들어가면 그 글자가 코드가 된다. 코드표는
지금 소스에서 온 값이지만, 같은 모양을 DB 값에 쓰면 바로 주입 통로가 된다.

**결정:** 은행 팝업도 `data` 속성 방식으로 맞춘다. `findBank.js` 가 `findWork.js`
와 같은 모양으로 읽어 간다.

화면에 보이는 것은 달라지지 않는다 — 라벨도, 링크도, 누르면 일어나는 일도 같다.
게이트도 통과한다(`onclick` 과 `data-*` 는 signature 에 들어가지 않는다).

레거시가 한 화면 안에서도 방식이 갈렸던 것을 하나로 모은 셈이다. 이관하며 굳이
두 갈래를 유지할 이유가 없다.

## D-036 · 문서 찾기 팝업의 도움말은 뜨지 않는다

세 팝업이 겉모습이 같다. 검색창 아래에 처음 열었을 때는 도움말, 검색한 뒤에는
결과 목록. 그런데 문서 찾기만 도움말이 뜨지 않는다.

```jsp
String search = Optional.ofNullable(request.getParameter("search")).orElse("");
...
if (search == null) {        // 절대 참이 되지 않는다
    <div class="tips"> ... </div>
} else {
    ... 결과 목록 ...
}
```

검색어를 **절대 `null` 이 안 되게 채워 놓고 `null` 인지 검사한다.** 도움말 마크업은
파일에 있지만 화면에는 한 번도 나온 적이 없다.

곁들여, `"".contains("")` 가 참이라서 **창을 열자마자 목록이 전부 뜬다.** 은행·업종
팝업은 도움말이 뜨고 목록은 검색해야 나온다. 같은 모양의 화면 셋이 다르게 동작한다.

**결정:** 그대로 옮긴다. 도움말이 뜨게 고치면 화면이 달라진다.

**마크업은 지우지 않는다.** 화면에 안 뜬다고 지우면 누락 게이트가 잡는다 — 정답은
JSP 원본에서 뽑으므로 도움말 마크업이 들어 있다. 조건도 레거시와 같이 «절대 참이
되지 않는 것»으로 맞춰 두었다.

게이트는 이 차이를 보지 못한다. 세 팝업 모두 도움말 마크업이 있고, 언제 보이는지는
서버가 정하기 때문이다. `FindPopupTest.documentPopupNeverShowsTips` 가 렌더링
결과에서 확인한다.

## D-037 · 겹쳐 닫힌 태그는 브라우저가 만드는 DOM 을 기준으로 옮긴다

`findUser.jsp` 는 `form` 과 `div` 가 서로 교차해 닫혀 있다.

```jsp
<div class="search-select-option-wrap">
  ...
  <form method="post" name="search-people-body" id="selectFrm">
    <input type="hidden" name="receivers">
    <div class="search-button"><button type="submit">선택</button></div>
</div>              <%-- form 이 열린 채로 div 를 닫는다 --%>
<hr>
<table> ... </table>
</form>             <%-- 짝이 이미 없다 --%>
```

Thymeleaf 는 이런 마크업을 읽지 못한다 — 파서가 짝을 요구한다. 그래서 옮기려면
한쪽으로 정해야 하는데, 기준은 **브라우저가 실제로 만드는 DOM** 이다.

HTML 파싱 규칙에서 `</div>` 는 그 `div` 뒤에 쌓인 요소를 전부 걷어낸다. `form` 도
같이 닫힌다. 뒤따라오는 `</form>` 은 짝이 없어 무시된다. 즉 화면에서 form 안에 있는
것은 `receivers` hidden 과 «선택» 버튼뿐이고 **표는 form 밖**이다.

**결정:** 그 DOM 을 그대로 적는다. form 을 `div` 경계에서 닫고 표를 밖에 둔다.

동작이 달라지지 않는 근거가 있다. 이 form 은 제출되지 않는다 — `findUser.js` 가
click 을 가로채 `preventDefault` 하고 고른 사번을 부모 창에 넘긴다. 체크박스를 읽는
선택자도 `$('input[name="userId"]:checked')` 로 문서 전체를 훑으며 form 안인지
밖인지 보지 않는다.

레거시에서는 표의 체크박스가 DOM 위치와 무관하게 `selectFrm` 에 **소속**된다. 파서가
«열려 있던 form» 을 기억해 뒤에 나오는 입력에 붙이기 때문이다. 제출하지 않으므로 그
소속은 아무 일도 하지 않는다.

게이트는 이 판단을 검증해 주지 않는다. signature 는 평면 목록이라 중첩을 보지 않는다
— 표를 form 안에 두든 밖에 두든 통과한다. 파싱 규칙을 근거로 정하고 여기 적는 것이
확인의 전부다.

`findEachUser.jsp` 도 같은 모양이며 같게 옮겼다. 한 사람이 같은 파일을 복사해 만들었을
것이다.

## D-038 · 관리자 부서 사용자는 목록에 보이지만 콤보로는 좁힐 수 없다

사용자 찾기 팝업은 세 조회를 쓴다. 여러 명 고르는 것과 한 명 고르는 것이 같은 조회다.

| 자리 | SQL |
|---|---|
| 부서 콤보 | `select * from dept_tbl where id <> -1` |
| 직급 콤보 | `select * from job_tbl where id <> -1` |
| 표 | `select dept_name, job_name, id, name from user_view where id <> 'admin'` |

`-1` 은 관리자 부서·직급이다. 레거시 `DepartmentService` 주석이 그렇게 적어 두었다 —
«불러올 때 관리자를 제외하고 불러올 것 (관리자 부서 번호: -1)». 콤보는 그것을 감춘다.

그런데 표는 `admin` **계정 하나만** 감춘다. 그래서 관리자 부서에 속한 일반 계정은 표에
나온다. 실제 데이터에 그런 사용자가 한 명 있다(직급은 «대표이사»). 표에 «관리자» 부서가
찍히는데 콤보에는 그 항목이 없으니, 그 부서만 골라 보는 것은 화면에서 불가능하다.

**결정:** 그대로 옮긴다. 콤보에 관리자 부서를 넣으면 레거시가 감춘 것이 드러나고,
표에서 그 사용자를 빼면 고를 수 있던 사람이 사라진다. 어느 쪽도 이관이 아니다.

시험은 콤보 쪽만 박아 뒀다(`FindPopupTest.adminDeptIsHiddenFromCombo`). 표에 그 부서가
보이는 것은 특정 계정의 부서 배정에 달린 사실이라, 시험으로 굳히면 데이터를 바꾸는
순간 깨진다. 부서로 걸러내는 시험도 «콤보에 있는 부서»를 골라 쓰게 해 두었다.

## D-039 · 협력업체 찾기는 번호로 찾을 수 없다

찾기 팝업 넷이 겉모습이 같다. 검색창에 코드나 이름을 넣으면 걸리는 것을 보여준다.
조건도 같아 보이는데 하나가 다르다.

| 화면 | 조건 |
|---|---|
| 은행 찾기 | `key.contains(search) \|\| value.contains(search)` |
| 업종 찾기 | `key.contains(search) \|\| value.contains(search)` |
| 제품 찾기 | `key.contains(search) \|\| value.contains(search)` |
| **협력업체 찾기** | `value.contains(search)` |

협력업체만 번호를 훑지 않는다. 그런데 도움말은 이렇게 안내한다.

```html
<strong>협력업체 ID</strong><br> 예) 1 -> 삼성
```

번호를 넣으면 «그 번호를 이름에 품은 업체»만 나온다. 도움말이 약속한 검색은 한 번도
동작한 적이 없다.

**결정:** 그대로 옮긴다. 조건을 고치면 검색 결과가 달라진다. 도움말도 지우지 않는다 —
화면에 있는 글자이고, 지우면 누락 게이트가 잡는다.

게이트는 이 차이를 보지 못한다. 도움말 마크업은 네 화면에 다 있고 무엇이 걸리는지는
서버가 정한다. `FindPopupTest.companyPopupCannotSearchById` 가 렌더링 결과에서
확인한다.

## D-040 · 여러 제품 찾기의 «전체 선택» 은 다시 켜지지 않는다

숨은 입력의 `name` 이 행 체크박스와 같다.

```html
<input name="productId" type="checkbox" value="031002">   <!-- 행마다 하나 -->
<input type="hidden" id="productId" name="productId">     <!-- 폼 끝에 하나 -->
```

스크립트는 이름으로 세어 «전체 선택» 을 맞춘다.

```js
const total = $("input[name=productId]").length;            // 행 수 + 1
const checked = $("input[name=productId]:checked").length;  // 행 수
if (total != checked) $("#chkAll").prop("checked", false);
```

숨은 입력은 체크될 수 없으므로 `total` 이 언제나 하나 크다. 그래서 행을 전부 골라도
«전체 선택» 이 켜지지 않는다. 위에서 눌러 한 번에 고르는 것은 되지만, 하나 풀었다 다시
채우면 그 체크는 돌아오지 않는다.

**결정:** 그대로 옮긴다. `name` 을 바꾸면 고쳐지지만 그것은 이관이 아니다. 고르는 동작
자체는 멀쩡하다 — 부모 화면에 넘어가는 것은 체크된 체크박스의 값이고 숨은 입력은
그 계산에 끼지 않는다. 표시만 어긋난다.

숨은 입력 둘(`productId`·`productName`)은 아무 곳에도 쓰이지 않는다. 폼이 제출되지 않고
스크립트도 읽지 않는다. 그래도 남긴다 — 정답에 있으므로 지우면 누락으로 잡힌다.

## D-041 · 결재라인 문자열은 컬럼을 그대로 읽는다

`proposal_route_view` 에는 결재 순서대로 사번을 이은 `route` 컬럼이 있다.

```
id=33  nickname=정기보고  route=20221003;20221001;20221002
```

레거시 팝업은 이 값을 그대로 쓰지 않는다. 목록을 받아 온 뒤 결재라인마다 조회를 한 번
더 하고, `route` 를 `;` 로 쪼개 사번마다 사용자를 조회해 객체로 만든 다음, 그 객체들의
사번을 다시 `;` 로 이어 화면에 찍는다. 결재라인이 10개면 조회가 1 + 10 + 사람 수만큼
일어나고, 결과는 처음 읽은 컬럼과 같은 문자열이다.

**결정:** 컬럼을 그대로 읽는다.

같은 값이 나오는 근거는 왕복이 항등이기 때문이다 — 쪼갠 순서대로 다시 이으며, 사번은
조회해도 달라지지 않는다. 지금 데이터의 `route` 값에는 빈 조각도 꼬리 구분자도 없다.
`FindPopupTest.proposalRoutePopupHandsBackTheRouteString` 이 그것을 확인한다.

어긋나는 경우가 둘 있는데, 둘 다 **레거시가 화면을 못 띄우는** 자리다.

| 자료 | 레거시 | 여기 |
|---|---|---|
| `route` 가 `null` | `NullPointerException` → 500 | 빈 값을 넘긴다 |
| 사번이 `user_view` 에 없다(사용자 삭제) | `NullPointerException` → 500 | 그 사번을 그대로 넘긴다 |
| `"a;b;"` 처럼 꼬리 구분자 | `"a;b"` 로 정리된다 | `"a;b;"` 그대로 |

앞의 둘에서 레거시는 팝업 자체가 뜨지 않는다. 그 죽음을 재현하지 않는다 — D-033 에서와
같은 판단이다. 셋째는 지금 데이터에 없고, 생기면 부모 화면이 받는 문자열이 달라진다.
그때는 여기 다시 적는다.

**곁들여 알아 둘 것:** 목록을 걸러내기 전에 조회한다는 점도 레거시와 다르다. 레거시는
검색어에 걸리지 않는 결재라인까지 전부 조회한 뒤 버린다. 읽기만 하므로 화면에 나오는
것은 같다.

## D-042 · 500 오류 화면을 잇는다 — 레거시에서는 한 번도 뜨지 않았다

레거시는 `web.xml` 에서 상태 코드를 화면에 이었다.

```xml
<error-page>
    <error-code>404</error-code>
    <location>/notFoundError.jsp</location>
</error-page>
<error-page>
    <error-code>500</error-code>
    <location>/internalServerError.html</location>   <!-- 실제 파일은 .jsp 다 -->
</error-page>
```

500 쪽이 없는 파일을 가리킨다. `internalServerError.html` 은 없고 `internalServerError.jsp`
가 있다. 확장자 한 글자가 어긋나 **그 화면은 500 응답에서 한 번도 뜬 적이 없다** —
톰캣 기본 오류 화면이 떴다. 화면 파일은 주소로 직접 열 때만 보였다.

**결정:** 둘 다 잇는다({@code ErrorViewConfig}).

레거시와 똑같이 만들 길이 없기 때문이다. 안 이으면 우리 앱은 스프링 기본 오류 화면을
띄우는데, 그것도 톰캣 기본 화면과 다르다. 어느 쪽을 골라도 달라지므로 **만든 사람의
의도와 같은 쪽**을 고른다 — 화면 파일이 있고, 이으려 했고, 한 글자를 틀렸다.

실행 중인 앱에서 확인했다.

| 요청 | 결과 |
|---|---|
| `/css/nope.css` (없는 정적 파일) | 404 + 페이지 없음 화면 |
| `/error` (HTML 요청) | 500 + 내부 서버 오류 화면 |
| `/not-found-error`·`/internal-server-error` | 200 + 각 화면 (레거시도 주소였다) |

**어긋나는 것 하나.** 로그인하지 않은 사람이 없는 주소를 열면 우리 앱은 404 화면이
아니라 로그인 화면으로 보낸다. Spring Security 가 요청을 받는 곳이 화면 찾기보다
앞이라, «없는 주소»와 «권한이 필요한 주소»를 구별하지 않기 때문이다. 레거시는 누구에게나
404 화면을 보여줬다 — 어떤 주소가 있는지 알려 주는 쪽이었다. 로그인한 사람에게는 양쪽이
같다.

404·5xx 밖의 상태에는 화면을 붙이지 않았다. 레거시 `web.xml` 도 그 둘만 적었고, 없던
화면을 새로 띄우는 것은 발명이다. 403 은 이미 권한 오류 화면으로 간다.

## D-043 · 수·발주 등록을 한 트랜잭션으로 묶는다

레거시 `createTask` 는 본체(`task_tbl`)를 넣고 생성된 id 로 이력(`task_history_tbl`)을
한 줄씩 넣는다. 트랜잭션이 없다 — 각 `INSERT` 가 그 자리에서 커밋된다. 게다가 예외를
`catch` 로 삼키고 **본체 삽입 성공 여부만** 돌려준다.

```java
flag = pstmt.executeUpdate() == 1;   // 본체
...
for (TaskHistoryBean bean : products) {
    if (bean.getCount() > 0) createTaskHistory(bean);   // 이력. 실패해도 무시
}
return flag;                          // 본체 결과만 본다
```

그래서 이력 하나가 실패해도 본체는 남고, 화면에는 «등록에 성공했습니다» 가 뜬다.
부분 저장이 성공으로 보고되는 것이다.

**결정:** `TaskService.create` 를 `@Transactional` 로 묶는다. 이력이 실패하면 본체까지
되돌린다.

정상 데이터(제품 팝업으로 고른 실재 제품, 수량 정수)에서는 결과가 같다 — 그래서
1단계 정합에 넣었다. 달라지는 것은 **오류 경로뿐**이고, 그 경로에서 레거시가 하던
«부분 저장 + 성공 보고» 는 되살릴 가치가 없는 결함이다. 되살리려면 이력 예외를 삼키고
성공을 반환해야 하는데, 그것은 데이터를 조용히 잃는 길이다.

이 결정은 «먼저 똑같이» 원칙에서 의도적으로 벗어난 예다. 게이트가 못 보는 서버 동작
이라 여기 적어 둔다. 2단계에서 등록 실패 처리를 다시 볼 때 이 항목을 참조한다.

수량 0 인 제품은 이력에 넣지 않는 것은 레거시 그대로다(`if count > 0`).

## D-044 · 발주 수정은 언제나 실패한다 — 레거시가 type 을 안 넣는다

레거시 `updateTask` 의 SQL 이다.

```sql
update task_tbl set user_tbl_id = ?, document_tbl_id = ?, task_at = ?, status = ?
 where id = ? and type = ?
```

그런데 `taskUpdateProc.jsp` 는 본체를 채울 때 `type` 을 넣지 않는다.

```java
task.setId(...); task.setUserId(...); task.setDocumentId(...);
task.setTaskAt(...); task.setStatus(...);
// task.setType(...) 이 없다
result = taskCon.updateTask(task);
```

`TaskBean.type` 은 int 기본값 **0** 이다. 그래서 WHERE 절이 언제나 `type = 0` 이 되어,
**발주(type=1) 수정은 걸리는 행이 없어 0 행이 바뀌고 «수정에 실패했습니다» 가 뜬다.**
수주(type=0)만 수정된다.

**곁들여** 더 나쁜 것: 본체 수정 결과와 상관없이 이력은 지우고 다시 넣는다.

```java
result = taskCon.updateTask(task);   // 발주면 false
taskCon.deleteTaskHistory(task.getId());   // 그래도 이력은 지운다
for (...) taskCon.createTaskHistory(bean); // 그리고 다시 넣는다
```

그래서 발주 수정은 «실패» 라고 뜨는데도 **제품 이력은 실제로 바뀐다.** 사용자는
실패한 줄 알지만 데이터는 달라져 있다.

**결정:** 그대로 옮긴다. `TaskUpdate.type` 을 flag 와 무관하게 0 으로 두고
({@code TaskController.update} 주석), 본체 결과만 «성공/실패» 로 보고하되 이력은 항상
갈아 끼운다. 게이트는 이 결함을 못 본다 — SQL 과 서버 동작이라 화면 대조에 안 잡힌다.
실화면 대조에서 «발주 수정이 늘 실패» 로 드러날 것이다.

2단계에서 고칠 후보다 — flag 로 type 을 넣으면 발주 수정이 되살아난다. 다만 그때
«실패해도 이력이 바뀌던» 동작도 함께 정리해야 한다.

수정은 등록과 달리 수량 0 인 제품도 이력에 넣는다(레거시가 수정 루프에는
`if count > 0` 을 걸지 않는다). 이것도 그대로 옮겼다.


> **2단계에서 해소했다(D-106).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-045 · 쪽지함 페이징은 원래 동작하지 않는다

`message/index.jsp` 의 페이징 링크는 `javascript:block(...)`·`javascript:paging(...)` 을
부른다. 그런데 이 화면이 읽어들이는 스크립트(`js/main/index.js`,
`js/message/index.js`) 어디에도 두 함수가 없다. 두 함수는 다른 목록 화면들
(`unitList.js`·`task.js`·`company.js` 등)에 각자 정의돼 있고, 쪽지 화면은 그 어느
것도 로드하지 않는다.

그래서 링크를 누르면 `ReferenceError` 가 날 뿐 아무 일도 일어나지 않는다. **쪽지가
15건을 넘어도 1페이지 말고는 볼 수 없다.**

**결정:** 그대로 옮긴다. 페이징 마크업은 두되(정답에 있으므로 지우면 누락),
`block`/`paging` 을 정의하지 않는다 — 레거시와 같은 «죽은 페이징» 이다.

게이트는 이것을 못 본다. 링크는 `javascript:` 라 detail 이 `javascript:` 로만 남고,
함수가 있는지는 마크업에 없다. 실화면에서 눌러 봐야 드러난다.

2단계에서 되살릴 후보다 — `block`/`paging` 이 `classFrm` 을 제출하게 정의하면
페이징이 동작한다. 다른 목록 화면들과 달리 쪽지는 페이징 폼이 `classFrm` 이라
그 이름에 맞춰야 한다.


> **2단계에서 해소했다(D-107).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-046 · 쪽지 읽기 화면은 여는 순간 «읽음» 으로 바꾼다

`read.jsp` 는 화면을 그리기 전에 `readMessage(session, messageId)` 를 부른다.

```sql
update message_tbl set read_at = now(), read_status = 1 where id = ?
```

읽지 않은 쪽지({@code read_status == 0})일 때만 갱신한다. 즉 **화면을 여는 것이 대상을
바꾼다** — 게시글 조회수(D-029)와 같은 부류다.

**결정:** 그대로 옮긴다. `MessageService.read` 가 `markRead` 로 읽음 처리를 한 뒤 내용을
읽어 온다. 레거시가 Java 에서 «읽지 않았을 때만» 을 판정하던 것을 SQL 의
`WHERE id = ? AND read_status = 0` 으로 옮겼다 — 이미 읽은 쪽지는 `read_at` 이 바뀌지
않아 결과가 같다.

**실화면 대조에서 주의.** 두 앱이 같은 스키마를 본다. 한 쪽에서 쪽지를 열면 다른 쪽에도
읽음으로 보인다 — 먼저 연 쪽이 뒤에 연 쪽을 오염시킨다(D-020 «대조가 대상을 바꾼다»).
쪽지 읽기를 실화면 대조에 넣는다면, 조회수에서 쓴 방법처럼 «이미 읽은 쪽지»를 골라
양쪽을 견주거나, 읽음 처리가 없는 화면만 대조해야 한다.

## D-047 · 쪽지 삭제는 지우지 않고 «내 쪽에서만» 숨긴다

쪽지 삭제는 행을 지우지 않는다. 보낸 사람과 받는 사람이 각자 «지울» 수 있어야 하므로,
지우면 상대의 쪽지까지 사라진다. 그래서 각 쪽에 visible 플래그가 따로 있다.

```java
if (isSender)   sb.append("sender_visible = 0 ");
if (isReceiver) sb.append("receiver_visible = 0 ");
String sql = "update message_tbl set " + sb + "where id = ?";
```

내가 보낸 쪽지면 `sender_visible`, 받은 쪽지면 `receiver_visible` 을 내린다. 자기 자신에게
보낸 쪽지는 둘 다 내려간다. 목록 SQL 이 `<class>_visible = 1` 로 거르므로(D 없음, Phase ①),
숨긴 쪽에서만 사라지고 상대 쪽에는 남는다.

**결정:** 그대로 옮긴다. `MessageService.delete` 가 쪽지의 보낸/받는 사람을 읽어
어느 플래그를 내릴지 정하고, `hide` 매퍼가 그 플래그만 0 으로 바꾼다.

**나와 무관한 쪽지.** 레거시는 이때 SET 절이 비어 `update message_tbl set where id=?`
가 되어 SQL 오류가 났고 결과가 false 였다. 오류를 재현하지 않는다 — 보낸 사람도 받는
사람도 아니면 서비스가 매퍼를 부르지 않고 false 를 돌려준다. 결과(false)는 같다.

삭제 액션은 둘이다. 목록에서 삭제({@code /message/delete})는 쪽지함으로 돌아가고,
읽기에서 삭제({@code /message/read-delete})는 팝업을 닫고 여는 창을 새로 고친다.
지우는 로직은 같다 — 후처리만 다르다.

## D-048 · 입·출고 수정은 사번 자리에 제품 코드를 채운다

`bound_view` 에는 {@code user_id} 컬럼이 없다. 그런데 뷰를 읽는 코드가 사번 자리에
제품 코드를 넣는다.

```java
// ResultSetExtractHelper.extractViewBoundBean
new ViewBoundBean(
    rs.getInt("id"),
    rs.getString("product_id"),   // productId
    rs.getString("product_name"),
    rs.getString("product_id"),   // userId  ← 제품 코드다
    rs.getString("user_name"),
    ...
```

수정 화면(`boundUpdate.jsp`)은 이 값을 숨은 `userId` 에 채운다. 사용자가 직원을 다시
고르지 않고 제출하면, 처리에서 `user_tbl_id = 제품 코드` 로 덮인다 — **조용히 데이터가
손상된다.** 화면에 보이는 이름(`user_name`)은 멀쩡해서 눈치채기 어렵다.

**결정:** 그대로 옮긴다. `findForUpdate` 가 `bound_view` 에서 `product_id AS userId` 로
읽어 숨은 필드에 제품 코드를 넣고, 수정 처리는 그 값을 그대로 저장한다.

이것은 «먼저 똑같이» 원칙을 지키느라 손상 버그까지 재현한 예다. D-044(발주 수정 실패)와
같은 결이지만 그쪽은 눈에 보이는 실패였고, 이쪽은 **조용한 손상**이라 더 위험하다.
게이트는 못 본다 — 숨은 입력의 값은 signature 에 안 들어간다.

**2단계 최우선 수정 후보.** `bound_tbl.user_tbl_id` 를 직접 읽으면 올바른 사번이 채워져
손상이 사라진다. 이관을 마치는 대로 이 항목부터 고칠 것을 권한다.

입고 시간(`bounded_at`)은 수정 대상이 아니다 — 레거시 update SQL 에 없고 화면 날짜
입력도 비어 있다. 그대로 뒀다.


> **2단계에서 해소했다(D-103).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-049 · 결재 승인·반려는 «내 차례»를 확인하지 않는다

`proposalDocumentProc.jsp` 는 로그인만 본다. 화면 권한(`PROGRAM_CODE`)도 없다.

```jsp
UserBean user = WebHelper.getValidUser(session);

if (!WebHelper.isLogin(session)) { ... }
...
int button = parameters.get("result").equals("confirm") ? 1 : 2;
```

`user` 를 꺼내 놓고 한 번도 쓰지 않는다. **결재번호만 맞으면 누구의 결재든 승인되고
반려된다.** 결재선에 없는 사람도, 이미 지나간 차례도 마찬가지다.

화면도 막지 않는다. 문서 상세는 상태가 진행중이기만 하면 승인·반려 버튼을 그린다 —
누가 열었는지 보지 않는다. 결재 문서를 볼 수 있는 사람이면 남의 차례를 대신 눌러
버릴 수 있다.

**결정:** 그대로 옮긴다.

막는 방법은 분명하다 — `route` 를 `;` 로 쪼개 `step` 번째가 로그인 사번인지 보면
된다. 목록이 이미 그 판정을 하고 있다(D-052). 그러나 판정을 붙이는 순간 «지금
동작하는 것»이 동작하지 않게 된다. 대리 결재가 관행일 수도 있고, 그 판단은 이관이
아니라 운영의 몫이다.

**2단계 최우선 수정 후보.** D-048 과 같은 자리에 둔다. 그쪽이 조용한 데이터 손상이라면
이쪽은 조용한 권한 구멍이다. **게이트는 못 본다** — 버튼도 폼도 레거시와 같고, 달라야
하는 것은 서버가 하는 확인이다.


> **2단계에서 해소했다(D-102).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-050 · 결재 도장은 사번이 아니라 «자리»로 찍힌다

결재 스탬프 표는 결재선 길이만큼 칸을 만들고, 그 문서의 결재 자취를 순서대로 짝짓는다.

```jsp
for (int i = 0; i < routeSize; ++i) {
    if (i < history.size()) {
        ViewProposalBean proposal = history.get(i);           // 자취의 i 번째
        String name = userCon.getUser(routes[i]).getName();   // 결재선의 i 번째
        boolean isApproved = proposal.getApprovedAt() != null;
```

이름은 **결재선의 i 번째**에서 오고, 승인 여부와 시각은 **자취의 i 번째**에서 온다.
둘이 같은 사람이라는 보장이 없다. 게다가 자취를 읽는 SQL 에 `ORDER BY` 가 없다.

```sql
select * from proposal_view where document_id = ?
```

라이브 데이터에 이미 어긋난 자리가 있다. 결재선이 넷인 어떤 문서의 자취가 다섯 줄이고
그중 둘이 같은 `step` 이다(한쪽은 승인 시각이 비어 있다). 그래서 마지막 자리의 도장에는
**셋째 결재자의 승인 시각**이 찍히고, 마지막 결재자가 실제로 승인한 시각은 표에 나오지
않는다.

**결정:** 그대로 옮긴다. `ORDER BY` 를 넣지 않고, 짝짓기도 자리 번호로 한다.

순서를 정해 주면 고쳐지는 것처럼 보이지만, 어느 순서가 정답인지는 근거가 없다. 지금
화면과 달라진다는 것만 확실하다. 자취가 결재선과 어긋나 있다는 사실 자체가 데이터의
문제이며, 그것을 화면에서 가리는 것은 이관이 아니다.

---

## D-051 · 승인 한 번을 한 트랜잭션으로 묶는다

레거시는 승인 한 번에 문장을 둘 또는 셋 던진다. 트랜잭션은 없다.

```java
proposalCon.confirmProposal(bean);   // 내 차례를 닫는다  (result 0, approved_at now)
int nextStep = bean.getStep() + 1;
String nextUser = route.getRoute().split(";")[nextStep];
...
proposalCon.createProposal(bean);    // 다음 차례를 만든다
```

사이에서 끊기면 **내 차례는 닫혔는데 다음 차례가 없는 결재**가 남는다. 그 문서는
아무도 결재할 수 없고 어느 목록에도 뜨지 않는다 — `result` 0 은 진행중(3)·승인(1)·
반려(2) 어느 필터에도 걸리지 않기 때문이다.

**결정:** 한 트랜잭션으로 묶는다(D-043 과 같은 판단). 정상 흐름에서 화면에 보이는
것은 달라지지 않는다.

**곁들여 알아 둘 것 둘.**

«마지막 차례인가»를 판정하는 `isFinalStep` 은 지금 결재의 `step` 이 아니라 **그 문서에서
가장 큰 `step`** 을 본다(`order by step desc limit 1`). 같은 문서에 결재가 여러 벌 쌓이면
지나간 차례를 승인해도 «마지막»으로 판정될 수 있다. 그대로 옮겼다.

안내 문구는 뜻이 뒤집혀 있다. 중간 결재가 «결재완료하였습니다», 마지막 결재가
«결재하였습니다» 다. 화면 글자이므로 손대지 않는다.

## D-052 · 결재 리스트는 «지금 내 차례»만 보여준다 — SQL 이 아니라 Java 가 거른다

결재 리스트를 옮길 때(B①) 조회 조건만 옮기고 **그 뒤에 오는 거르기를 빠뜨렸다.**

```java
// ProposalServiceImpl.getProposalViews(userId, result, start, cnt)
String sql = "select * from proposal_view where (result = 3 and route like ?) "
        + "or (original_user = ? and user_id= ? and result = ?) " + additional
        + " order by id desc limit ?, ?";
...
return vlist.stream().filter(bean -> {
    ViewProposalRouteBean routeBean = routeSvc.getProposalRouteView(bean.getRouteId());
    Vector<ViewUserBean> users = routeBean.getRoute();
    int step = bean.getStep();
    return users.size() > step && users.get(step).getId().equals(userId);
}).collect(Collectors.toCollection(Vector::new));
```

SQL 의 `route like '%나%'` 는 **결재선 어딘가에 내가 있으면** 걸린다. 넷이 결재하는
문서라면 진행중인 동안 네 사람 모두의 목록에 뜬다. 거르기가 그중 «지금 차례인
사람»만 남긴다. 이 조각이 없으면 아직 오지 않은 차례와 이미 지나간 차례가 함께
보인다 — 승인해도 목록에서 사라지지 않는다.

**결정:** 레거시와 같은 자리에서 같은 방식으로 거른다. 가져온 뒤 Java 에서 한다.

SQL 로 옮기면 «맞는» 결과가 나오지만 레거시와 달라진다. 거르기가 `limit` 뒤에
일어나므로 한 페이지에 남는 줄 수가 들쭉날쭉하고(10건을 가져와 3건만 남기도 한다),
페이지 수를 세는 `getProposalViewsCount` 에는 이 거르기가 없어 **세는 것과 보여주는
것이 애초에 다르다.** SQL 로 내리면 그 어긋남이 사라져 페이지 수가 달라진다.

결재선을 다시 조회하지 않는 것만 다르다. 레거시는 판정을 위해 결재라인을 한 번 더
읽고 사번마다 사용자를 또 읽었는데, 견주는 값은 뷰가 이미 들고 있는 `route` 컬럼의
`step` 번째와 같다(D-041 과 같은 판단).

**왜 게이트가 못 잡았나.** 게이트는 화면의 요소를 견준다. 표의 «줄이 몇 개인가»는
데이터이고 정답에 없다. B③(문서 상세)을 만들며 승인 뒤 목록이 어떻게 달라져야 하는지
따지다 드러났다 — 화면 하나를 끝냈다고 그 화면이 끝난 것이 아니라는 예다.

## D-053 · 관리자 화면은 경로로 막는다 — `screen` 표에 없기 때문이다

다른 화면은 `screen` 표가 경로를 프로그램에 잇고, 프로그램의 비트마스크로 판정한다
(`ScreenAuthorizationManager`). 표에 없는 경로는 **로그인만 되어 있으면 통과**한다 —
레거시에서 `PROGRAM_CODE` 가 없던 화면들이 그랬기 때문이다.

관리자 화면 26개가 전부 그 표에 없다. 레거시가 프로그램 권한을 쓰지 않고 화면마다
이렇게만 물었다.

```jsp
if (!permissionCon.isAdmin(session)) {
    response.sendRedirect("../../permissionError.jsp");
    return;
}
```

그래서 지금까지의 규칙을 그대로 두면 **로그인한 누구나 `/admin/user/list` 를 열 수
있다.** 사원 명부와 주민등록번호가 통째로 열린다.

**결정:** 경로 규칙으로 막는다. `/admin`, `/admin/**` 은 `ROLE_ADMIN` 을 요구한다.

관리자 판정은 레거시와 같다 — 부서·직급 비트마스크 양쪽에 최상위 비트
(`Permissions.isAdmin`). 그 판정 결과를 로그인 시 권한으로 실어 준다. 비밀번호를
바꿔야 하는 사용자에게는 주지 않는다.

화면마다 다시 묻지 않는다. 39개 JSP 에 같은 조각이 박혀 있던 것을 한 곳으로 모은 것과
같은 이유다 — 새 관리자 화면을 만들며 검사를 빠뜨리는 실수가 구조적으로 막힌다.

**게이트는 이 자리를 못 본다.** 마크업이 아니라 누가 열 수 있는가의 문제다. 시험으로
박아 둔다(`AdminUserScreenTest`).

## D-054 · 검색할 «칸 이름»이 SQL 에 그대로 붙는다

사원 리스트의 검색은 고른 칸 하나를 훑는다. 그 칸 이름이 요청 파라미터다.

```java
String additional = keyfield + " like ? and ";
String sql = "select * from user_view where " + additional
        + "id <> 'admin' order by dept_name, job_name limit ?, ?";
```

검색어는 `?` 로 묶이지만 **칸 이름은 묶이지 않는다.** 주소창에 무엇을 적든 조건이
된다. 화면 콤보는 다섯 가지만 주지만 콤보는 값을 제안할 뿐 막지 못한다.

**결정:** 화면이 주는 다섯 가지만 받는다(`AdminUserSearch`). 그 밖의 값은 조건이 아예
붙지 않는다.

D-028(내려받기 제한)과 같은 예외다 — **없던 구멍을 그대로 옮기는 것은 이관이 아니다.**
정상 검색은 달라지지 않는다.

**달라지는 것 하나.** 레거시에 엉뚱한 칸 이름을 주면 SQL 이 깨져 예외가 나고, 예외를
삼킨 자리가 빈 목록과 건수 -1 을 돌려주어 **빈 표**가 뜬다. 우리는 조건 없는 전체
목록이 뜬다. 관리자가 기본으로 보는 화면이 그 전체 목록이므로 새로 드러나는 것은
없다.

## D-055 · 로그아웃은 링크(GET)다 — CSRF 를 켜자 404 가 됐다

레거시 헤더 메뉴의 «로그아웃» 은 링크다.

```html
<a href="/ERFlow/login/logoutProc.jsp">로그아웃</a>
```

이관하면서 CSRF 방어를 켰다(D-013). 그러자 프레임워크 기본 로그아웃이 **POST 만**
받게 되고, 링크는 어느 필터에도 걸리지 않아 404 가 됐다. 헤더 메뉴는 DB 에서 오므로
링크는 멀쩡히 그려진다 — **눌러야만 드러나는 고장**이었다. 관리자 헤더를 옮기다
확인했다(`GET /login/logout-proc` → 404).

**결정:** 로그아웃만 GET 을 받는다(`logoutRequestMatcher`). 화면은 레거시 그대로
링크와 버튼이다.

POST 로 바꾸는 쪽은 폼을 새로 만들어야 한다. 헤더 메뉴 항목은 데이터(menu 표)라
그 자리에 폼을 넣으려면 «이 URL 만 폼으로» 같은 예외가 필요하다 — 화면에 없던 것을
지어내는 셈이다.

**대신 잃는 것:** 로그아웃 CSRF. 남이 만든 페이지가 사용자를 강제로 로그아웃시킬 수
있다. 데이터가 새거나 바뀌지 않으므로 D-013 이 막으려던 것과 급이 다르다. 눌리지도
않는 로그아웃이 더 나쁘다.

시험으로 박아 둔다(`LogoutTest`).

## D-056 · 정답이 0건인 화면이 있다

주소 팝업(`admin/user/userAddress.jsp`)에서 정답을 뽑으면 **요소가 하나도 안 나온다.**

```jsp
<span class="location-span">우편번호 : <%=postalCode%></span>
```

글자가 전부 «라벨 : 값» 모양이라 추출기가 그 텍스트 노드를 통째로 동적으로 본다.
라벨만 따로 떼어 낼 방법이 없다 — 한 노드 안에서 섞여 있기 때문이다.

**결정:** 화면 목록에 그대로 둔다. 정답도 0건인 채로 커밋한다.

0건짜리 정답은 **아무것도 판정하지 못한다.** 무엇을 넣어도 발명으로 잡히지 않고,
무엇을 빼도 누락으로 잡히지 않는다. 그래도 목록에서 빼지 않는 이유는 «이 화면이
있다»는 사실과 «게이트가 이 화면을 못 본다»는 사실을 함께 남기기 위해서다. 빼면
둘 다 사라진다.

이 화면은 게이트가 아니라 눈으로 대조한 결과다. 실화면 대조(D-020)가 볼 수 있는
자리이므로 그때 다시 본다.

## D-057 · 사원 등록·수정이 화면에 입력한 값을 버린다

`userRegisterProc.jsp` 는 요청 파라미터를 여섯 개만 맵에 담는다.

```java
final String[] keys = new String[] { "id", "name", "socialNumber", "email", "job", "dept" };
for (String key : keys) { ... parameters.put(key, value.equals("") ? null : value); }
...
user.setAddress2(parameters.get("address1"));   // 맵에 없다 -> null
user.setAddress2(parameters.get("address2"));   // 맵에 없다 -> null
```

주소 두 줄을 **맵에 담지도 않은 채** 꺼내 쓴다. 그래서 둘 다 `null` 이다. 게다가
같은 setter 를 두 번 부른다 — 도로명 주소를 상세 주소 자리에 넣으려던 흔적이다.
휴대 전화(`mobilePhone`)는 아예 읽지 않는다. 화면에는 입력칸이 있고, 사용자는 채워
넣고, 저장 버튼을 누르면 **우편번호만 남는다.**

수정(`userUpdateProc.jsp`)은 주소를 제대로 담는다. 대신 휴대 전화를 읽지 않는데
갱신 문장에는 그 칸이 있다.

```sql
update user_tbl set name = ?, ..., mobile_phone = ? where id = ?
```

**사원 정보를 한 번 고칠 때마다 저장돼 있던 휴대 전화가 지워진다.** 화면에는 번호가
채워져 보이고, 고친 사람은 이름만 바꿨다고 생각한다.

| | 등록 | 수정 |
|---|---|---|
| 도로명 주소 | 버린다 | 저장한다 |
| 상세 주소 | 버린다 | 저장한다 |
| 휴대 전화 | 버린다 | **저장된 값을 지운다** |
| 주민등록번호 | 저장한다 | 갱신 문장에 없어 그대로 남는다 |

**결정:** 그대로 옮긴다. 화면도 손대지 않는다 — 입력칸을 지우면 있던 것이 사라진다.

D-048(입·출고 수정이 사번 자리에 제품 코드를 넣는다)과 같은 «조용한 손상» 이며,
**2단계 최우선 수정 후보**다. 고치는 방법은 분명하다 — 처리에서 그 파라미터를 읽으면
된다. 다만 지금 고치면 «레거시와 같은가»를 물을 수 없다.

**게이트는 못 본다.** 입력칸은 양쪽에 다 있고, 사라지는 것은 저장된 값이다. 시험으로
박아 뒀다(`AdminUserScreenTest`).


> **2단계에서 해소했다(D-104).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-058 · 같은 콤보가 화면마다 다른 순서로 그려진다

직급·부서 콤보는 두 화면에 있다. 조회는 같은 SQL 이다.

```sql
select * from job_tbl where id <> -1     -- ORDER BY 가 없다
```

사원 추가 화면은 이 순서를 그대로 그린다. 사원 수정 화면만 받아 온 목록을 **자바에서**
이름순으로 다시 정렬한다(`Collections.sort` + 익명 `Comparator`). 그래서 같은 콤보의
항목 순서가 두 화면에서 다르다.

**결정:** 그대로 옮긴다. 정렬도 자바에서 한다.

`ORDER BY name` 으로 내리면 «맞는» 결과가 나오지만 기준이 달라진다 — 자바
`String.compareTo` 는 UTF-16 코드 단위 비교이고 DB 는 collation(`utf8mb4_general_ci`)
비교다. 지금 데이터(한글 이름)에서는 결과가 같지만 영문·숫자가 섞이면 갈린다
(대소문자를 DB 는 같게 보고 자바는 다르게 본다). 기준이 다른 것을 결과가 같다는
이유로 바꾸지 않는다.

## D-059 · 부서를 고치면 주소가 지워진다

`deptUpdate.jsp` 의 주소칸에는 `value` 가 없다.

```jsp
<input type="text" id="sample6_postcode" placeholder="우편번호" name="postalCode" readonly>
<input type="text" id="sample6_address" placeholder="도로명 주소" name="address1" readonly>
```

부서 이름만 고치러 들어와도 주소는 **언제나 빈 채로** 뜨고, 처리는 그 빈 값을 그대로
저장한다. 우편번호 찾기를 다시 누르지 않으면 저장돼 있던 주소가 사라진다.

**이미 일어난 일이다.** 라이브 데이터에 흔적이 남아 있다.

```
dept 12 영업관리부  postal_code='49376'  address1='부산 …'   <- 손대지 않은 부서
dept 11 인사관리부  postal_code=''       address1=''         <- 한 번 수정한 부서
dept 19 영업1팀     postal_code=NULL     address1=NULL       <- 처음부터 없던 부서
```

빈 문자열과 `NULL` 이 갈리는 것이 그 자국이다. 누군가 수정 화면을 열어 저장했고, 그
순간 주소가 지워졌다.

**결정:** 그대로 옮긴다. 화면도 손대지 않는다 — 값을 채워 주면 «고쳐지지만» 그것은
이관이 아니다. D-057(사원 등록·수정이 값을 버린다)과 같은 자리이며 **2단계 수정
후보**다.

부서장(`user_tbl_manager_id`)은 다르다. 그쪽은 화면에 입력칸이 아예 없고 레거시가
읽어서 되돌려 놓으므로, 우리도 읽어서 되돌려 놓는다. 안 그러면 없던 손상이 생긴다.


> **2단계에서 해소했다(D-105).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-060 · 새 비트 자리는 `long` 으로 고른다 — 레거시는 31번째에서 관리자를 만든다

부서·직급을 만들면 아직 아무도 안 쓰는 비트를 하나 받는다. 그 자리를 만드는 식이
레거시에서는 `int` 다.

```java
if ((permission & 1) == 0) { result = 1 << i; i = 64; }   // 1 은 int 다
```

`i` 가 31이면 `1 << 31` 은 `Integer.MIN_VALUE` 이고, `long` 으로 넓히면 **비트 31~63 이
전부 켜진다.** 그 안에 관리자 비트가 있다. 32번째는 `1 << 32` 가 `1` 로 돌아가 첫
부서와 같은 비트를 받는다.

자바 셈법 그대로 흉내 내 확인했다.

| 이미 찬 비트 | 레거시 결과 | 뜻 |
|---|---|---|
| 0~7 (지금 데이터) | `256` | 정상 |
| 0~30 | `-2147483648` | **새 부서가 관리자가 된다** |
| 0~31 | `1` | **첫 부서의 권한을 물려받는다** |

**결정:** `1L << i` 로 고친다(`Levels.next`).

레거시가 정답이라는 원칙의 예외다. 근거는 셋이다. **첫째,** 지금 데이터로는 닿지
않는다 — 부서 8개, 직급 9개이고 23개를 더 만들어야 터진다. 즉 «지금 화면에 보이는
것»은 달라지지 않는다. **둘째,** 재현하면 새 부서가 관리자가 된다. 없던 구멍을 그대로
옮기는 것은 이관이 아니다(D-013·D-028과 같은 판단). **셋째,** 게이트도 실화면 대조도
이 자리를 볼 수 없다.

`LevelsTest` 가 31·32번째 자리를 못 박아 둔다.

## D-061 · 부서·직급 만들기를 한 트랜잭션으로 묶는다

레거시는 표를 만들고(`dept_tbl`) 권한 행을 따로 만든다(`permission_dept_tbl`).
트랜잭션이 없어 사이에서 끊기면 **권한 행이 없는 부서**가 남는다. 그 부서에 속한
사람은 권한 조회가 0이라 아무 화면도 보지 못하는데, 화면에는 부서가 멀쩡히 보인다.

**결정:** 한 트랜잭션으로 묶는다(D-043·D-051과 같은 판단). 정상 흐름에서 보이는 것은
달라지지 않는다.

## D-062 · 지운 부서의 비트는 남는다 — 다음 부서가 물려받는다

부서를 지우면 그 부서의 권한 행만 사라진다. **다른 부서의 `permission` 과 프로그램의
`dept_level` 에는 그 비트가 그대로 남는다.** 나중에 새 부서를 만들면 빈 자리를 찾는
규칙이 그 비트를 다시 주므로, 새 부서가 사라진 부서의 권한을 그대로 물려받는다.

걷어내는 코드가 레거시에 있긴 하다(`revokePermission`). **어느 화면도 부르지 않는다.**
게다가 그 SQL 은 비트 연산을 DB 에서 한다 — 관리자 비트가 걸리면 뒤집히는 자리다.

**결정:** 그대로 옮긴다. 걷어내지 않고, 부르는 곳 없는 코드도 옮기지 않는다.

D-060 과 갈린 이유를 적어 둔다. 그쪽은 **지금 데이터로 도달할 수 없는 자리**이고 고치면
동작이 달라지지 않는다. 이쪽은 **지금도 일어나는 일**이라 고치면 화면에 보이는 권한이
달라진다. 이관 중에 바꿀 수 있는 것은 앞의 것뿐이다.

**2단계 후보.** 지울 때 다른 행에서 그 비트를 걷어내면 된다 — 계산은 Java 에서.


> **2단계에서 해소했다(D-109).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-063 · 프로그램 권한은 레거시 표에서 읽고 쓴다 — 생성물에 두지 않는다

이관하며 만든 `program` 표에 권한 값을 복사해 두었다. 화면 권한 판정이 그것을 읽는다.

```
레거시   permission_program_tbl.dept_level   <- 관리자 화면이 고치는 곳
신규     program.dept_level                  <- 판정이 읽던 곳 (seed 생성물)
```

프로그램 권한 수정 화면을 붙이려니 둘 중 하나가 된다.

- 레거시 표에 쓰면 → **«수정했습니다» 라고 하고 아무것도 안 바뀐다**
- 생성물에 쓰면 → seed 를 다시 적용하는 순간 관리자가 바꾼 값이 통째로 사라진다
  (`V2__layout_and_permission.sql` 은 세 표를 `DROP` 하고 다시 만든다)

**결정:** 판정도 편집도 `permission_program_tbl` 을 본다. `program` 표에서 권한 두 칸을
뺀다 — 이름표와 FK 대상만 남는다.

근거 셋.

**첫째, 나머지 권한은 이미 그렇다.** 부서·직급은 `permission_dept_tbl`·
`permission_job_tbl` 을 직접 읽고(로그인) 이제 직접 쓴다(③a). 게시판은
`board_tbl.permission_*_level` 을 직접 읽는다. **프로그램만 사본이었다.**

**둘째, 생성물의 뜻이 그렇다.** `program` 은 «어느 경로가 어느 프로그램인가» 를 담는
표이고 그것은 레거시 JSP 를 훑어 만든 이관 산출물이다. 반면 권한 값은 운영 중에
바뀌는 데이터다. 둘을 한 표에 담은 것이 애초에 어긋난 것이고, 빼면 `program` 은 다시
«다시 만들어도 잃을 것이 없는» 생성물이 된다.

**셋째, 지금 바꿔도 달라지는 것이 없다.** 그 두 칸을 읽는 곳은 `findScreenAccess`
한 곳뿐이고, 두 표의 20개 값이 지금 전부 같다(확인했다).

**한 가지 조심할 것.** 권한 행이 없으면 `COALESCE(..., 0)` 으로 0이 되어 **아무도 못
들어간다.** 조인을 그냥 비우면 «권한 대상이 아닌 경로» 와 구별되지 않아 모두에게
열린다 — 잠기는 쪽이 옳다.

## D-066 · 문서 양식 «보기» 는 어느 줄을 눌러도 첫 줄이 뜬다

목록의 줄마다 모달이 하나씩 생기는데 **id 가 전부 같다.**

```jsp
for (TemplateBean bean : vlist) {
...
    <button data-bs-toggle="modal" data-bs-target="#calendar-plus">보기</button>
    <div class="modal fade" id="calendar-plus"> ... <%=content%> ... </div>
```

부트스트랩은 `#calendar-plus` 로 찾은 **첫 요소**를 연다. 양식이 다섯이면 모달도
다섯인데 전부 같은 이름이라, 셋째 줄의 «보기» 를 눌러도 첫 줄의 양식이 보인다.

**결정:** 그대로 옮긴다. id 를 줄마다 다르게 하면 «고쳐지지만» 화면 동작이 달라진다.
문서 번호를 눌러 수정 화면으로 가면 그 줄의 양식이 제대로 나오므로, 내용을 확인할
길이 아예 없는 것은 아니다.

**게이트는 못 본다** — 모달도 버튼도 양쪽에 다 있고, 다른 것은 어느 것이 열리느냐다.

## D-067 · 게시글 페이징이 게시판 페이지 번호를 따라간다

게시판 관리 화면은 표가 둘이고 페이징도 둘이다. 그런데 오른쪽(게시글) 페이징의 블록을
왼쪽 변수로 계산한다.

```jsp
nowBlock = (int)Math.ceil(1.0 * nowBoard / pagePerBlock);   // nowPage 가 아니다
start = (nowPage - 1) * numPerPage;
```

목록을 가져올 때는 `nowPage` 를 쓰므로 <b>표는 맞게 나오는데</b>, 그 아래 페이지 번호는
왼쪽 게시판 목록의 페이지에서 나온다. 왼쪽을 2페이지로 넘기면 오른쪽 번호가 6부터
시작한다.

**결정:** 그대로 옮긴다. 게시글 쪽 페이징을 «블록» 과 «현재 페이지» 두 벌로 나눠
계산해서, 블록은 `nowBoard` 로 현재 페이지는 `nowPage` 로 만든다 — 레거시와 같은 숫자가
그려진다.

게시판이 4개뿐이라 왼쪽은 언제나 1페이지이고, 그래서 지금 화면에서는 드러나지 않는다.

## D-068 · 같은 근무 상태를 두 자리가 다르게 부른다

관리자 대시보드는 근무 상태를 두 곳에 찍는다. 이름표 배열이 두 곳에 따로 있고, 하나가
어긋나 있다.

```java
// admin.jsp — 출퇴근 표
final String[] workStatus = { "결근", "근무 중", "퇴근", "조퇴", "지각", "반차", "연차" };

// adminGraph.js — 근무 현황 그래프
const keys = ['결근','출근', '퇴근', '지각', '조퇴', '반차', '연차']
```

코드 1 이 표에서는 «근무 중», 그래프에서는 «출근» 이다. **게다가 그래프 쪽은 3·4가
서로 바뀌어 있다** — 표는 3 조퇴 / 4 지각인데 그래프는 3 지각 / 4 조퇴로 읽는다.

**결정:** 그대로 옮긴다. 두 배열을 {@code WorkStatus} 한 클래스에 나란히 두되 값은
손대지 않는다 — 어느 쪽이 «맞는» 이름인지 정할 근거가 없고, 화면에 보이는 글자가
달라진다.

라벨을 한 벌로 합치는 것은 2단계 안건이다. 합칠 때는 근무 상태 코드의 뜻을 사람에게
물어야 한다.

## D-069 · 근무 현황 그래프는 없는 상태가 있으면 이름이 밀린다

그래프 값은 «상태 코드 → 인원» 이다. 서버가 <b>그날 있는 상태만</b> 담아 보낸다.

```java
for (ViewWorkBean work : works) { values.put(status, ...); }   // 없는 상태는 아예 없다
```

화면 쪽은 받은 것을 순서대로 배열에 쌓은 뒤, 이름표를 0번부터 따로 붙인다.

```js
$.each(rows, function(key, value) { names.push(`${keys[key]} ${value}명`) });
for (let i = 0; i < keys.length; ++i) { dataset.push({ name: names[i], value: values[i] }); }
```

받은 값이 일곱 개보다 적으면 뒤쪽 조각이 {@code undefined} 가 되고, 조각 이름과 값이
어긋난다. 그날 아무도 결근하지 않으면 그렇게 된다.

**결정:** 그대로 옮긴다. 서버는 레거시와 같은 모양의 값을 돌려준다 — 코드 오름차순으로
고정한 것만 다르다(레거시는 `HashMap` 을 그대로 직렬화해 순서를 우연에 맡겼다).

고치려면 없는 상태를 0으로 채워 일곱 개를 늘 보내면 된다. 그러면 조각 하나가 더
그려지므로 화면이 달라진다 — 2단계 안건이다.

`productRegisterProc.jsp` 와 `productUpdateProc.jsp` 의 첫머리다.

//UserBean user = WebHelper.getValidUser(session);

//if (user == null) {

서로 다른 프로그램이다) 정작 값을 바꾸는 처리에는 아무 검사가 없다. 주소만 알면

## D-071 · 제품을 고치면 없는 화면으로 간다

## D-072 · 공정을 하나만 등록할 수 없다

공정 등록은 화면의 표를 통째로 JSON 으로 보내고, 서버가 순서대로 앞뒤 고리를 채운다.

```java
for (int i = 1; i < jsonArray.size(); i++) {
    if (i == 1) {
        JsonObject jsonNextObject = jsonArray.get(i + 1).getAsJsonObject();   // 다음이 없으면?
```

첫 공정이면 <b>무조건</b> 다음 공정을 찾는다. 표에 줄이 하나뿐이면 배열 밖을 읽어 그
자리에서 죽는다 — 500 이 뜨고 아무것도 저장되지 않는다.

(반복이 1부터 시작하는 것은 정상이다. 화면이 표의 머리글 행까지 담아 보내기 때문에

**결정:** 죽음은 옮기지 않는다. 줄이 둘 미만이면 실패로 돌려주고, 화면은 레거시와 같은
«이벤트 추가에 실패했습니다» 를 받는다(그 문구도 레거시 그대로다 — 일정 등록 서블릿을
복사한 흔적이다).

공정 하나짜리를 만들 수 있게 하는 것은 <b>없던 기능을 만드는 것</b>이라 하지 않는다.
D-033(이미 본 글을 다시 열면 죽는다)과 같은 판단이다.

## D-073 · 공정 삭제는 볼 수 없는 저장 프로시저에 기댄다

```java
String sql = "{call DeleteProcess(?)}";
```

공정 삭제만 SQL 이 아니라 <b>저장 프로시저</b>다. 지우면서 앞뒤 고리를 다시 잇는 것으로
보이지만 <b>그 안을 볼 수 없다.</b>

- 복제한 스키마(`erflow_mig`)에 그 프로시저가 없다. 복제 도구가 표와 뷰만 옮긴다
- 우리 계정으로는 루틴을 조회할 수 없다(`information_schema.ROUTINES` 가 비어 있다)

**결정:** 호출을 그대로 옮긴다. 지어내지 않는다.

프로시저가 없으면 예외가 나고 «선택한 내역을 삭제하지 못했습니다» 가 뜬다 — 레거시도
예외를 삼키고 실패를 돌려주므로 <b>같은 화면</b>이다. 프로시저가 생기면 양쪽이 함께
동작한다.

로직을 짐작해 SQL 로 옮기는 쪽은 고르지 않았다. 고리를 어떻게 다시 잇는지(앞을 뒤에
잇는지, 우선순위를 다시 매기는지) 근거가 없고, 틀리면 **사슬이 조용히 끊긴다.**

**사람이 확인할 것:** 운영 DB 에 `DeleteProcess` 가 있는지, 있다면 그 정의(O-013).

## D-074 · 공정 검색은 페이지를 넘기면 풀린다

목록의 숨은 폼이 검색어 자리를 비운 채로 그려진다.

```jsp
<input type="hidden" name="keyfield" value="">
<input type="hidden" name="keyword" value="">
```

다른 목록 화면은 이 자리에 지금 검색어를 넣어 둔다. 공정만 비어 있어서, 검색한 뒤
2페이지를 누르면 <b>조건 없는 1페이지</b>가 아니라 조건 없는 2페이지가 나온다.

**결정:** 그대로 옮긴다. 값을 채우면 «고쳐지지만» 화면 동작이 달라진다.

공정 데이터가 한 건도 없어 지금은 드러나지 않는다.

## D-075 · 결재에 올라간 문서는 고치지 않고 새로 만든다

문서 수정 처리가 갈래를 하나 더 갖는다.

```jsp
case "update":
    if (activityCon.hasProposal(docId)) {
        paramFlag = "renew";
        result = activityCon.createDocument(session, bean);   // 새로 만든다
    } else {
        result = activityCon.updateDocument(session, bean);   // 그 자리에서 고친다
    }
```

이미 결재에 올라간 문서를 고치면 <b>원본은 그대로 두고 새 문서를 만든다.</b> 화면에는
«이미 결재 진행된 문서이므로, 문서를 새로 등록합니다» 가 뜬다.

삭제도 같은 원칙이다 — 결재에 걸린 문서는 지우지 않고, 하나라도 걸리면 «결재 진행 중인
항목 외의 문서를 삭제하였습니다» 라고 알린다.

**결정:** 그대로 옮긴다. 결재선이 본 내용이 나중에 달라지면 결재 자체가 뜻을 잃기
때문이며, 레거시가 <b>일부러</b> 그렇게 갈랐다고 보는 것이 옳다(문구까지 따로 두었다).

이 규칙은 게이트가 못 본다 — 화면은 같고 달라지는 것은 저장되는 자리다. 시험으로
박아 뒀다(`DocumentScreenTest`).

## D-076 · 양식을 고르면 쓰던 글이 사라진다

작성 화면에서 양식을 고르면 화면이 다시 열리고, 그 양식의 내용이 편집기를 <b>덮는다.</b>

```jsp
if (isChecked) {
    content = template.getContent();   // 쓰던 내용을 버린다
}
```

그리므로 편집기의 실행 취소도 비어 있다).

**결정:** 그대로 옮긴다. «덮기 전에 물어본다» 는 없던 동작을 만드는 것이고, 덮지 않으면
양식을 고르는 뜻이 없어진다.

**2단계 후보.** 고친다면 «내용이 비어 있을 때만 덮는다» 가 가장 작은 변경이다.

## D-081 · 속성을 통째로 찍는 표현식이 태그 이름을 먹고 있었다

근태 달력은 날짜 머리글의 요일 색을 이렇게 넣는다.

```jsp
<th<%=isSunday ? " style=\"color: red;\"" : (isSaturday ? " style=\"color: blue;\"" : "")%>>
    <%=String.format("%02d", i)%>
</th>
```

표현식이 <b>값이 아니라 속성 자체</b>를 찍는다. 전처리는 이것을 다른 표현식과 똑같이
자리표시자로 바꿨고, 그래서 `<th«dyn»>` 이 되었다. 파서에게 이것은 `th` 가 아니라
`th«dyn»` 이라는 처음 보는 태그다. 뒤따르는 `</th>` 는 짝을 못 찾아 버려지고, 그
노드는 열린 채로 남아 뒤의 형제 요소들을 안으로 빨아들인다.

결과는 <b>정답에서 날짜 머리글이 통째로 빠지는 것</b>이다. 게이트는 조용히 통과했다 —
없는 것을 견주지 않았으니 다를 수도 없다.

**결정:** 태그 이름을 지킨다. 여는 태그 이름에 바로 붙은 표현식은 지우고 그 자리에
`data-dyn-attr="«dyn»"` 을 놓는다. «속성이 하나 붙는다» 는 사실만 남기고 무엇이
붙는지는 묻지 않는다 — 그것은 스타일이고, 스타일은 애초에 대조 대상이 아니다.

따옴표 <b>안</b>의 표현식은 건드리지 않는다. `href="profile.jsp?id=<%=id%>"` 는 값이고,
속성 자리로 오해하면 링크 대상이 통째로 사라진다. 그래서 규칙을 «태그 이름에 붙어
있을 때» 로 좁혔다. 레거시 전체에서 이 모양은 여섯 군데, 전부 근태 달력 두 화면이다.

`EXTRACTOR_VERSION` 을 7 -> 8 로 올렸다. 정답 83건을 다시 뽑았고 <b>signature 는 한 건도
바뀌지 않았다</b> — 이 모양이 없던 화면들은 영향이 없다. 프로필의 정답은 36건에서
38건으로 늘었다(날짜 머리글 둘).

**이것이 네 번째다.** D-008 은 정답 생성기가 원본의 일부만 읽어서, 날짜 형식(D-020)은
값이 동적이라서, D-022 는 추출기의 대상 목록에 구멍이 있어서, 이번은 전처리가 태그를
망가뜨려서. <b>네 번 다 게이트가 아니라 사람이 원본을 읽다가 찾았다.</b> 게이트는
"정답 대비 다른가" 만 본다 — 정답이 원본의 일부만 보고 있으면 할 말이 없다.

`TestAttributeEmittingExpression` 이 네 성질을 못으로 박는다. 태그 이름이 살아남는지,
닫는 태그가 다시 짝을 찾는지, 신규의 `th:style` 과 같은 signature 를 내는지, 따옴표
안의 표현식은 그대로인지.

## D-077 · 근무 현황 통계가 줄마다 따로 세어진다

프로필 아래 «이번 달 근무 현황» 은 한 달을 두 줄로 그린다 — 1~16일, 17일~말일.
오른쪽 끝에 «정상·지각·조퇴·연차» 네 칸이 붙어 있는데, 이 숫자는 <b>그 줄만의
합계</b>다. 두 줄을 그리는 사이에 카운터를 0으로 되돌리기 때문이다.

```jsp
<%-- 윗줄을 그리고 나서 --%>
normalCount = 0;
lateCount = 0;
leaveCount = 0;
vacationCount = 0f;
<%-- 아랫줄을 그린다 --%>
```

그래서 <b>한 달 합계는 화면 어디에도 없다.</b> 윗줄 숫자와 아랫줄 숫자를 눈으로
더해야 한다. 두 줄에 같은 이름의 칸이 나란히 있어 합계로 보이지만 아니다.

같은 표에 어긋난 것이 하나 더 있다. 윗줄 머리글의 «통계» 는 `colspan="5"` 인데 실제
통계 칸은 넷이라, 두 줄의 칸 수가 하나 어긋난다.

**결정:** 그대로 옮긴다. 합계를 더해 보이는 것은 화면에 없던 숫자를 만드는 일이다.
셈을 `WorkCalendar` 한 곳에 모아 두고 시험으로 박았다(`WorkCalendarTest`).

주말 취급도 상태마다 다르다. 결근·지각·반차는 토·일이면 색도 칠하지 않고 세지도
않는데, <b>연차만 요일을 보지 않는다</b> — 그 자리에만 검사가 빠져 있다. 이것도
그대로 옮겼고 시험이 두 상태를 나란히 놓고 확인한다.

**2단계 후보.** 표를 한 줄로 펴고 합계를 한 번만 낸다.

## D-078 · 프로필 수정은 세션 사본이 아니라 DB 를 본다

레거시는 로그인할 때 `user_tbl` 한 행을 통째로 읽어 세션에 담아 두고, 프로필 수정
화면이 <b>그 사본</b>을 채워 넣었다. 저장도 그 사본에 값을 얹어 통째로 덮어썼다.

```jsp
UserBean user = WebHelper.getValidUser(session);   // 로그인 때 뜬 사본
user.setName(...); user.setEmail(...);
userCon.updateUser(session, user);
```

```sql
update user_tbl set name = ?, email = ?, postal_code = ?,
    address1 = ?, address2 = ?, job_tbl_id = ?, dept_tbl_id = ?,
    extension_phone = ?, mobile_phone = ? where id = ?
```

직급·부서·내선 전화는 <b>이 화면에 없다.</b> 그런데도 저장 문에 들어간다 — 세션이
들고 있던 로그인 시점의 값으로. 관리자가 그 사이에 부서를 옮겨 두었다면, 사원이
프로필을 저장하는 순간 그 인사 이동이 되돌아간다.

**결정:** 화면이 보낸 여섯 칸만 고치고, 화면을 채울 값은 <b>그때마다 DB 에서 읽는다.</b>

레거시 동작과 달라지는 자리는 하나다 — 로그인한 뒤 남이 내 정보를 고쳤을 때. 레거시는
낡은 사본을 되돌려 놓고, 여기서는 남이 고친 값이 남는다. 되돌리는 쪽을 재현할 이유가
없다. 그것은 «세션에 사본을 들고 있었다» 는 구현의 부작용이지 화면의 동작이 아니고,
Spring Security 의 인증 주체는 애초에 프로필 값을 들고 있지 않다.

곁가지로 좋아진 것 하나. 레거시는 로그인 때 주민번호를 지우고 세션에 담았고
(`user.setSocialNumber(null)`), 그래서 수정 화면의 «주민 번호» 칸은 언제나 비어
있었다. 여기서는 그 값을 <b>읽지도 않는다</b> — 화면에 없는 값을 서버가 들고 있을
이유가 없다. 사원 리스트 쪽 노출은 별개 안건이다(O-012).

## D-079 · 비밀번호 재확인은 문이 아니다 — 수정 화면은 그냥 열린다

프로필의 «Edit» 은 비밀번호를 다시 묻는 화면으로 간다. 맞으면 수정 화면으로 보낸다.

```jsp
if (result) {
    nextPage = "profileUpdate.jsp";
}
```

그런데 `profileUpdate.jsp` 는 <b>로그인만 확인한다.</b> 확인을 통과했는지 묻지 않으므로
주소를 직접 치면 그냥 열린다. 확인 화면은 길목에 놓여 있을 뿐 문이 아니다.

그 확인 화면 자체도 성한 데가 없다. 버튼이 하나뿐이고 그 하나가 «이전페이지» 인데,
form 안에 있어 type 이 `submit` 이고 안에 링크가 들어 있다 — 누르면 제출과 이동이
동시에 일어난다. 확인 버튼은 아예 없어서 비밀번호 칸에서 엔터를 쳐야 제출된다.

**결정:** 그대로 옮긴다. 확인을 진짜 문으로 만들면 «주소를 치면 열리던 화면이 안
열린다» 가 되어 동작이 바뀐다.

이것은 게이트가 못 보는 자리다 — 화면 두 개는 그대로이고 달라지는 것은 사이의 관문
유무다. 시험으로 박아 뒀다(`ProfileScreenTest`).

**2단계 후보.** 확인에 성공하면 짧은 표를 세션에 두고, 수정 화면이 그 표를 요구한다.


> **2단계에서 해소했다(D-111).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-080 · 프로필을 저장하면 전화번호가 지워진다

수정 화면이 값을 여섯 개 채우는데, 그중 «개인 번호» 만 채우지 않는다.

```jsp
String mobilePhone = Optional.ofNullable(user.getMobilePhone()).orElse("");
...
<input type="text" id="" name="mobilePhone" placeholder="휴대전화" value="">
```

값을 꺼내 두고 <b>쓰지 않았다.</b> `value` 는 빈 글자로 박혀 있다. 저장 처리는 그 빈
칸을 그대로 받아 적으므로, 이 화면을 한 번 열어 저장하면 전화번호가 사라진다. 다시
넣으려면 직접 쳐 넣는 수밖에 없고, 다음에 또 저장하면 또 지워진다.

옆의 `id=""` 와 짝 없는 `<label for="input7">` 을 보면 손이 덜 간 자리로 보인다.

같은 처리에 어긋난 것이 하나 더 있다. 여섯 칸을 다듬어(`trim`, 빈 값은 `null`) 담아
놓고, <b>우편번호와 개인 전화만 다듬지 않은 원본을 다시 꺼내 쓴다.</b>

```jsp
user.setName(parameters.get("name"));                       // 다듬은 값
user.setPostalCode(request.getParameter("postalCode"));     // 원본
user.setMobilePhone(request.getParameter("mobilePhone"));   // 원본
```

그래서 이름을 공백만 넣으면 `null` 이 되지만 우편번호는 공백이 그대로 남는다.

**결정:** 그대로 옮긴다. 화면에 <b>빈 칸이 보이는 것</b>이 사실이고, 거기에 값을 채우면
화면에 없던 글자를 만드는 일이다. 게이트는 이 자리를 보지 못한다 — 편집 가능한 입력의
`value` 는 라벨이 아니라 데이터라서 대조 대상이 아니다(D-034). 시험으로 박았다.

**2단계 후보.** `value` 를 채운다. 한 글자 고치면 되는 일이고, 고치는 순간 «저장하면
지워진다» 가 사라진다. 다만 그때는 지워져 있던 55명의 전화번호가 돌아오지 않는다 —
데이터 복구는 별개다.


> **2단계에서 해소했다(D-100).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-082 · 나란히 놓인 두 게시판 위젯이 다르게 자른다

메인 화면의 «공지사항» 과 «자유게시판» 은 같은 표다. 그런데 글자를 자르는 규칙이 다르다.

```jsp
<%-- 공지사항 --%>
if (subject.length() > 10) { subject = subject.substring(0, 10) + "..."; }

<%-- 자유게시판 --%>
if (subject.length() > 10) { subject = subject.substring(0, 10) + "..."; }
if (name.length() > 3)     { name = name.substring(0, 3) + "..."; }
```

자유게시판만 <b>작성자 이름까지</b> 세 글자에서 자른다. 두 위젯이 화면에 나란히 있어
같은 사람의 이름이 위에서는 «홍길동», 아래에서는 «홍길동...» 으로 보인다.

세 글자에서 자르는 것도 어중간하다. 한국 이름은 대개 세 글자라 <b>네 글자 이름만</b>
잘리는데, 잘린 결과가 원래 이름보다 길다(«남궁민수» -> «남궁민...»).

**결정:** 그대로 옮긴다. 자르는 일은 위젯을 만드는 자리에서 하고 줄(record)에는 두지
않았다 — 몇 글자에서 자르는가는 줄의 성질이 아니라 그 자리의 성질이다.

게이트는 못 본다. 잘린 글자는 서버가 채우는 값이라 «dyn» 이다. 시험으로 박았다.

## D-083 · 일정 고치기는 주인을 보지 않는다

달력의 일정은 만들기·고치기·지우기가 모두 JSON 창구로 간다. 셋 다 «보낸 사번이
로그인한 사번과 같은가» 를 먼저 보므로 남을 사칭할 수는 없다. 그런데 그 다음이 다르다.

```sql
-- 지우기: 주인까지 본다
delete from calendar_tbl where id = ? and user_tbl_id = ?

-- 고치기: 번호만 본다
update calendar_tbl set subject = ?, ... where id = ?
```

<b>고치는 문에는 주인 조건이 없다.</b> 자기 사번을 실어 보내면서 남의 일정 번호를
적으면 그 일정이 고쳐진다. 지우는 것은 막히는데 고치는 것은 막히지 않는다.

일정 번호는 달력에 그려진 일정을 눌러 보면 화면에 그대로 뜬다. 부서·전체 일정은
남에게도 보이므로 번호를 알아내는 데 아무 수고가 들지 않는다.

**결정:** 그대로 옮긴다. 조건을 하나 더 붙이는 것은 한 줄이지만, 그 한 줄이 «되던
것이 안 되는» 변화다. 결함으로 적어 두고 시험으로 못 박았다 — 남의 일정을 고쳐 놓고
주인이 그대로인 것까지 확인한다.

**2단계 후보.** `and user_tbl_id = ?` 를 붙인다. 지우기와 같은 모양이 된다.


> **2단계에서 해소했다(D-101).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-084 · 메인 화면은 권한을 묻지 않는다

메인 화면의 위젯 넷은 공지사항·전자결재·자유게시판·받은 쪽지함이다. 넷 다 각자
프로그램 권한이 걸린 화면인데, <b>메인은 로그인만 확인한다.</b>

```jsp
if (!WebHelper.isLogin(session)) {
    response.sendRedirect("permissionError.jsp");
    return;
}
```

그래서 게시판을 볼 권한이 없는 사람도 메인에서는 공지사항 제목과 작성자를 본다.
제목을 누르면 그때야 권한 화면으로 튕긴다 — 목록은 이미 보여 준 뒤다.

**결정:** 그대로 옮긴다. `screen` 표에 `/index` 행이 없으므로 이관 구조에서도 자연히
같은 동작이 된다(행이 없는 경로는 로그인만 본다). 일부러 맞춘 것이 아니라 <b>맞춰
두었더니 같아진</b> 자리다.

**2단계 후보였다가 종결했다(D-115).** 위젯마다 권한을 보는 안(빈 위젯 또는 제거)은
사람마다 메인이 달라 보이는 문제가 있어, 레거시대로 «메인은 보이고 누르면 문에서
막힌다» 를 유지하기로 정했다(2026-08-21, 사용자 판단).

## D-085 · 위젯 머리의 아이콘 셋 중 둘은 동작하지 않는다

위젯마다 오른쪽 위에 아이콘이 셋 있다 — 새 창, 새로고침, 추가.

```html
<a href="post/postList.jsp?boardId=1"><i class="fa-arrow-up-right-from-square"></i></a>
<a href=""><i class="fa-arrows-rotate"></i></a>
<a href=""><i class="fa-plus"></i></a>
```

뒤의 둘은 `href=""` 다. 브라우저는 빈 `href` 를 «지금 주소» 로 읽으므로 새로고침처럼
보이기는 한다 — 새로고침 아이콘은 우연히 뜻이 맞는 셈이다. 추가 아이콘은 아니다.

달력 위젯은 한술 더 뜬다.

```html
<a href="http://localhost:5501/index.html"><i class="fa-arrows-rotate"></i></a>
```

<b>만든 사람 PC 의 주소가 그대로 남아 있다.</b> 다른 데서 누르면 아무 데도 가지 않는다.

**결정:** 그대로 옮긴다. 지우면 화면에서 아이콘이 사라지고, 주소를 고치면 «어디로
가야 하는가» 를 우리가 지어내는 것이 된다. 눌러도 아무 일이 없는 것이 지금의 화면이다.

게이트는 이 차이를 본다 — 링크의 대상이 `detail` 이라 빈 것과 채운 것이 구별된다.
그래서 빈 채로 두어야 통과한다.

**2단계 후보.** 달력 위젯의 개발자 PC 주소만이라도 지운다. 이것은 «되던 것이 안
되는» 변화가 아니라 애초에 되지 않던 것이다.


> **2단계에서 해소했다(D-114).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-086 · JSON 을 보내는 ajax 는 form 이 아니라 토큰이 붙지 않는다

CSRF 방어를 켜면서(D-013) form 은 Thymeleaf 가 hidden 입력을 알아서 넣어 준다.
그런데 <b>ajax 로 JSON 을 보내는 자리는 form 이 아니다.</b> 토큰이 붙지 않고 서버는
403 으로 되돌린다. 화면은 «오류가 발생했습니다» 만 띄우므로 무엇이 막혔는지도 모른다.

이 프로젝트에 그런 자리가 둘 있다.

| 화면 | 창구 |
|---|---|
| 메인 달력 | `/calendar/insert` · `/calendar/update` · `/calendar/delete` |
| 공정 등록 | `/process/processRegister` |

공정 등록은 <b>이미 그 상태였다.</b> 시험이 서비스 계층을 직접 불러서 통과했고, 창구를
지나가는 시험이 없어 드러나지 않았다. 달력을 붙이며 같은 구멍을 밟고서야 보였다.

**결정:** 토큰을 `<meta>` 로 내려보내고 `js/common/csrf.js` 가 모든 ajax 에 헤더로 붙인다.
GET 에는 붙이지 않는다 — 서버도 그쪽은 검사하지 않는다.

`<meta>` 는 화면에 보이는 요소가 아니므로 정합성 게이트에 영향이 없다(추출기가
`meta` 를 아예 건너뛴다). 레거시에 없던 요소를 화면에 더하지 않고 문제를 닫는다.

시험이 이 장치가 <b>정말 필요한지</b> 를 못 박는다. 토큰 없이 보내면 403, 실어 보내면
200 이다. 장치를 지우면 시험이 먼저 깨진다.

## D-087 · 최상위 화면 셋이 로그인하지 않은 사람을 404 로 보낸다

레거시는 로그인하지 않은 사람을 안내 화면으로 보낸다. 그런데 **웹앱 최상위에 있는**
화면 셋이 한 칸 위로 보낸다.

```jsp
response.sendRedirect("../permissionError.jsp");
```

`/ERFlow/passwordCheck.jsp` 에서 `../` 는 `/permissionError.jsp` 다 — 컨텍스트 밖이라
그런 주소는 없다. **안내 화면 대신 톰캣 404 가 뜬다.**

띄워 놓고 실제로 받아 확인했다.

| 화면 | 보내는 곳 | 결과 |
|---|---|---|
| `passwordCheck.jsp` | `../permissionError.jsp` | 404 |
| `findProposalRoute.jsp` | `../permissionError.jsp` | 404 |
| `profile.jsp` (읽을 수 없는 달) | `../accessError.jsp` | 404 |

하위 폴더에 있는 화면들은 같은 글자가 맞는 주소가 된다(`/ERFlow/post/postList.jsp`
에서 `../` 는 `/ERFlow/`). 그래서 폴더를 옮기며 딸려 온 오타로 보인다.

**결정:** <b>재현하지 않는다.</b> 신규는 셋 다 제대로 된 안내 화면으로 보낸다
(`/permission-error`, `/access-error`).

이관 원칙은 «화면에 보이는 것을 더하거나 빼지 않는다» 이지 «깨진 주소를 똑같이 깨뜨린다»
가 아니다. 레거시도 <b>안내 화면을 보여 주려 했고</b>, 셋을 뺀 나머지 서른 몇 화면이
그렇게 동작한다. 404 는 의도가 아니라 오타의 결과다.

게이트에는 걸리지 않는다 — 안내 화면 자체는 양쪽에 있고, 어디로 보내는가는 화면
요소가 아니다.

## D-088 · 레거시는 날짜를 화면이 아니라 ResultSet 에서 바꿨다

관리자 게시판 관리 화면의 작성날짜가 «2023-11-10T03:16:39» 로 나왔다. 가운데 `T` 는
`LocalDateTime.toString()` 이다. 레거시는 «2023-11-10 03:16:39» 다.

그것을 고치려고 레거시 JSP 를 열어 보니 형식을 맞추는 코드가 없었다. 그냥
`<%=createdAt%>` 다. 그런데 화면에는 «2023년 09월 21일» 처럼 한글 날짜가 뜨는 자리도
있다. 어디서 바뀌는지 화면만 읽어서는 알 수 없었다.

`ResultSetExtractHelper` 안에 있었다.

```java
extractTaskBean       WebHelper.getDate(rs.getString("created_at"))
extractViewtTaskBean  WebHelper.getDate(rs.getString("created_at"))
extractUserViewBean   WebHelper.getDate(rs.getString("hired_at"))
```

`WebHelper.getDate` 가 «yyyy년 MM월 dd일» 로 바꾼다. **DB 를 읽는 자리에서** 바꾸므로
그 Bean 을 쓰는 모든 화면이 한글 날짜를 보게 된다. 화면 코드에는 흔적이 없다.

**결정:** 같은 세 자리를 맞춘다. 형식은 `common/LegacyDates` 한 곳에 모았다 — 흩어
두면 또 어긋난다. 이미 D-026 이 «같은 앱 안에서 형식이 화면마다 다르다» 를 적어
두었고, 그 목록에 이 셋이 더해지는 셈이다.

| 자리 | 레거시 | 고치기 전 |
|---|---|---|
| 관리자 게시판 관리 · 작성날짜 | `2023-11-10 03:16:39` | `2023-11-10T03:16:39` |
| 대시보드 · 공지 작성일 | `2023-11-10 03:16:39` | `2023-11-10T03:16:39` |
| 대시보드 · 수·발주 요청일 | `2023년 09월 21일` | `2023-09-21 10:15:14` |
| 사원 리스트 · 입사일 | `2004년 10월 01일` | `2004-10-01 09:00:00` |

**게이트는 넷 다 통과시켰다.** 날짜 자리는 서버가 채우므로 «dyn» 이고, 형식은 보이지
않는다. 실화면 대조(D-020)가 아니면 잡을 방법이 없다 — 그리고 실제로 그렇게 잡혔다.

## D-089 · 문서가 없는 수·발주는 «null» 이라는 글자를 찍는다

수·발주 목록의 «문서» 칸이다.

```jsp
String subject = task.getSubject();
...
<td><%=subject%></td>
```

문서가 딸리지 않은 수·발주가 있다. 그때 `subject` 가 `null` 이고, `<%= %>` 는 그것을
«null» 이라는 네 글자로 찍는다. 빈칸이 아니라 글자다.

**결정:** 그대로 옮긴다. 화면에 그 네 글자가 보이는 것이 사실이고, 빈칸으로 바꾸면
화면에 있던 것이 사라진다. 처음에는 빈칸으로 옮겼다가 실화면 대조에서 걸렸다.

게이트는 못 본다 — 그 칸의 내용은 «dyn» 이다.

**2단계 후보.** 빈칸으로 바꾼다. 문서가 없는 것이 정상 상태라면 «-» 가 낫다.


> **2단계에서 해소했다(D-112).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-090 · 이미 로그인한 사람은 로그인 화면을 보지 못한다

레거시 `login.jsp` 첫 줄이 이렇다.

```jsp
UserBean user = WebHelper.getValidUser(session);

if (user != null) {
    if (permissionCon.isAdmin(session)) {
        response.sendRedirect("../admin/admin.jsp");
    } else {
        response.sendRedirect("../index.jsp");
    }
}
```

로그인한 채로 주소를 치면 되돌아간다 — 관리자는 관리자 화면으로, 나머지는 메인으로.

(`return` 이 없어서 리다이렉트를 보낸 뒤에도 로그인 화면 본문을 계속 찍는다.
브라우저는 헤더를 먼저 보고 옮겨 가므로 눈에는 안 띈다.)

**결정:** 그대로 옮긴다. Spring Security 는 이런 일을 하지 않으므로 매핑에서 직접
갈랐다. 비밀번호를 바꿔야 하는 상태는 예외다 — 그 사람은 아직 로그인한 것이 아니다.

실화면 대조가 이것을 «레거시 36행 / 신규 0행» 으로 보고했다. 로그인한 오프너로
`/login` 을 받으니 레거시는 관리자 대시보드를 돌려주고 신규는 로그인 폼을 돌려줬다.

## D-091 · 사원 리스트의 줄 순서는 정해져 있지 않다

실화면 대조가 사원 리스트에서 «4/15행 다름» 을 보고했다. 그런데 빠진 사람도 더해진
사람도 없었다 — 여섯 명이 자리만 바꿔 앉아 있었다.

```sql
select * from user_view where id <> 'admin' order by dept_name, job_name limit ?, ?
```

SQL 은 양쪽이 같다. 자리를 바꾼 여섯 명의 정렬 키를 보면 답이 나온다.

```
구매팀 대리   권명승 · 도재욱 · 이승윤
생산1팀 사원  김민수 · 박범수 · 송민우
```

**동순위다.** `dept_name, job_name` 이 이 여섯을 가리지 못하고, 동순위의 순서는 DB 가
보장하지 않는다. 실행 계획이나 연결이 달라지면 순서가 달라진다 — 레거시끼리 두 번
받아도 달라질 수 있다.

**결정:** 정렬을 더 붙이지 않는다. 붙이면 레거시와 다른 SQL 이 되고, 순서가 «달라질
수 있는 것» 에서 «다른 것» 으로 바뀐다.

대신 대조 도구가 이 화면을 <b>순서 무관</b>으로 본다. 줄의 내용이 같고 순서만 다르면
KNOWN 으로 넘기고, 내용이 다르면 그대로 FAIL 이다 — 예외가 진짜 차이를 덮지 않는다.

**2단계 후보.** `order by dept_name, job_name, id` 로 순서를 못 박는다. 화면에 보이는
줄은 같고 순서만 정해지므로 잃는 것이 없다.


> **2단계에서 해소했다(D-113).** 이 항목은 1단계(1:1 정합) 시점의 기록이다.

## D-092 · 닫는 태그 하나가 화면을 2단에서 1단으로 무너뜨렸다

관리자 게시판 관리 화면이 레거시에서는 <b>좌우 2단</b>(왼쪽 게시판 목록, 오른쪽 게시글
목록)인데 신규는 세로로 쌓여 있었다. 게시판 목록의 페이지 번호는 화면 오른쪽 끝에
따로 떨어져 떠 있었다.

**게이트도 글자 대조도 전부 통과했다.** 게이트는 요소를 세지 배치를 보지 않고,
`compare_live` 는 표에 찍히는 글자를 견줄 뿐 어디에 놓였는지는 모른다.

원인은 `</div>` 하나였다. 레거시는 여는 태그와 닫는 태그를 교차해 쓴다.

```jsp
        </table>
    </form>      <-- .box 를 닫지 않은 채 form 을 닫는다
</div>
```

브라우저는 이것을 나름의 규칙으로 바로잡는다(D-037). 우리는 Thymeleaf 가 요구하는
대로 `.box` 를 명시적으로 닫았고, 그러면서 <b>닫는 태그가 하나 늘었다.</b> 그 하나가
뒤의 모든 것을 한 단계씩 얕게 만들어 `.right` 가 `.main-notice` 밖으로 밀려났다.

| | 레거시 | 고치기 전 |
|---|---|---|
| `div.page-controller` | `.left` 안 | `.left` 밖 |
| `div.right` | `.main-notice` 안 | `.main-notice` 밖 |

`.main-notice` 가 좌우를 나누는 자리이므로, 밖으로 나간 오른쪽 열은 아래로 떨어진다.

**결정:** 닫는 태그를 레거시와 같은 개수로 맞춘다. 판정 기준은 원문 글자가 아니라
<b>브라우저가 만드는 트리</b>다 — D-037 이 적어 둔 그 원칙이고, 이번에는 그것을
지키지 못해 생긴 결함이다.

고친 뒤 브라우저 DOM 이 한 줄도 어긋나지 않고, 두 화면을 그려 비교한 PNG 가
<b>바이트까지 같다</b>(SHA256 일치).

### 그래서 도구를 하나 더 만들었다

`compare_render.py` 는 두 앱의 화면을 <b>실제로 그려서</b> 견준다. 헤드리스 크롬으로
같은 크기의 그림을 만들어 해시를 맞춰 본다.

원문을 파이썬 파서로 견주는 것으로는 이 결함이 보이지 않았다 — 파이썬 파서와 브라우저가
교차 태그를 <b>다르게</b> 바로잡기 때문에, 원문 기준으로는 두 트리가 같아 보였다.
그려 봐야 보인다.

처음 돌린 결과가 46화면 일치 / 13화면 다름이다. 남은 13화면은 별도 안건으로 둔다(O-014).

## D-093 · 공용 head 조각이 화면마다 다른 CSS 순서를 눌렀다

«검색창이 한 덩어리로 안 묶인다» 를 파다가 뿌리를 찾았다. 마크업은 글자까지 같고 CSS
파일도 바이트까지 같았는데 **목록과 순서**가 달랐다.

```
레거시  common > page > header > index > aside > bootstrap > boardList
신규    bootstrap > common > page > header > aside > boardList
```

`index.css` 가 빠졌고 bootstrap 이 맨 앞으로 왔다. CSS 는 나중에 실은 것이 이기므로
<b>순서가 곧 화면이다.</b> 검색창이 달라 보인 것은 부트스트랩의 입력 규칙이 이기고
지고가 뒤집혔기 때문이다.

레거시를 세어 보니 **56가지 조합**이 있다. 화면마다 손으로 적었고 규칙이 없다.

| | |
|---|---|
| 같은 파일을 두 번 싣는 화면 | `product/*`, `bound/*`, `task/*` |
| `bootstrap2.css` 를 쓰는 화면 | `documentFormList`, `proposalDocument` |
| `main.min.css` 를 혼자 쓰는 화면 | `purchaseTask` |
| 글꼴 아이콘이 놓인 자리 | 화면마다 다르다. `index.jsp` 는 세 번째, 목록 화면들은 맨 앞 |

공용 `fragments/head` 가 다섯 개를 고정으로 싣고 화면은 뒤에 덧붙이기만 했다.
**87화면 중 76화면이 어긋났다.**

**결정:** 조각이 고정 목록을 갖지 않는다. 화면이 자기 목록을 통째로 넘긴다. CDN 도
그 목록에 들어간다 — 놓인 자리가 화면마다 다르므로 조각이 정할 수 없다.

`check_stylesheets.py` 가 화면마다 목록과 순서를 견준다. 정합성 게이트는 `<link>` 를
아예 보지 않고(화면에 «보이는» 요소가 아니므로), 그림 대조는 «다르다» 까지만 말한다.
이 검사가 원인을 바로 짚는다. 87화면 전부 일치한다.

### 이름으로 고르면 안 된다

한 번 실패하고 되돌렸다. `index.css` 가 `css/main/` 과 `css/message/` 두 곳에 있어서,
파일 이름만 보고 고르니 **프로필 화면에 쪽지함 CSS 가 들어갔다.** href 는 그 JSP 가
있는 폴더 기준이므로 경로로 풀어야 한다.

`editor.css` 는 레거시에도 없다 — `postRegister.jsp` 가 없는 파일을 가리킨다. 그 죽은
링크도 그대로 옮긴다. 빼면 화면이 달라지고, 어차피 양쪽 다 404 다.

## D-094 · CSRF 토큰이 form 맨 앞에 붙어 순번을 밀었다

생산 설비 등록 화면에서 «관리자ID» 와 «문서ID» 의 생김새가 서로 바뀌어 있었다.
레거시는 문서ID 칸이 좁고 그 옆에 «문서 선택» 버튼이 붙는데, 신규는 관리자ID 칸이
좁아졌다. **마크업은 글자까지 같았다.**

CSS 가 위치로 요소를 고르기 때문이다.

```css
.form-group:nth-child(3)>[type="text"] { width: 80%; }
```

`th:action` 을 쓰면 Thymeleaf 가 CSRF 토큰을 **form 의 맨 앞 자식**으로 끼워 넣는다.
그러면 세 번째가 문서ID 가 아니라 관리자ID 가 된다 — 한 칸씩 밀린다.

**결정:** 이 화면만 `th:action` 대신 `action` 을 쓰고 토큰을 손으로 **맨 뒤**에 넣는다.
앞쪽 순번이 지켜진다.

```html
<form action="/unit/register" method="post" name="unitFrm">
  ...
  <input type="hidden" name="_csrf" th:value="${_csrf.token}">
</form>
```

이름을 `th:name="${_csrf.parameterName}"` 로 쓰면 안 된다. 추출기가 이름을 «dyn» 으로
보아 allowlist 의 `control:hidden|_csrf|hidden` 과 어긋나고, 이미 허용해 둔 것이
발명으로 잡힌다. Spring 의 기본 이름을 글자로 적는다.

**한 화면만 고친다.** 위치로 고르는 규칙이 있는 CSS 는 `unitRegister.css` 하나뿐이다 —
나머지는 `:last-child` 이거나(드롭다운), `:nth-child(n)` 이라 전부에 걸리거나,
`table-striped:nth-child(1)` 처럼 점이 빠져 아무것도 고르지 못한다. 다 뒤집으면 고치는
자리보다 건드리는 자리가 많아진다.

**게이트가 이 자리를 새로 보게 됐다.** 자동으로 붙던 토큰은 템플릿 원문에 없어 대조
대상이 아니었는데, 손으로 적으니 보인다. allowlist 에 이미 있던 항목이라 통과한다.

## D-095 · 페이지 번호의 태그 중첩이 화면마다 다르다

수·발주 목록에서 페이지 «2», «3» 이 파란 링크가 아니라 회색으로 보였다. 눌러도 갈 수
없는 것처럼 생겼다. 마크업을 보니 `<a>` 와 `<li>` 의 안팎이 뒤집혀 있었다.

```html
레거시  <li><a href="..." class="disabled">1</a></li>
신규    <a href="..." class="disabled"><li>1</li></a>
```

CSS 가 «바로 아래 자식» 을 고르기 때문에 갈린다.

```css
.page-controller>a , .page-numbers>a { ... }   /* 바로 아래 a */
.page-controller a { ... }                     /* 자손 a */
```

뒤집히면 `<a>` 가 `.page-numbers` 의 바로 아래 자식이 되어 위 규칙이 걸리고, 제대로면
`<li>` 아래에 있어 아래 규칙이 걸린다. 색이 달라진다.

**한 모양으로 통일하면 안 된다.** 열두 화면을 전부 `<li><a>` 로 바꿨다가 셋이 고쳐지고
셋이 깨졌다. 레거시가 화면마다 다르게 적어 두었기 때문이다.

| 모양 | 화면 |
|---|---|
| `<li><a>` | 협력업체 목록, 발주 관리, 수주 관리 — **셋뿐** |
| `<a><li>` | 나머지 아홉 |

**결정:** 화면마다 레거시를 읽어 그 모양을 따른다. 세 화면만 고쳤다.

한 화면을 고쳐 놓고 «같은 모양일 것» 이라고 넘겨짚으면 안 된다는 것을 또 배웠다.
레거시에 규칙이 있을 것이라 기대하는 것 자체가 틀렸다.

## D-096 · 스크립트도 화면마다 다르다 — 빠진 것 때문에 버튼이 죽어 있었다

입·출고 등록 화면의 «출고 날짜» 칸이 레거시에는 오늘 날짜로 채워져 있는데 신규는
비어 있었다. 마크업은 글자까지 같았다.

값을 채우는 것은 `js/datepicker.js` 이고, 그것이 도는 데 필요한 **jQuery UI 가 실리지
않았다.** CSS 와 같은 이유다(D-093) — 공용 `fragments/head` 가 다섯 개를 고정으로 싣고
화면은 뒤에 덧붙이기만 했다.

세어 보니 76화면 중 37화면의 스크립트 목록이 어긋났다. 빠진 것들이 하나같이 «눌러야
동작하는» 것들이다.

| 빠진 스크립트 | 화면 수 | 그 화면에서 죽는 것 |
|---|---|---|
| `postcode.v2.js` | 8 | 우편번호 찾기 |
| `location.js` | 7 | 주소 입력 |
| `jquery-ui.js` / `.min.js` | 9 | 날짜 고르기 |
| `ckeditor.js` · `editor.js` | 3 | 본문 편집기 |
| `admin.js` | 3 | 관리자 화면의 찾기 창 |

**결정:** 조각이 스크립트도 목록으로 받는다. CSS 와 같은 구조다.

`csrf.js` 만 우리가 넣는다(D-086). 레거시에 없던 것이고 jQuery 뒤에 와야 하므로 목록
다음에 붙인다 — 화면이 넘기는 목록에는 들어가지 않는다.

### 속성을 지켜야 한다

주소만 옮기면 안 된다. `type="module"` 은 실행 방식을 바꾸고(메인 화면의 FullCalendar),
`integrity` 는 무결성 검사다. 자기 head 를 쓰는 화면은 원래 붙어 있던 속성을 그대로
적는다. 공용 조각을 쓰는 화면은 목록이 주소만 나르므로 CDN 무결성 속성이 빠진다 —
화면에는 영향이 없고, 되살리려면 조각이 속성까지 받아야 한다(2단계 후보).

### 레거시가 CSS 를 `<script>` 로 싣는다

```jsp
<script src="../css/main/taskHistory.css"></script>
```

발주 관리 화면에 있다. 브라우저가 CSS 를 자바스크립트로 실행하려다 조용히 실패하므로
아무 일도 일어나지 않는다. 그대로 옮긴다 — 지우면 화면에 있던 것이 사라진다.

`check_stylesheets.py` 가 이것 때문에 한 번 헛짚었다. 조각 인자를 통째로 훑으면
스크립트 목록의 `.css` 까지 스타일시트로 세어 없던 차이를 보고한다. 두 번째 인자만
보도록 고쳤다.

## D-097 · 제목 뒤의 점 하나가 화면에 찍히고 있었다

수·발주 등록에서 신규 화면 전체가 레거시보다 위로 살짝 붙어 있었고, 레거시에는 화면
왼쪽 위에 점이 하나 찍혀 있었다.

```jsp
<title><%=isSell ? "수주" : "발주"%> 등록 페이지</title>.
```

레거시 `taskRegister.jsp:38` 이 <b>점으로 끝난다.</b> 오타다. `<head>` 안의 글자를
브라우저는 body 첫머리로 끌어내리므로 그 점이 화면에 보이고, 뒤의 모든 것이 그만큼
밀린다.

**결정:** 같은 자리에 같은 점을 둔다. 브라우저 DOM 이 기준이다(D-037) — DOM 에서 그
점은 body 의 첫 글자이므로, 우리 템플릿도 body 첫머리에 점을 적는다.

게이트는 이것을 <b>양쪽 다 못 본다.</b> 레거시 쪽은 추출기가 `<head>` 를 통째로
건너뛰어 안 보이고, 신규 쪽은 body 의 글자라 보인다 — 그래서 충실히 재현하면 오히려
발명으로 잡히는 사각지대다. allowlist 에 사유를 적어 등록했다(`text:static|.|`).

## D-098 · 일찍 닫힌 form 이 푸터를 삼키고 있었다

쪽지함에서 오른쪽 위 «admin 관리자 + 종» 묶음이 신규만 오른쪽으로 밀려 있었고,
신규만 세로 스크롤이 생겼다. 머리글 마크업과 CSS 는 글자까지 같았다.

원인은 머리글이 아니라 <b>푸터의 소속</b>이었다. 소스만 보면 레거시도 `</form>` 뒤에
푸터를 적는다. 그런데 레거시는 `message-main` 을 닫지 않은 채 `</form>` 을 만나고,
HTML 파서는 그때 <b>form 만 스택에서 빼고 열린 div 는 그대로 둔다.</b> 그래서 뒤따르는
푸터가 `message-main` 의 자식이 된다.

| | 레거시(브라우저 DOM) | 신규(고치기 전) |
|---|---|---|
| `message-footer` | `form > message-main` 안 | `message-nav-wrap` 바로 아래 |

균형 잡힌 우리 마크업에서는 푸터가 밖으로 나가 `message-nav-wrap` 의 flex 형제가
됐고, 그 여파로 배치가 어긋났다.

**결정:** 푸터를 `message-main` 안으로 옮긴다. 단 그 안의 `classFrm` 은 밖으로 뺀다 —
바깥 form 이 열린 채로 중첩 form 을 만나면 파서가 <b>안쪽 form 을 버려서</b> JS 의
`$('form[name=classFrm]')` 이 빈손이 되고 받은/보낸함 전환이 죽는다. 레거시는 form
조기 닫힘 덕에 그 자리가 우연히 살았다. classFrm 은 숨은 입력뿐이라 화면에 아무것도
그리지 않는다.

D-092(관리자 게시판)와 같은 뿌리다 — 교차 닫힘을 균형 마크업으로 옮길 때 닫는 태그
하나가 소속을 바꾼다. 이번에도 게이트와 글자 대조는 통과했고 그림 대조만 잡았다.

## D-099 · 조퇴의 주말 규칙이 윗줄과 아랫줄이 다르다

근태 확인은 한 사람의 한 달을 두 줄로 그린다 — 1~16일, 17일~말일. 상태마다 주말
처리가 있는데, <b>조퇴만 줄이 갈린다.</b>

| 상태 | 1~16일(윗줄) | 17일~말일(아랫줄) |
|---|---|---|
| 지각·반차 | 주말이면 지운다 | 주말이면 지운다 |
| 연차 | 주말에도 센다 | 주말에도 센다 |
| **조퇴** | **주말에도 센다** | **주말이면 지운다** |

레거시가 switch 를 두 벌로 복사하면서 한쪽에만 주말 검사를 넣었다. 1~16일의 주말
조퇴는 세어지고 보라색으로 칠해지는데, 17일 뒤의 주말 조퇴는 지워진다.

**결정:** 그대로 옮긴다. 프로필 달력의 연차 주말 규칙(D-077)과 같은 종류의 어긋남이며,
맞추는 쪽이 «고침» 이 되기 때문이다. `AttendanceSheet` 가 두 줄을 한 코드로 만들되
이 갈림만 인자로 받고, 시험이 두 줄을 나란히 놓고 못 박는다.

곁가지 둘. 결근은 주말이면 <b>글자만</b> 지워지고 빨간 style 은 빈 칸에 남는다 —
보이지 않지만 레거시가 그렇게 그린다. 그리고 아는 코드가 아니면 «결근» 글자가 색
없이 남는다(기본 문구가 결근이고 switch 에 default 가 없다).

정상 근무 칸의 시간(HH:mm)은 퇴근이 안 찍혔으면 «지금» 을 퇴근으로 놓고 센다 —
화면을 열 때마다 자란다. 대시보드의 출퇴근 표와 같다.

여기부터는 «레거시와 같은가» 가 아니라 «레거시의 결함을 고쳤는가» 를 적는다.

권한 구멍 둘을 먼저 고쳤다. 고치기 전 동작은 각 원 항목(D-048 등)에 남아 있고,
1단계 마지막 커밋까지는 레거시와 1:1 이었다.

## D-100 · 프로필 수정 화면이 전화번호를 채운다 (D-080 해소)

레거시는 «개인 번호» 칸을 언제나 비워 뒀고, 저장이 그 빈 칸을 받아 적어 **저장할
때마다 전화번호가 지워졌다.** 값을 꺼내 두고 넣는 것을 잊은 오타였다.

**수정:** `th:value` 로 현재 값을 채운다. 한 줄이다. 화면이 채워 주므로 그대로
저장하면 값이 산다. 이미 지워져 있던 번호는 돌아오지 않는다 — 데이터 복구는 별개다.

게이트는 영향이 없다 — 편집 가능한 입력의 value 는 라벨이 아니라 데이터다(D-034).

## D-101 · 일정 고치기가 주인을 본다 (D-083 해소)

레거시는 지우기에만 `and user_tbl_id = ?` 를 걸고 고치기에는 걸지 않았다 — 번호만
맞으면 남의 일정이 고쳐졌다. 부서·전체 일정은 남에게도 보이고 번호는 눌러 보면
뜨므로 아무 수고 없이 뚫리는 구멍이었다.

**수정:** 고치기에도 지우기와 같은 주인 조건을 붙였다. 시험이 «남의 일정은 그대로,
내 일정은 고쳐진다» 를 나란히 못 박는다.

## D-102 · 결재 승인·반려가 «내 차례» 를 확인한다 (D-049 해소)

레거시는 로그인만 보고 결재번호만 맞으면 누구의 결재든 승인·반려했다. 결재선에
없는 사람도, 이미 지나간 차례도 눌 수 있었다.

**수정:** 결재선의 `step` 번째가 누른 사람이고 그 차례가 아직 진행중일 때만
처리한다 — 결재 리스트가 이미 하던 판정(D-052 의 `isTurnOf`)과 같다. 남의 차례를
누르면 권한 화면으로 보낸다. 처리 결과가 세 갈래(처리됨·대상 없음·남의 차례)가
되어 `decide` 가 문자열 대신 `Decision` 을 돌려준다.

대리 결재가 관행이었을 가능성은 D-049 에 적어 둔 그대로다 — 필요하면 위임 기능을
새로 설계할 일이지, 아무나 누를 수 있는 구멍으로 대신할 일이 아니다.

## D-103 · 입·출고 수정이 진짜 사번을 채운다 (D-048 해소)

레거시 extract 가 `bound_view` 의 `user_id` 자리에 `product_id` 를 읽어, 직원을
다시 고르지 않고 저장하면 **담당 사번이 제품 코드로 덮였다.** 조사해 보니 뷰에는
`user_id` 컬럼이 멀쩡히 있다 — 읽는 쪽의 오타였다.

**수정:** `user_id AS userId`. 한 줄이다.

## D-104 · 사원 등록·수정이 화면 값을 전부 저장한다 (D-057 해소)

레거시 등록 처리는 주소 두 줄을 맵에 담지도 않은 채 꺼내 쓰고(둘 다 null),
휴대 전화는 아예 읽지 않았다. 수정 처리는 휴대 전화를 읽지 않으면서 갱신 문장에는
그 칸을 두어 **수정할 때마다 저장된 번호가 지워졌다.**

**수정:** 컨트롤러가 주소 두 줄과 휴대 전화를 받아 넘긴다. SQL 은 원래 값을 그대로
흘리고 있었으므로 손대지 않았다 — 버리는 자리는 컨트롤러뿐이었다.

## D-105 · 부서 수정 화면이 주소를 채운다 (D-059 해소) — 화면 단위 allowlist

레거시는 부서 수정 화면의 주소칸을 언제나 비워 뒀다. 이름만 고치러 들어와도
저장하면 그 빈 값이 주소를 덮었고, **라이브 데이터에 그렇게 지워진 부서가 실제로
남아 있다**(D-059 의 dept 11).

**수정:** 주소 세 칸에 현재 값을 채운다.

이 수정은 여섯 중 유일하게 **게이트 signature 를 바꾼다.** 우편번호·도로명은
readonly 라 value 가 화면 글자이고(D-034), 채우는 순간 라벨이 «우편번호» 에서
«dyn» 으로 바뀐다 — 발명과 누락이 동시에 잡힌다.

그래서 allowlist 에 **화면 단위 승인**을 추가했다. entry 에 `"screen"` 을 적으면
그 화면에서만 승인된다. 전역으로 열면 같은 모양의 진짜 회귀가 다른 화면에서
조용히 통과하기 때문이다 — CSRF 토큰처럼 어디에나 생기는 요소만 전역으로 둔다.
`load_allowlist(path, screen)` 이 골든의 `screen` 이름으로 거르고, 하네스 시험이
«그 화면에서만 열리고 다른 화면에서는 닫힌다» 를 못 박는다.

## D-106 · 발주 수정이 성공한다 — 실패한 수정은 아무것도 바꾸지 않는다 (D-044 해소)

레거시는 수정 SQL 의 `where type = ?` 에 넣을 type 을 채우지 않아 언제나 0 이었고,
**발주(type=1) 수정은 걸리는 행이 없어 늘 «실패» 했다.** 더 나쁜 것은 본체 결과와
무관하게 이력을 지우고 다시 넣어, 실패라고 떠도 제품 이력은 바뀌어 있었다.

**수정 둘:** 컨트롤러가 flag 로 type 을 채운다(수주 0 / 발주 1 — 등록·삭제가 이미
그렇다). 그리고 본체가 수정됐을 때만 이력을 간다 — 실패한 수정은 이력도 그대로다.

## D-107 · 쪽지함 페이징이 동작한다 (D-045 해소)

레거시 페이징 링크는 `javascript:block(...)`·`javascript:paging(...)` 을 부르는데 이
화면이 읽는 어느 스크립트에도 두 함수가 없었다 — 누르면 `ReferenceError`, **쪽지가
15건을 넘으면 1페이지 말고는 볼 수 없었다.**

**수정:** `js/message/index.js` 에 두 함수를 정의했다. 다른 목록 화면들의 정의와
같은 모양이되, 쪽지의 페이징 폼은 `classFrm` 이라 그 폼을 제출한다. 폼에 페이지
번호를 담을 숨은 칸(`nowPage`)이 하나 새로 생겨 allowlist 에 `message-index` 로
좁혀 등록했다. 컨트롤러와 서비스는 처음부터 페이지를 제대로 갈라 두었으므로
서버 쪽은 손대지 않았다.

## D-108 · 게시판 목록 페이징이 동작한다 (D-025 해소)

레거시는 `start` 를 계산해 두고 쓰지 않아 **몇 페이지를 눌러도 0번부터 15건**이
나왔다. 게시판이 4개뿐이라 드러나지 않았을 뿐이다.

**수정:** `pagination.start()` 부터 자른다. 순서는 레거시 그대로 둔다 —
`ORDER BY` 를 더하면 지금 화면에 뜨는 순서가 달라진다(D-025 의 경고 그대로).

## D-109 · 지운 부서·직급의 비트를 걷어낸다 (D-062 해소)

부서를 지우면 그 권한 행만 사라지고 **다른 부서의 `permission` 과 프로그램의
`dept_level` 에는 그 비트가 남았다.** 빈 자리를 찾는 규칙이 그 비트를 새 부서에
다시 주면, 새 부서가 지운 부서의 권한을 그대로 물려받았다.

**수정:** 지울 때 남은 모든 부서 권한 행과 프로그램 행에서 그 비트를 걷어낸다.
계산은 Java 에서 한다 — 레거시의 (부르는 곳 없던) `revokePermission` 은 DB 비트
연산이라 관리자 비트가 걸리면 뒤집히는 자리였고, 쓰지 않는다. 직급 삭제도 결함의
모양이 같아 같은 규칙으로 걷어낸다.

## D-110 · 양식은 내용이 비어 있을 때만 덮는다 (D-076 해소)

레거시는 양식을 고르면 편집기 내용을 무조건 그 양식으로 덮었다 — 문서를 반쯤
쓰다가 양식을 바꾸면 쓰던 글이 사라지고 되돌릴 수도 없었다.

**수정:** 내용이 비어 있을 때만 양식으로 채운다(D-076 에 적어 둔 최소 변경).
빈 문서에서 양식을 고르는 뜻은 그대로 남는다. 한계도 적어 둔다 — 타이핑만 하고
저장하지 않은 글은 양식 선택이 GET 재로딩이라 서버에 온 적이 없고, 서버가 지킬
수 있는 것은 저장된 내용이다.

## D-111 · 비밀번호 재확인이 진짜 문이 됐다 (D-079 해소)

레거시의 재확인 화면은 길목에 놓여 있을 뿐 문이 아니었다 — 수정 화면은 로그인만
보고 열려, 주소를 직접 치면 확인 없이 들어갔다.

**수정:** 확인에 성공하면 세션에 표를 두고, 수정 화면(GET)과 수정 처리(POST)가
그 표를 요구한다. 없으면 확인 화면으로 보낸다. 수정을 마치면 표를 걷는다 — 한 번
통과로 한 번 수정한다. D-079 에 적어 둔 방식 그대로다.

화면 두 장은 그대로라 게이트에는 아무것도 걸리지 않는다. 달라진 것은 사이의 관문
유무이고, 시험이 «표 없으면 막히고, 있으면 열린다» 를 못 박는다.

## D-112 · 문서 없는 수·발주는 빈칸이다 (D-089 해소)

레거시는 문서가 딸리지 않은 수·발주의 «문서» 칸에 `<%=subject%>` 가 null 을 찍어
**«null» 이라는 네 글자가 화면에 떴다.** 1단계에서는 그 네 글자까지 그대로
옮겼고, 실화면 대조가 그것을 지키고 있었다.

**수정:** 빈칸으로 바꾼다(D-089 에 적어 둔 그대로). «-» 같은 표시는 화면에 없던
글자를 지어내는 일이라 넣지 않았다.

실화면 대조가 이제 이 화면에서 레거시와 다른 글자를 본다. 그래서 대조 도구에
**«일부러 달라진 칸» 장치**를 달았다 — 경로별로 (레거시 칸, 신규 칸) 짝을
등록하고, 칸 전체가 정확히 그 짝일 때만 결함이 아니라고 본다. 부분 일치가
아니므로 제목에 우연히 같은 글자가 든 진짜 차이는 덮지 않는다. 그림 대조는
같은 화면을 같은 이유로 KNOWN 처리한다.

## D-113 · 사원 리스트의 줄 순서를 못 박는다 (D-091 해소)

레거시 정렬 키(부서·직급)는 동순위를 가리지 못해 **같은 질의도 실행마다 순서가
달라질 수 있었다** — 레거시끼리 두 번 받아도 달라진다.

**수정:** `ORDER BY dept_name, job_name, id`. 화면에 보이는 줄은 같고 순서만
정해지므로 잃는 것이 없다(D-091 에 적어 둔 그대로).

대조 도구의 순서 무관 처리(D-091)는 **그대로 둔다** — 신규는 이제 흔들리지
않지만 레거시 쪽이 여전히 흔들리기 때문이다. 예외의 조건도 그대로다: 줄의
내용이 다르면 여전히 FAIL 이다.

## D-114 · 달력 위젯의 개발자 PC 주소를 지운다 (D-085 해소)

메인 달력 위젯의 새로고침 아이콘이 **만든 사람 PC 의 주소**
(`http://localhost:5501/index.html`)를 가리키고 있었다. 다른 데서 누르면 아무
데도 가지 않는다.

**수정:** 다른 위젯의 새로고침과 같은 `href=""` 로 맞췄다. «되던 것이 안 되는»
변화가 아니라 애초에 되지 않던 것이다(D-085 에 적어 둔 그대로). 어디로 가야
하는지는 여전히 지어내지 않는다 — 아이콘 셋 중 둘이 장식인 것은 그대로다.

게이트는 «같은 라벨, 다른 대상» 을 라우트 변경(MEDIUM)으로 보므로 allowlist 는
필요 없었다. 그림 대조는 href 가 픽셀을 바꾸지 않아 영향이 없다.

## D-115 · 메인 위젯 권한은 레거시대로 둔다 — 종결 (D-084)

메인 위젯 넷(공지사항·전자결재·자유게시판·받은 쪽지함)은 각자 권한이 걸린
화면인데 메인은 로그인만 본다(D-084). 위젯마다 권한을 보는 안이 2단계 후보로
있었다.

**결정: 바꾸지 않는다**(2026-08-21, 사용자 판단). 메인은 모두에게 같은 모습으로
보이고, 위젯을 눌러 들어가는 순간 각 화면의 권한이 막는다. 근거:

- 사람마다 메인이 달라 보이면(빈 위젯이든 제거든) 화면이 «내 권한 상태» 를
  설명해야 하는 새 문제가 생긴다. 지금은 문이 하나이고 그 문이 확실히 막는다.
- 위젯이 보여 주는 것은 제목·작성자 수준이고, 내용으로 들어가는 길은 전부
  권한이 걸린 화면이다.

바뀐 코드는 없다. 시험이 이 짝을 못 박는다 — 권한 없는 사용자도 메인은 열리고
(IndexScreenTest), 위젯의 목적지는 그 사용자를 막는다.
